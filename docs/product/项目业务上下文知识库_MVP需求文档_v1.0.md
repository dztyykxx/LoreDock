# 项目业务上下文知识库 MVP 需求文档

| 属性 | 内容 |
|---|---|
| 文档版本 | v1.0 |
| 文档日期 | 2026-07-29 |
| 文档状态 | 需求基线稿 |
| 建设周期 | 20 天 |
| 部署范围 | 公司内部环境 |
| 试点项目 | 网络设计工具，Java + Vue 3，约 20 万行代码 |
| 核心客户端 | Web、Claude Code MCP |

## 1. 产品定义

本产品是面向组内开发人员的“项目业务上下文知识库”。

它将人工项目文档、公司原 Wiki 内容、通用业务知识和轻量代码快照集中管理，为开发人员提供可检索、可引用的 Web 问答，同时通过 MCP 向本地 Claude Code 提供业务上下文。

本产品不试图替代本地代码阅读或自动理解整个代码库：

- 云端知识库负责回答“业务是什么、为什么这样设计、有哪些约束和历史经验”；
- Web 问答可参考服务器中带分支和 commit 的代码快照，回答“该快照中如何实现”；
- 本地 Claude Code 以用户本地代码为当前事实，知识库仅补充代码中缺失的业务上下文。

## 2. 背景与问题

组内存在近百个代码仓库，每个仓库通常有 20～30 万行代码。很多项目维护超过五年，但缺少系统文档，业务逻辑、设计原因、兼容规则和历史坑主要依赖口头传递。

公司已有 Wiki，但检索体验较差，开发人员难以通过自然语言快速找到相关内容。即使文档存在，也常因标题、目录、用词或页面结构不同而难以检索。

本次试点选择一个 Java + Vue 3 的本地网络设计工具。该项目约 20 万行代码、业务复杂、几乎没有规范文档。当前已有一份“场景包导入导出”链路文档，内容包括：

- 入口与调用链；
- 场景包格式；
- 导入导出业务规则；
- 兼容性要求；
- 容易遗漏的步骤；
- 历史设计原因；
- 测试和验证方法。

这份文档将作为 MVP 的核心知识样本和演示场景。

## 3. 建设目标

### 3.1 最高优先级目标

在 20 天结束时完成以下现场演示：

1. 在公司内部环境启动系统；
2. 导入网络设计工具项目及两个分支的代码快照；
3. 导入场景包文档和部分原公司 Wiki 内容；
4. 导入一次真实需求文档及其 PR 变更材料，由 Agent 生成“需求到实现”知识草稿；
5. 管理员核对需求项、代码改动和测试证据的映射后发布文档；
6. 在 Web 中提出真实业务问题，得到带来源的回答；
7. 在 Claude Code 中通过 MCP 查询同一问题，获取原始业务知识和引用；
8. Claude Code 结合本地最新代码，辅助定位一次类似需求涉及的文件和修改范围；
9. 对缺少依据的问题明确拒答，并记录知识缺口。

### 3.2 产品目标

- 统一管理项目知识和通用业务知识；
- 改善原 Wiki 内容的检索体验；
- 将业务知识从口头传播转为可持续维护的内容；
- 将需求及其 PR 实现过程沉淀为可追溯知识，使存量项目随每次真实变更逐步补齐文档；
- 让 Web 用户和本地 Agent 使用同一份知识和引用；
- 为未来接入更多项目、定期同步代码和 Welink 内容保留扩展空间。

### 3.3 非目标

MVP 不追求：

- 自动生成完整项目 Wiki；
- 构建 IDE 级代码理解系统；
- 一次性接入近百个仓库；
- 证明长期用户活跃度；
- 替代公司原 Wiki；
- 替代 Git、代码评审或本地 Agent。

## 4. 用户与权限

### 4.1 管理员

管理员负责：

- 创建和维护项目；
- 创建分支信息；
- 上传代码快照；
- 上传、新建和编辑知识文档；
- 设置知识所属范围；
- 触发或重建索引；
- 查看知识缺口反馈。

MVP 只需要一个管理员账号。

### 4.2 组内成员

组内成员可以：

- 浏览项目和知识目录；
- 搜索知识和代码快照；
- 使用 Web 问答；
- 查看回答引用；
- 提交“没有回答、回答错误或知识已过期”反馈。

MVP 使用一个组内共享只读账号，不提供注册、个人资料和细粒度权限。

### 4.3 Claude Code

Claude Code 通过共享 MCP Token 使用只读工具，可以：

- 检索当前项目和通用业务知识；
- 读取指定知识文档；
- 搜索指定项目、分支和代码快照。

MCP 不允许修改知识、修改代码、执行命令或访问其他内部系统。

## 5. 知识范围模型

### 5.1 通用业务知识

适用于多个项目的业务概念、术语、流程、规范和约束。

示例：

- 网络场景、设备、拓扑等通用术语；
- 公司级文件格式规范；
- 通用兼容策略；
- 通用测试和发布要求。

### 5.2 项目级知识

适用于一个项目的所有分支。

示例：

- 项目用途和模块划分；
- 总体架构；
- 业务流程和历史原因；
- 开发、调试和测试方法；
- 与其他系统的关系。

### 5.3 分支级知识

仅适用于指定分支的临时设计、功能变化或实现说明。

### 5.4 代码快照

代码快照必须关联：

- 项目；
- 分支；
- commit；
- 上传或索引时间。

同一个分支在 MVP 中只有一个活动代码快照。上传新快照后，新快照替换旧快照的查询入口；MVP 不提供历史快照查询。

## 6. 查询范围规则

### 6.1 项目查询

用户发起项目查询时必须选择项目，分支默认使用 `main`。

默认检索范围为：

```text
通用业务知识
+ 当前项目的项目级知识
+ 当前项目、当前分支的分支级知识
+ 当前项目、当前分支的活动代码快照
```

不得召回其他项目或其他分支的内容。

### 6.2 全局查询

只有用户明确进入“通用业务知识”或选择“全局搜索”时，才检索通用业务知识。MVP 不提供默认跨项目召回。

### 6.3 分支不存在

如果请求分支没有代码快照：

- 可以返回通用业务知识和项目级知识；
- 可以返回该分支已有的人工知识；
- 不得使用其他分支代码冒充当前分支；
- 必须提示“当前分支代码尚未索引”。

#### 7.3.1 知识生成与定期整理

系统使用 DeepSeek `deepseek-v4-flash` 的 OpenAI 兼容接口辅助生成和整理知识。文档类任务采用受控多 Agent 工作流完成证据提取、编写和独立审查，但模型输出仍只能保存为草稿、报告或知识缺口，不得自动进入正式知识索引。

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-KG-01 | P0 | 生成知识草稿 | 管理员可选择项目、分支、已有文档和有限代码片段，输入生成目标并获得 Markdown 草稿 |
| FR-KG-02 | P0 | 生成依据 | 草稿记录使用的源文档、代码快照、分支、commit、生成时间和模型信息 |
| FR-KG-03 | P0 | 不确定项 | 生成结果单独列出无法确认、来源冲突和需要人工补充的事项 |
| FR-KG-04 | P0 | 审核发布 | 管理员可编辑草稿，确认后发布并触发知识索引更新 |
| FR-KG-05 | P0 | 禁止自动发布 | 模型生成或整理得到的内容不能绕过管理员审核成为正式知识 |
| FR-KG-06 | P1 | 手动知识体检 | 管理员可触发检查，生成过期、重复、冲突和知识缺口报告 |
| FR-KG-07 | P1 | 定期整理任务 | 系统可按周运行知识体检并保存报告，不自动修改正式文档 |
| FR-KG-08 | P1 | 修订建议 | 整理报告可生成合并、补充、归档或更新建议，并可转为待审核草稿 |

MVP 的知识体检只覆盖以下四类问题：

- 文档引用的代码快照已被更新；
- 多篇文档内容疑似重复；
- 文档描述与当前分支代码快照疑似冲突；
- 问答记录中反复出现没有可靠答案的知识缺口。

对于代码冲突，系统只生成待核实项，不要求模型自动判断完整代码语义。定期任务失败不得影响已发布知识的正常检索。

#### 7.3.2 知识 Agent 与 Skill

Web 问答、知识生成和知识整理统一使用同一套受控 Agent Runtime、模型适配、工具权限、项目范围、运行记录和错误语义。Web 项目问答继续使用单 Agent；普通知识生成、需求到实现沉淀和知识体检使用固定、可审计的多 Agent Graph，不建设动态 Agent 创建、LLM 自由规划主流程、跨服务 Agent 或可视化 Graph 编排器。

需求到实现和文档生成的核心流程为：

```text
准备输入
→ 并行提取需求证据、代码证据和测试证据
→ 汇总证据台账
→ 文档编写
→ 独立审查
→ 通过、最多一次自动返工，或等待人工指导
→ 待审核草稿
```

独立审查 Agent 只读取证据台账、草稿、引用、项目约束和审查规则，不读取文档编写 Agent 的隐藏推理或内部消息历史。前端和运行接口也不展示原始思维链，只展示阶段、工具与来源摘要、结构化产物、审查问题、Token、耗时和错误。

Skill 是可版本化的任务说明，至少定义：

- Skill 名称、版本和适用场景；
- 必要输入和允许使用的工具；
- 推荐执行步骤和最大执行步数；
- 输出结构、引用要求和拒答条件；
- 哪些结果只能保存为草稿或报告；
- 示例输入、示例输出和验收样例。

MVP 规划以下 Skill：

| Skill | 优先级 | 用途 | 允许结果 |
|---|---|---|---|
| `project_qa` | P0 | 围绕所选项目和分支检索、补充读取并生成带引用回答 | Web 回答或拒答 |
| `document_writer` | P0 | 根据指定知识、代码片段和写作目标生成结构化文档 | 待审核草稿 |
| `change_documenter` | P0 | 整理需求文档、PR 变更和测试证据，建立需求到实现的映射 | 变更知识草稿 |
| `knowledge_audit` | P1 | 检查过期、重复、冲突和反复出现的知识缺口 | 整理报告 |
| `knowledge_curator` | P1 | 根据整理报告提出合并、补充、归档和修订方案 | 待审核草稿或建议 |

多 Agent 文档工作流至少包含以下固定角色，角色说明同样使用版本化 `SKILL.md`：

| 角色 | 用途 | 关键输出 |
|---|---|---|
| 需求证据 Agent | 拆分需求目标、范围、非目标和验收点 | 带来源的需求条目和未确认项 |
| 代码证据 Agent | 分析 PR/diff、变更文件和指定分支代码快照 | 带 Commit/文件路径的实现证据和版本差异 |
| 测试证据 Agent | 识别测试说明、验证范围和缺失覆盖 | 测试证据、覆盖关系和缺口 |
| 文档编写 Agent | 只依据证据台账和项目记忆生成结构化草稿 | Markdown 草稿及引用 |
| 独立审查 Agent | 检查无引用事实、证据遗漏、版本混淆和结构问题 | 通过、返工或请求人工的结构化审查结果 |

知识 Agent 的内部工具限定为：

- 搜索知识并读取完整文档；
- 搜索指定分支的代码快照并读取有限片段；
- 查询知识缺口、文档元数据和代码快照元数据；
- 读取需求材料、PR 元数据、变更文件列表、diff 和测试证据；
- 保存草稿、引用关系和整理报告；
- 记录运行轨迹、失败原因和 Token 用量。

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-AGENT-01 | P0 | 统一 Agent Runtime | Web 问答和文档生成均通过同一套模型、工具调用和运行记录机制执行 |
| FR-AGENT-02 | P0 | Skill 注册 | 系统可加载启用的 Skill，并记录名称和版本 |
| FR-AGENT-03 | P0 | Skill 选择 | Web 问答自动使用 `project_qa`；普通文档生成使用 `document_writer`；需求与 PR 整理使用 `change_documenter` |
| FR-AGENT-04 | P0 | 工具白名单 | 每个 Skill 只能调用其声明的内部工具，不允许任意执行命令或访问网络 |
| FR-AGENT-05 | P0 | 运行限制 | 每次运行设置最大步骤数、超时时间、检索条数和上下文长度 |
| FR-AGENT-06 | P0 | 可追溯运行 | 保存 Skill 版本、模型、工具调用摘要、输入来源、最终引用和运行状态 |
| FR-AGENT-07 | P0 | 写入隔离 | Agent 只能创建草稿、报告和知识缺口，不能直接修改或发布正式知识 |
| FR-AGENT-08 | P1 | 整理 Skill | 手动或定期任务能够调用 `knowledge_audit`，并按需调用 `knowledge_curator` |
| FR-AGENT-09 | P1 | Skill 配置管理 | 管理员可启用、停用或更新 Skill 配置，不要求在 Web 中制作可视化编排器 |
| FR-AGENT-10 | P0 | 多 Agent 文档工作流 | 需求、代码和测试证据并行提取后，由文档编写 Agent 生成草稿并交给独立审查 Agent；主流程由应用固定，不由模型自由改写 |
| FR-AGENT-11 | P0 | 持久运行与恢复 | 每个可靠节点保存 PostgreSQL 检查点；后端进程中断后运行标记为可恢复，管理员可从最后检查点继续且不重复已完成节点和幂等写入 |
| FR-AGENT-12 | P0 | 人在回路 | 证据不足或独立审查阻断时暂停，管理员可补充方向、允许保留待核实项、要求重写或取消，人工决定绑定具体产物版本并可追溯 |
| FR-AGENT-13 | P0 | 项目记忆 | 每个项目可维护版本化 `PROJECT_MEMORY.md`；运行开始时固定项目记忆版本，项目间严格隔离，低层 Markdown 不能放宽服务端安全与权限规则 |
| FR-AGENT-14 | P0 | 运行过程展示 | Web 展示阶段、并行角色状态、中间产物摘要、来源、审查返工、错误和人工请求，不展示模型原始思维链 |
| FR-AGENT-15 | P0 | 版本快照 | 运行固定工作流、Skill、项目记忆、模型和输出结构版本，运行期间发布的新版本只影响后续新运行 |
| FR-AGENT-16 | P0 | 部分失败与幂等 | 并行步骤部分失败时保留成功产物并显式展示失败；恢复或重试不得重复创建草稿、报告或知识缺口 |

Skill 和项目记忆以 Markdown 作为用户可编辑格式，数据库保存版本、状态、内容哈希、修改人与 ObjectStorage 的不透明 object key；数据库元数据是事实来源。MVP 每个项目只维护一个 `PROJECT_MEMORY.md`，不建设个人记忆、分支记忆、多文件记忆目录或自动从对话提炼记忆。系统安全提示、工具白名单、项目范围、运行限制和发布权限由后端结构化配置强制执行，不允许被 Skill、项目记忆、人工反馈或导入材料覆盖。

运行状态与对话状态必须分离。每次工作流使用独立运行标识和检查点；用户关闭浏览器、切换对话或停止后重新从 IDEA 启动后端，不应丢失已经提交的步骤和中间产物。MVP 采用单机手动恢复：异常遗留的运行显示为“可恢复”，由管理员确认继续，不建设多实例抢占或分布式调度。

内部 Agent 工具与对外 MCP 工具可以复用同一查询服务，但二者的授权边界必须分开。

#### 7.3.3 需求到代码实现的知识沉淀

系统把一次需求及其实现材料组织为一个“变更知识单元”。它不是 PR 管理工具，而是把散落在需求文档、代码改动和测试记录中的信息整理成可长期检索的项目知识。

一个变更知识单元至少关联：

- 项目和目标分支；
- 需求标题、需求正文或上传文件；
- PR 标题、编号或原始 URL；
- base commit、head commit；
- 变更文件列表和 diff/patch；
- 可选的 PR 描述、评审结论、测试说明和人工补充材料；
- Agent 生成的草稿、引用关系和管理员审核状态。

MVP 不依赖具体 Git 平台 API。管理员可以手动填写 PR 元数据并上传 diff/patch、变更文件列表或整理后的 Markdown。后续再接入公司实际使用的 Git 平台，自动拉取 PR 内容。

`change_documenter` 工作流由需求、代码、测试证据角色、文档编写角色和独立审查角色协作完成，生成的文档至少包含：

1. 需求背景、目标和明确的非目标；
2. 需求条目到代码文件或模块的对应关系；
3. 关键调用链和数据流；
4. 新增或修改的业务规则、接口、数据结构和配置；
5. 兼容性、异常处理和容易遗漏的步骤；
6. 测试与验证证据；
7. 实际实现与原需求之间的偏差；
8. 尚未确认的问题和后续建议；
9. PR、分支、commit、文件路径和原始材料引用。

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-CHANGE-01 | P0 | 创建变更知识单元 | 管理员可选择项目和分支，上传需求材料并填写 PR 基本信息 |
| FR-CHANGE-02 | P0 | 导入实现材料 | 支持上传 diff/patch、变更文件列表和 Markdown 格式的测试说明 |
| FR-CHANGE-03 | P0 | 需求实现映射 | Agent 输出需求条目与相关模块、文件路径和变更摘要的映射 |
| FR-CHANGE-04 | P0 | 代码补充读取 | Agent 可在对应分支代码快照中搜索和读取有限片段，以解释 diff 的上下文 |
| FR-CHANGE-05 | P0 | 偏差与缺口 | 无法确认的映射、未实现需求和实现偏差必须单独列出，不得猜测补全 |
| FR-CHANGE-06 | P0 | 草稿审核发布 | 产物首先进入草稿状态，管理员核对后才能发布并参与检索 |
| FR-CHANGE-07 | P0 | 双向追溯 | 发布文档可以查看对应需求、PR、commit 和文件路径；变更知识单元也可查看产出的文档 |
| FR-CHANGE-08 | P1 | 批量沉淀历史变更 | 可连续导入多个历史需求和 PR，但不要求一次批量处理全部历史记录 |
| FR-CHANGE-09 | P0 | 独立证据审查 | 草稿发布前展示证据角色产物和独立审查结果；无来源事实、版本混淆和无法确认的映射必须被阻断或标记为待核实 |
| FR-CHANGE-10 | P0 | 人工整理方向 | 管理员可在证据不足或审查阻断时补充本次整理方向，并可另行确认将指导保存为新的项目记忆版本 |

当 PR diff 对应的 head commit 与当前活动代码快照不一致时，系统必须提示快照版本差异。MVP 可以基于 diff 生成草稿，但不得把当前快照内容误称为该 PR 当时的实现。

### 7.4 代码快照管理

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-CODE-01 | P0 | 导入本地代码快照 | 至少支持 ZIP 上传或服务器目录挂载中的一种，优先满足现场演示 |
| FR-CODE-02 | P0 | 快照元数据 | 上传时必须指定项目、分支和 commit |
| FR-CODE-03 | P0 | 忽略规则 | 默认排除依赖、构建产物、二进制、`.git`、`.env`、证书和密钥类文件 |
| FR-CODE-04 | P0 | 文件全文检索 | 可按关键词搜索当前项目和分支的代码文件 |
| FR-CODE-05 | P0 | 代码片段读取 | 问答和 MCP 可按文件路径读取受限长度的代码片段 |
| FR-CODE-06 | P0 | 替换活动快照 | 同一分支上传新快照后重新建立该分支代码索引 |
| FR-CODE-07 | P1 | 变化摘要 | 如果提供旧、新 commit 信息，显示快照已经变化，不要求自动计算完整 diff |

代码快照只建立文件级切分和全文索引，不做：

- 全量代码向量化；
- 完整 AST 或语义分析；
- 类、方法调用图；
- 跨仓库依赖图；
- 自动生成代码文档。

### 7.5 搜索

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-SRCH-01 | P0 | 知识关键词检索 | 支持对标题、正文和标签进行关键词查询 |
| FR-SRCH-02 | P0 | 知识语义检索 | 支持中文自然语言查询和相似表达召回 |
| FR-SRCH-03 | P0 | 代码全文检索 | 支持按文件内容和路径查询当前分支代码 |
| FR-SRCH-04 | P0 | 范围隔离 | 查询不混入其他项目或分支结果 |
| FR-SRCH-05 | P0 | 来源展示 | 每条结果展示所属范围、标题、片段和来源 |
| FR-SRCH-06 | P1 | 条件过滤 | 支持按标签、知识类型和来源类型过滤 |

业务知识使用关键词与向量语义检索。代码只使用路径和文本关键词检索。

### 7.6 Web 问答

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-QA-01 | P0 | 项目问答 | 用户选择项目和分支后可提出自然语言问题 |
| FR-QA-02 | P0 | Agent 检索增强生成 | DeepSeek `deepseek-v4-flash` 使用 `project_qa` Skill，通过受限工具检索和补充读取后生成回答 |
| FR-QA-03 | P0 | 引用 | 项目事实回答至少包含一个可查看的知识或代码来源 |
| FR-QA-04 | P0 | 快照提示 | 涉及代码时显示分支、commit 和索引时间 |
| FR-QA-05 | P0 | 流式响应 | 支持逐步展示回答；模型暂时不可用时显示明确错误 |
| FR-QA-06 | P0 | 无依据拒答 | 证据不足时明确说明无法回答，不使用通用模型知识猜测项目事实 |
| FR-QA-07 | P0 | 冲突提示 | 代码快照与人工知识矛盾时显示冲突，不静默选择其中一个 |
| FR-QA-08 | P0 | 知识缺口反馈 | 用户可记录问题和缺口类型，不建设完整工单流程 |

### 7.7 事实优先级

- 回答“当前快照如何实现”时，以选择分支的代码快照为准；
- 回答“为什么这样设计、业务规则和历史约束”时，以人工知识为准；
- 两者冲突时必须同时呈现，并提醒代码或知识可能已经过期；
- Claude Code 通过 MCP 获取知识后，必须以用户本地最新代码作为实现事实。

### 7.8 MCP 服务

MCP 是 MVP 正式入口，使用远程 Streamable HTTP，以 Claude Code 完成验收。

#### 7.8.1 `knowledge_search`

用途：检索当前项目、分支和通用业务知识。

建议输入：

```json
{
  "project": "network-designer",
  "branch": "feature/import-export",
  "query": "场景包导入后为什么需要刷新拓扑？",
  "top_k": 5
}
```

#### 7.8.2 `document_read`

用途：读取指定知识文档的完整内容或分页内容。

#### 7.8.3 `code_search`

用途：在指定项目、分支和活动代码快照中执行路径及文本搜索，返回有限代码片段。

#### 7.8.4 MCP 返回要求

每条结果尽量包含：

- 项目标识，或标明属于通用业务知识；
- 分支；
- 文档标题；
- 命中片段；
- 原 Wiki URL 或上传文件名；
- 关联代码文件路径；
- 代码快照 commit；
- 索引或更新时间；
- 相关性分数；
- 内容是否被截断。

MVP 不要求精确代码行号。

MCP 不调用 DeepSeek 生成最终答案，只返回原始上下文和引用，由 Claude Code 自行综合。

### 7.9 最小 Web 页面

MVP 只建设以下页面：

1. **登录页**；
2. **项目列表页**，包含“通用业务知识”入口；
3. **项目详情页**，包含文档目录、变更知识单元、需求和 PR 材料导入、知识草稿生成与审核、Agent 运行列表与详情、项目记忆、整理报告、代码快照上传和重新索引；
4. **问答页**，包含项目与分支选择、问答、来源展示和知识缺口反馈。

不建设仪表盘、个人中心、组织管理和复杂统计页面。

## 8. 可信回答要求

### 8.1 必须拒答的情况

- 没有检索到相关业务知识或代码；
- 只有低相关内容，无法支持结论；
- 用户询问的分支没有代码快照，却要求确认具体实现；
- 问题超出当前项目和通用业务知识范围；
- 来源之间存在无法解释的冲突。

### 8.2 拒答内容

拒答时应：

- 明确说明“当前知识库没有足够依据”；
- 展示少量可能相关的来源；
- 提示代码快照的分支和时间；
- 允许用户创建知识缺口反馈；
- 不允许模型用通用知识补写项目事实。

### 8.3 内容安全

导入的 Wiki、人工文档、需求材料、PR 描述、diff 和源代码均视为不可信数据。其中包含的指令不能改变系统行为，也不能触发命令、网络访问或数据修改。

## 9. 数据来源

| 来源 | MVP 接入方式 | 后续方向 |
|---|---|---|
| 人工整理文档 | Web 新建、编辑或上传 Markdown/文本 | 多人协作、审核、版本 |
| 公司原 Wiki | 系统外转为 Markdown 后一次性导入 | 专用连接器和增量同步 |
| 需求与 PR | 手动录入元数据，上传 Markdown、diff/patch 和变更文件列表 | 对接公司 Git 平台并按合并事件触发知识草稿 |
| 本地代码 | 上传或挂载带分支、commit 的快照 | 定期拉取 Git 仓库和增量索引 |
| 通用业务知识 | 管理员新建或批量导入 | 负责人、复审和适用范围治理 |
| 模型生成内容 | DeepSeek `deepseek-v4-flash` 生成待审核 Markdown 草稿 | 模板化生成、变更驱动更新和多人审核 |
| Welink 群聊/会议 | 不接入，仅预留来源类型 | 人工选择内容、脱敏、摘要和审核后入库 |

## 10. 非功能需求

### 10.1 部署与模型

- 系统部署在公司内部环境；
- 后端采用团队可维护的 Java 技术栈；
- 支持 Docker Compose 启动；
- Embedding 和向量检索可在 CPU 环境运行；
- Web 答案生成调用 DeepSeek `deepseek-v4-flash` OpenAI 兼容接口；
- 模型接口与业务逻辑解耦，接口不可用时文档浏览和搜索仍可使用。
- Agent Runtime、Skill 定义和底层模型接口解耦，替换模型不应改变知识与权限边界。
- 多 Agent 主流程使用应用定义的固定 Graph，不依赖模型动态创建角色或自由修改流程；
- 运行、步骤、公开事件和 Graph 检查点持久化到 PostgreSQL，大型中间 Markdown 产物通过 ObjectStorage 保存；

### 10.2 性能目标

- 普通知识或代码搜索目标响应时间不超过 3 秒；
- MCP 检索目标响应时间不超过 3 秒；
- Web 问答支持流式输出，生成耗时以 DeepSeek `deepseek-v4-flash` 接口实测为准；
- 单次 MCP 和代码片段返回设置长度上限；
- 单个索引任务失败不得破坏现有可查询索引。
- Agent 单次运行必须设置最大步骤数、超时和上下文长度，超限后安全终止并保留错误记录。
- 文档工作流最多自动返工一次；证据不足或再次审查阻断时必须进入人工处理，不允许无限循环；
- 前端以服务端运行快照为事实来源，SSE 中断或页面刷新后可重新获取当前状态；

### 10.3 安全底线

- Web 和 MCP 均不能匿名访问；
- 管理写操作和普通查询操作分离；
- MCP 只读；
- 知识 Agent 按 Skill 使用工具白名单，不能执行 Shell、任意 HTTP 请求或数据库管理操作；
- 项目记忆、Skill、人工反馈和导入材料中的文本不能扩大 Agent 工具、项目范围、文件系统、网络或发布权限；
- Agent 产生的内容只能写入草稿、整理报告或知识缺口，发布操作必须由管理员执行；
- Token 和模型密钥不得写入知识文档、代码快照或日志；
- 默认排除 `.env`、私钥、证书和明显密钥文件；
- 记录导入、重建索引和问答错误，不记录完整密钥和不必要的完整代码内容。

### 10.4 可恢复性

- 原始上传文件与索引状态分离；
- 索引可以删除后重新构建；
- 重新索引失败时继续使用上一个成功索引；
- 项目和知识数据应支持备份。
- Agent 运行、步骤、事件、Skill、项目记忆、检查点和中间产物引用应支持备份；
- 后端异常退出后，已提交检查点的运行可由管理员手动恢复，已完成步骤和幂等写入不得重复；

## 11. MVP 验收

### 11.1 数据验收

- 成功创建两个项目；
- 网络设计工具项目包含 `main` 和一个场景包演示分支；
- 成功导入场景包文档和一批由原 Wiki 转换的 Markdown；
- 成功导入两个分支的代码快照，并记录 commit；
- 成功创建至少一篇通用业务知识。

### 11.2 检索验收

开发前准备 15～20 个真实问题，并为每个问题标注应命中的知识文档或代码文件：

- 约 10 个场景包导入导出问题；
- 约 5 个项目启动、架构或通用业务问题；
- 至少 3 个系统不应回答的问题；
- 至少 2 个使用口语或相似表达的问题。

建议验收目标：

- 至少 80% 的有答案问题在 Top-5 结果中出现正确来源；
- 所有包含项目事实的 Web 答案均展示至少一个来源；
- 无依据问题不编造答案；
- 当前分支查询不返回其他分支代码；
- 代码与文档冲突时能够明确提示。

### 11.3 知识生成与整理验收

- 管理员能够基于场景包文档和指定分支代码片段生成一篇 Markdown 草稿；
- 草稿展示来源文档、分支、commit、生成时间和无法确认的事项；
- 草稿发布前不会出现在普通用户检索和 Web 问答中；
- 管理员编辑并发布后，重新索引即可检索到该文档；
- 手动知识体检能够输出至少一种过期、重复、冲突或知识缺口提示；
- 每周任务只生成报告或草稿，不自动修改已发布知识，失败不得影响已发布知识和检索。

### 11.4 Agent 与 Skill 验收

- Web 问答运行记录显示使用了 `project_qa` Skill 及其版本；
- 文档生成运行记录显示使用了 `document_writer` Skill、工具调用摘要和最终来源；
- 需求实现整理运行记录显示使用了 `change_documenter` Skill；
- Agent 无法调用当前 Skill 白名单以外的工具；
- Agent 达到最大步骤数或超时后能够安全停止，不产生半发布状态；
- Agent 只能保存草稿、报告和知识缺口，不能直接发布文档；
- 修改 Skill 文件后可通过版本号区分新旧运行结果。
- 项目管理员可编辑并发布 `PROJECT_MEMORY.md`，新运行使用新版本，活动运行仍使用启动时固定的旧版本；
- 需求、代码和测试证据 Agent 可并行运行，页面分别展示其状态、产物摘要和来源；
- 文档编写 Agent 只依据证据台账生成草稿，独立审查 Agent 不读取其隐藏推理；
- 独立审查最多自动退回一次，再次阻断时进入等待人工；
- 管理员可补充本次整理方向、允许保留待核实项、要求重写或取消，且反馈绑定具体产物版本；
- IDEA 停止并重新启动后端后，运行显示为可恢复，继续后不重复已完成节点或创建重复草稿；
- 并行步骤部分失败时保留成功中间产物并明确显示失败，不得静默忽略；
- 运行详情不展示模型原始思维链。

### 11.5 需求到实现沉淀验收

- 使用“场景包导入导出”真实需求文档、对应 PR 信息和 diff 创建一个变更知识单元；
- Agent 生成包含需求条目、变更文件、实现摘要、测试证据和未确认项的知识草稿；
- 运行过程展示需求、代码和测试证据角色、文档编写、独立审查及人工决定；
- 每个主要实现结论能够追溯到需求材料、PR、commit 或文件路径；
- 对无法从材料确认的实现关系明确标记，不生成虚假映射；
- 管理员审核发布后，该文档可被 Web 和 MCP 检索到；
- 当 PR head commit 与活动代码快照不一致时显示版本差异提示。

### 11.6 MCP 验收

- Claude Code 可使用共享 Token 连接 MCP；
- 可以调用三个只读工具；
- 同一业务问题能够返回与 Web 使用的同源知识；
- 结果包含项目、分支、来源、文件路径、commit 和更新时间；
- Claude Code 可以结合本地代码完成一次相似需求的文件定位；
- MCP 不调用 DeepSeek 生成最终答案。

### 11.7 权限验收

- 只读账号不能新增、上传、编辑或重新索引；
- 管理员能够完成所有内容维护操作；
- 无效 MCP Token 无法检索内部内容。

## 12. 20 天交付边界

建议按以下顺序交付，后续功能不得阻塞前面的核心链路：

1. 项目、分支、文档和代码快照数据准备；
2. 管理员导入与编辑、普通用户浏览；
3. 业务文档关键词与向量检索；
4. 代码快照全文搜索和片段读取；
5. 可恢复 Agent Runtime、项目记忆、版本化 Skill、`project_qa` 单 Agent 和固定多 Agent 文档工作流；
6. Web 带引用问答和无依据拒答；
7. Claude Code MCP 三个只读工具；
8. 需求文档、PR 材料导入及需求/代码/测试证据并行提取、独立审查和人在回路的需求到实现知识草稿；
9. 知识草稿生成、管理员审核发布；
10. 分支隔离、冲突提示、知识缺口反馈和手动知识体检；
11. Docker Compose、测试、文档和现场演示脚本；
12. `knowledge_audit`、`knowledge_curator`、每周整理任务及其报告/草稿审核入口。

## 14. 后续路线

MVP 验收后，再按实际使用反馈考虑：

1. 定期拉取 Git 仓库并按变更文件更新代码索引；
2. 公司 Wiki 专用连接器和增量同步；
3. 对接公司 Git 平台，在 PR 合并后自动创建待整理任务；
4. Welink 群聊和会议纪要的人工选择、脱敏、摘要、审核和入库；
5. OIDC、个人账号和项目权限；
6. 普通成员编辑、版本历史和审核发布；
7. 更完整的知识过期检测、负责人提醒和多级审核；
8. 更多 MCP 客户端兼容验证；
9. 在真实需求中评估是否需要代码向量、符号索引或调用关系。
10. 评估动态 Supervisor、分布式 Agent、A2A、多实例抢占和自动恢复是否具有真实收益；
11. 扩展多文件、分支级或用户级记忆，并评估自动提炼记忆的审核机制。
