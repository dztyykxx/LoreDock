| 属性 | 内容 |
|---|---|

| 文档日期 | 2026-08-02 |
| 文档状态 | 需求基线稿 |

## 1. 产品定义

本产品是面向组内开发人员的“项目业务上下文知识库”。

它将人工项目文档、公司原 Wiki 内容以及本地开发 Agent 根据需求、PR、代码和测试提炼的 Markdown 候选知识，整理为可持续维护的业务知识。系统为开发人员提供可检索、可引用的 Web 问答，同时通过 MCP 向本地 Agent 提供业务上下文和待审核草稿提交入口。

本产品不试图替代本地代码阅读或自动理解整个代码库：

- 云端知识库负责回答“业务是什么、为什么这样设计、有哪些约束和历史经验”；
- Web 问答只使用管理员发布的知识文档作为项目事实证据，不承诺回答当前代码实现；
- 本地 Claude Code 以用户本地代码为当前事实，知识库仅补充代码中缺失的业务上下文。

## 2. 背景与问题

组内存在近百个代码仓库，每个仓库通常有 20～30 万行代码。很多项目维护超过五年，但缺少系统文档，业务逻辑、设计原因、兼容规则和历史坑主要依赖口头传递。

公司已有 Wiki，但检索体验较差，开发人员难以通过自然语言快速找到相关内容。即使文档存在，也常因标题、目录、用词或页面结构不同而难以检索。

本次试点选择一个 Java + Vue 3 的本地网络设计工具。该项目约 20 万行代码、业务复杂、几乎没有规范文档。当前已有一份“场景包导入导出”链路文档，内容包括：

- 入口与调用链；
- 场景包格式；
- 导入导出业务规则；
- 兼容性要求；
- 容易遗漏的步骤；
- 历史设计原因；
- 测试和验证方法。

这份文档将作为 MVP 的核心知识样本和演示场景。

## 3. 建设目标

### 3.1 最高优先级目标

在 20 天结束时完成以下现场演示：

1. 在公司内部环境启动系统；
2. 导入场景包文档和部分原公司 Wiki 内容；
3. 在 Web 中连续提出真实业务问题，实时看到 Agent、Tool、RAG 来源和引用校验过程，并只基于已发布文档得到带来源的回答；
4. 开发者在本地结合需求、PR、代码和测试生成一份或多份 Markdown 候选知识，先通过 Web 上传到项目待处理草稿列表；
5. 管理员在草稿列表勾选一份或多份草稿并点击“合并整理”，系统才创建知识任务会话和 run；单一知识整理 Agent 根据本地 `knowledge-curator` Workflow Skill，自主调用目录、语义检索、关键词匹配、全文读取、工作区草稿修订和 Diff Tool；
6. 管理员查看 Agent 最终回复、本轮多文档变更和累计 Diff，可在同一会话追加指导让 Agent 继续修改，确认完整修订集合后原子发布并更新索引；
7. 在 Claude Code 中通过 MCP 查询同一问题，获取原始业务知识和引用；
8. Claude Code 结合本地最新代码，辅助定位一次类似需求涉及的文件和修改范围；
9. 对文档缺少依据的问题明确拒答，并记录知识缺口。

### 3.2 产品目标

- 统一管理项目知识和通用业务知识；
- 改善原 Wiki 内容的检索体验；
- 将业务知识从口头传播转为可持续维护的内容；
- 让开发者在本地把每次需求和 PR 提炼为 Markdown 候选知识，再由服务端完成冲突整理、审核、发布和检索；
- 让 Web 用户和本地 Agent 使用同一份知识和引用；
- 为未来接入更多项目、Git 平台和 Welink 内容保留扩展空间。

### 3.3 非目标

MVP 不追求：

- 自动生成完整项目 Wiki；
- 构建 IDE 级代码理解系统；
- 一次性接入近百个仓库；
- 证明长期用户活跃度；
- 替代公司原 Wiki；
- 替代 Git、代码评审或本地 Agent。

### 3.4 当前阶段范围（快速迭代期）

项目当前处于核心流程快速迭代阶段，唯一开发主线是：**接收本地开发 Agent 根据需求、PR、代码和测试提炼的 Markdown，在平台内检索已发布知识、整理冲突并生成可多轮修改的 Diff，经人工审核后发布与检索**。服务端不负责解析 PR 代码或从工程材料生成初始知识。

#### 必须实现（直接服务“可回答”主链路）

- 项目管理：创建、启停和项目范围解析；
- 知识文档全生命周期：导入/编辑、发布/归档、项目/通用范围隔离；
- 知识索引与混合检索：分块、离线 Embedding、关键词与向量候选、RRF、范围复核；
- Markdown 候选知识提交：管理员先通过 Web 向指定项目的待处理草稿列表上传 Markdown，再勾选草稿启动合并整理；后续 MCP 只复用草稿上传 Service，不自动启动 Agent；
- 单 Agent 知识整理：使用一个 `knowledge-curator` Workflow Skill 检索目录和文档，检查重复、冲突、过期和知识缺口，安全修订本次候选草稿并输出待人工审核的 Diff；
- Web 项目问答：创建、历史、详情、SSE 续读、仅带文档引用的回答、无文档证据拒答；
- 知识缺口反馈：幂等记录、问答关联、管理员状态流转；
- 长任务恢复：知识挖掘、冲突整理和等待人工审核的长任务使用 Spring AI Alibaba Graph Checkpoint 保存节点级状态，服务重启后从最近已提交节点继续；
- 认证与会话：固定 ADMIN/MEMBER 账户、Sa-Token 会话；
- 支撑能力：本地对象存储、通用后台任务、系统状态与健康检查。

#### 允许简化

- 认证：固定配置账户，不提供注册、找回密码和细粒度权限；
- Agent 流程：知识整理只使用单一 `ReactAgent` 和本地 `knowledge-curator` Workflow Skill，模型自主选择服务端已注册 Tool，不使用子 Agent 或多 Agent 编排；
- 运行监控：持久化可公开的 Agent、工具、来源和校验摘要并通过 SSE 增量展示，不保存完整提示、证据正文或模型原始思维链；
- 多轮问答：只保存同一会话内用户问题与经校验的最终回答作为后续上下文，不在当前阶段实现活动运行的检查点恢复或详细过程恢复；
- 导入结果：批次统计与条目结果合并为有界 JSON 字段，不单独建表；
- 问答终态说明：失败/终止由服务端稳定错误码映射脱敏 `failureMessage`，不暴露模型原文。

#### 明确延后

- MCP Markdown 提交入口：先用 Web 跑通完整流程，再在同一提交 Service 上增加 MCP Tool，不复制冲突整理流程；
- 代码快照上传、版本维护、全文索引、代码片段读取及其管理页面；已有代码模块保留但不接入当前 MVP 页面、问答和 MCP；
- 前端的分支新增、选择和分支级知识维护；后端已有分支表与接口暂时保留，所有 Web 流程省略分支并由后端统一解析为默认 `main`；
- 子 Agent、多 Agent、分布式 Agent、A2A 和可视化 Graph 编排平台；
- 数据库或 Web Skill 市场、Skill 历史版本、发布与回滚体系；Workflow Skill 以受控本地文件维护；
- 短时 QA 运行的检查点续跑、单次模型流或 Tool 调用内部的精确续传、项目长期记忆，以及多实例自动抢占恢复；
- 生产级审计、完整可观测平台、多级恢复和穷举容错；
- 移动端与窄屏专项布局。

#### 明确不做

- 按微服务、DDD、六边形或多 Maven 子模块重建项目；
- 替代本地代码阅读或自动理解整个代码库；
- 自研 Agent 运行时、安全协议、加密算法或通用基础框架；
- 当前阶段新增与“可回答”主链路无关的新 HTTP 功能或前端页面；
- 在 Web 问答中使用代码快照、PR diff 或模型常识作为项目事实证据；
- 在服务端导入需求、PR、diff/patch、代码或测试材料并自动生成初始业务知识；
- 为覆盖率或测试数量给无业务逻辑小类补测试。

## 4. 用户与权限

### 4.1 管理员

管理员负责：

- 创建和维护项目；
- 上传、新建和编辑知识文档；
- 通过 Web 上传一份或多份 Markdown 到项目待处理草稿列表，并勾选草稿启动合并整理；
- 查看 Agent 检索、关键词匹配、全文读取、冲突发现和草稿修订过程；
- 在同一会话追加指导让 Agent 继续修改，并审核明确修订的 Diff；
- 设置知识所属范围；
- 触发或重建索引；
- 查看知识缺口反馈。

MVP 只需要一个管理员账号。

### 4.2 组内成员

组内成员可以：

- 浏览项目和知识目录；
- 搜索已发布知识；
- 使用 Web 问答；
- 查看回答引用；
- 提交“没有回答、回答错误或知识已过期”反馈。

MVP 使用一个组内共享只读账号，不提供注册、个人资料和细粒度权限。

### 4.3 Claude Code

Claude Code 通过 MCP Token 使用受控工具，可以：

- 检索当前项目和通用业务知识；
- 读取指定知识文档；
- 在网页提交流程验证后，使用独立写入权限向项目待处理草稿列表提交 Markdown 候选知识。

MCP 提交只能创建待处理草稿，不自动启动 Agent；后续仍由管理员在 Web 勾选草稿并启动合并整理。MCP 不允许直接修改或发布正式知识、修改代码、执行命令或访问其他内部系统。

## 5. 知识范围模型

### 5.1 通用业务知识

适用于多个项目的业务概念、术语、流程、规范和约束。

示例：

- 网络场景、设备、拓扑等通用术语；
- 公司级文件格式规范；
- 通用兼容策略；
- 通用测试和发布要求。

### 5.2 项目级知识

适用于一个项目。

示例：

- 项目用途和模块划分；
- 总体架构；
- 业务流程和历史原因；
- 开发、调试和测试方法；
- 与其他系统的关系。

### 5.3 本地开发来源

需求、PR、代码、diff/patch 和测试证据由开发者的本地 Agent 读取和理解，LoreDock 服务端不导入这些原始工程材料，也不负责根据它们生成初始业务知识。本地 Agent 应在每次需求或 PR 完成后提炼一份或多份 Markdown 候选知识，再提交给 LoreDock 进行平台知识冲突整理和人工审核。

候选 Markdown 可携带需求编号、PR 编号或 URL、commit、生成时间和本地 Skill/模型名称等来源说明。这些信息是客户端声明的追溯元数据，服务端未持有原始材料时不得将其表述为已由平台验证的事实证据。

## 6. 查询范围规则

### 6.1 项目查询

用户发起项目查询时只需选择项目。

默认检索范围为：

```text
通用业务知识
+ 当前项目的项目级知识
```

不得召回其他项目的内容。

### 6.2 全局查询

只有用户明确进入“通用业务知识”或选择“全局搜索”时，才检索通用业务知识。MVP 不提供默认跨项目召回。

## 7. 功能需求

### 7.1 登录

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-AUTH-01 | P0 | 管理员登录 | 正确账号可进入管理功能，错误密码被拒绝 |
| FR-AUTH-02 | P0 | 组内只读登录 | 只读账号可浏览、搜索和问答，不能上传或编辑 |
| FR-AUTH-03 | P0 | MCP Token | 无 Token 或错误 Token 的 MCP 请求被拒绝 |

### 7.2 项目管理

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-PROJ-01 | P0 | 创建项目 | 可填写项目名称、标识、简介和主要技术栈 |
| FR-PROJ-03 | P0 | 项目列表 | 普通成员可查看已启用项目 |
| FR-PROJ-04 | P1 | 项目停用 | 管理员可停止项目出现在普通查询入口 |

MVP 完整验收两个项目：网络设计工具项目和一个小型对照项目。前端不提供分支创建、选择或独立知识范围，所有 Web 操作使用后端默认 `main`。

### 7.3 知识文档管理

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-DOC-01 | P0 | 新建知识 | 管理员可创建 Markdown 或纯文本知识 |
| FR-DOC-02 | P0 | 编辑知识 | 管理员可修改标题、正文、标签、来源和适用范围 |
| FR-DOC-03 | P0 | 上传文档 | 支持 Markdown、纯文本和包含 Markdown 的 ZIP |
| FR-DOC-04 | P0 | 知识范围 | 文档可设置为通用或项目级 |
| FR-DOC-05 | P0 | 来源信息 | 可记录原 Wiki URL、上传文件名或人工整理说明 |
| FR-DOC-06 | P0 | 文档浏览 | 普通成员可按项目和目录浏览文档 |
| FR-DOC-07 | P0 | 手动重建索引 | 内容改变后，管理员可触发重新索引 |
| FR-DOC-08 | P1 | 批量导入结果 | 展示导入成功、失败和被忽略的文件 |
| FR-DOC-09 | P0 | 文档状态 | 文档至少支持草稿、已发布、已归档三种状态 |
| FR-DOC-10 | P0 | 发布控制 | 只有管理员确认发布的文档才进入正式检索索引 |
| FR-DOC-11 | P0 | 替代关系 | 新文档可以标记其替代的旧文档，旧文档归档后不参与默认检索 |
| FR-DOC-12 | P0 | 目录子树与批量发布 | 父目录展示自身及全部后代文档并保持递归计数；管理员可勾选当前页草稿后原子批量发布，批量操作不自动替代旧文档或触发重新索引 |

MVP 不直接解析网页、Word、PDF 和附件。原 Wiki 内容需在系统外转换成 Markdown 或纯文本后导入。

项目页面顶部“工作空间”可返回项目列表；公共侧栏的问答入口在当前项目上下文进入项目问答，因此仍可使用该项目范围允许的通用业务知识。无当前项目时必须先选择项目，不建设独立的无项目全局问答数据模型。

#### 7.3.1 Markdown 提交与冲突整理

知识生产与平台整理的责任明确分开：本地开发 Agent 掌握需求、PR、最新代码和测试上下文，负责生成 Markdown 候选知识；LoreDock 只接收候选 Markdown，使用平台已发布知识完成重复、冲突、过期和缺口整理，并通过草稿修订、Diff 和人工审核维护正式知识库。详细交互和 Tool 契约见 [`Markdown知识提交与冲突整理详细流程.md`](./Markdown知识提交与冲突整理详细流程.md)。

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-KG-01 | P0 | 待处理草稿池 | 管理员选择项目后可在网页上传一份或多份 Markdown，每份文档作为独立 `DRAFT` 进入待处理列表，上传本身不启动 Agent |
| FR-KG-02 | P0 | 勾选合并整理 | 管理员勾选同一项目内一份或多份待处理草稿并点击“合并整理”后才创建任务会话和 run；勾选草稿作为不可变输入保留，Agent 只修改任务多文档工作区 |
| FR-KG-03 | P0 | 单 Agent Workflow | 知识整理只使用一个 `knowledge-curator` Agent，其工具选择和整理策略由本地 Workflow Skill 决定，Java 不固定检索或修订顺序 |
| FR-KG-04 | P0 | 目录与文档发现 | Agent 可列出当前项目的知识目录树和指定目录文档，不能访问其他项目或任意文件系统 |
| FR-KG-05 | P0 | 语义检索 | Agent 可在当前项目和允许的通用知识内检索含义相近的已发布文档，并获得有限摘要和稳定来源 ID |
| FR-KG-06 | P0 | 关键词匹配 | Agent 可对平台已发布 Markdown 执行受限关键词或短语匹配，返回文档 ID、标题、匹配行和有限上下文 |
| FR-KG-07 | P0 | 文档全文读取 | Agent 可按已授权文档 ID 读取完整 Markdown；超限文档使用明确分页或分段，不以仅有标题和元数据代替全文 |
| FR-KG-08 | P0 | 冲突发现 | Agent 检查候选 Markdown 与已发布知识的重复、规则冲突、适用范围差异、过期线索和知识缺口 |
| FR-KG-09 | P0 | 判断可见性 | 重复、冲突、过期、缺口、来源和待人工问题由模型在最终 AssistantMessage 中明确说明，不使用专用警告 Tool，也不写入工作文档正文 |
| FR-KG-10 | P0 | 安全草稿修订 | Agent 可删除候选草稿内的重复表达、统一术语、补充适用范围或根据明确证据修正内容，但不自动覆盖或归档正式文档 |
| FR-KG-11 | P0 | 未解决问题 | 无法从已授权来源确定结论时，Agent 保留工作文档事实边界，在最终回复中提出具体问题并正常结束本轮，不自行选择冲突一方 |
| FR-KG-12 | P0 | 版本化草稿 | Agent 先读取当前修订，再通过带基础修订号、幂等键和来源的结构化 Tool 提交正文修改；ADD 工作文档可以幂等改名，MODIFY 标题仍由正式基线固定；每次成功更新形成不可变修订 |
| FR-KG-13 | P0 | Diff 审核 | 一次整理可新增或修改多篇工作文档；页面分别展示本轮净变化和每篇文档从正式/空基线到当前修订的累计 Diff |
| FR-KG-14 | P0 | 多轮继续修改 | 一轮完成后会话保持可继续；新 run 注入有界的历史用户消息和各轮最终回复，并从服务端最新工作区继续，不注入历史 Tool 过程 |
| FR-KG-15 | P0 | 人工确认发布 | 管理员可继续修改或放弃任务；只有明确审核的当前全部有效修订集合可在一个事务内发布并触发一次索引更新 |
| FR-KG-16 | P0 | 禁止自动发布 | Agent 工具集不包含发布能力，模型输出、草稿修订和无冲突结论均不得自动进入正式检索 |

#### 7.3.2 知识 Agent、Workflow Skill 与平台 Tool

Web 问答和知识整理复用受控模型适配、工具注册、项目范围、运行记录和错误语义。知识整理不使用子 Agent 或多 Agent；一个 `ReactAgent` 根据 `knowledge-curator` Workflow Skill 自主调用平台 Tool。Java 只保留业务 Tool、权限与范围、幂等写入、引用完整性、业务产物持久化和正式发布边界，不硬编码检索词、调用次数或 Tool 顺序。

大型 Agent 能力在需求确定阶段就必须判断“框架原生提供还是 LoreDock 自定义”，不能先把自研写成需求、再到实现阶段寻找复用方案。本项目以锁定版本的 Spring AI Alibaba Agent Framework 与 Graph 为运行时事实来源：需求和 OpenSpec 必须先核对本地依赖源码/API及官方资料，明确框架能力、业务扩展与真实缺口。框架已经提供的能力不得由 LoreDock 重复实现：

| 能力 | 直接使用的 Spring AI Alibaba 能力 | LoreDock 只负责 |
|---|---|---|
| 内置 Skill | `ClasspathSkillRegistry`、`SkillsAgentHook`、`SkillsInterceptor` | 随应用发布允许的 Skill，并记录运行摘要 |
| Tool 注册与解析 | Spring AI `ToolCallback`、`ToolCallbackProvider`、`ToolCallbackResolver` | 实现 LoreDock 业务 Tool 及其服务端权限和范围校验 |
| 单 Agent 循环与限制 | `ReactAgent`、框架 Hook/Interceptor、模型/Tool 调用限制 Hook | 配置已确认上限并持久化安全结果摘要 |
| 多轮任务会话 | `ReactAgent`、每轮独立 `RunnableConfig.threadId` | 保存有界问答历史、已提交工作区和每轮状态；失败或提问后创建新 run |

除非当前锁定版本经验证存在不能满足已确认行为的明确缺口，LoreDock 不建设通用 Agent Runtime、Skill Registry/Loader、Tool Registry 框架、Graph Checkpoint 或 Human-in-the-Loop 机制，也不为知识整理建设子 Agent 定义和调度层。

Workflow Skill 使用仓库内的应用资源文件：

- Skill 采用独立目录及 `SKILL.md`，可以包含 `references/`、`examples/` 等只读资源；
- `project-qa` 与 `knowledge-curator` 均从 `src/main/resources/agent-skills` 随应用打包，由 `ClasspathSkillRegistry` 加载，避免启动工作目录影响可用性；
- 运行开始时记录本次使用的 Skill 内容摘要和允许工具；Skill 修改通过应用构建与重启生效；
- 不建设数据库 Skill 版本、在线市场、Web 编辑发布、自动下载执行或复杂回滚体系。

从外部取得的 Skill 视为不可信输入。Skill 只能使用服务端通过 `ToolCallback`/`ToolCallbackResolver` 明确提供且当前任务授权的工具；Shell、任意 HTTP、数据库管理、任意文件系统和正式发布 Tool 不得进入候选集合，下载包携带的脚本默认不得执行。

MVP 规划以下面向用户的协调 Skill：

| Skill | 优先级 | 用途 | 允许结果 |
|---|---|---|---|
| `project-qa` | P0 | 围绕所选项目检索已发布文档并生成带引用回答 | Web 回答或拒答 |
| `knowledge-curator` | P0 | 读取管理员勾选的待处理草稿，恢复多文档工作区，自主检索平台知识并增量新增或修订工作文档 | AssistantMessage、工作文档、Diff 和最终摘要 |

通过 Spring AI ToolCallback 机制注册的 LoreDock 平台 Tool 至少逐步提供：

- 列出当前任务固定的勾选草稿，并读取指定草稿 Markdown；
- 列出当前会话的多文档工作区及最新修订；
- 列出当前项目知识目录树和指定目录文档；
- 语义搜索已发布知识，对已发布 Markdown 执行受限关键词匹配，并按文档 ID 读取全文；
- 创建空草稿、读取当前修订与 Markdown 区块结构；
- 使用 `baseRevision`、幂等键和结构化区块操作更新草稿，并记录来源、变更摘要和不可变修订；
- 查询任意两个草稿修订或正式文档基线之间的 Diff；
- 查询 Agent 运行与已提交的安全产物。

搜索、匹配、全文读取、草稿更新和 Diff 调用都由模型根据当前 Skill 自行决定；服务端不根据问题类型硬编码搜索词、调用次数或顺序。公开沟通使用模型原生 AssistantMessage，不注册专用消息或警告 Tool。

每个知识任务拥有长期会话，但每轮使用独立 Agent run。模型需要人工补充时以普通最终回复提问并结束当前 run；用户回复、运行失败或用户停止后均创建新 run，不恢复旧 Checkpoint。新 run 只携带同项目、同操作者、同会话内有界的历史用户消息和各轮最终回复，历史 Tool 调用与过程消息不注入；当前工作文档和执行事实由 Tool 重新读取。每个 run 仍保留独立状态、用量和错误事实，已经提交的草稿修订继续保留。

草稿是独立于对话文本的受控产物。首次生成先创建空草稿或以待修订正式文档作为基线；Agent 使用 `draft_read` 获取当前修订和区块标识，再以 `draft_update(baseRevision, idempotencyKey, operations, sourceRefs)` 提交插入、替换或删除操作。`sourceRefs` 可以引用本次运行 evidenceId 或当前会话用户消息；新增项目事实必须至少引用有效证据，纯结构、措辞或用户明确要求的修改可以引用用户消息。服务端执行乐观修订校验、范围与来源校验，成功后生成新的不可变修订和可展示 Diff；基础修订过期时拒绝写入并要求 Agent 重新读取。Agent 的最终对话消息只引用草稿修订并总结所做修改，不能携带一份未经过 Tool 落库的“最终全文”替代草稿。

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-AGENT-01 | P0 | 统一 Agent Runtime | Web 问答和知识整理均直接使用 Spring AI Alibaba `ReactAgent`/Graph、工具调用和运行记录机制，不另建通用 Agent Runtime |

内部 Agent Tool 与对外 MCP Tool 可以复用同一查询 Service，但二者的身份、允许参数和授权边界必须分开。

#### 7.3.3 本地提炼与候选知识边界

开发者在本地完成需求或 PR 后，由本地 Agent 结合当前工作区、需求文档、PR、diff 和测试结果提炼 Markdown 业务知识。本地如何读取代码和生成 Markdown 由开发者的 Skill 负责，不属于 LoreDock 服务端实现范围。

LoreDock 对这类输入只承担以下职责：

- 接收一份或多份 Markdown，并保留原始输入和客户端声明的来源元数据；
- 使用平台已发布知识检查重复、冲突、过期和缺口；
- 将可安全处理的问题修订到待审核草稿，将无法确定的问题留给管理员；
- 保存修订、来源、Diff 和会话历史，经管理员明确确认后才发布并更新索引。

MVP 用 Web 上传草稿、勾选合并和对话入口承载完整整理流程，同时提供 MCP Markdown 提交 Tool。MCP 只复用待处理草稿上传 Service，提交后仍由管理员在 Web 勾选并启动合并整理。

### 7.4 代码快照管理

代码快照上传、版本维护、全文索引和片段读取不属于当前 MVP。已有后端代码模块可以保留作为实验性架子，但必须满足：

- 不注册到 Web 问答 Agent 或 MCP 工具；
- 不在当前前端提供上传、重建索引或快照维护入口；
- 不要求用户维护项目历史版本的完整代码副本；
- 不作为知识检索、问答引用或知识整理的事实来源；
- 不因缺少活动代码快照影响文档检索和问答。

“处理过程”是由真实 Agent、Tool、证据和服务端校验事件组成的可公开执行轨迹。模型提供的计划或决策摘要可以作为带明确标签的补充信息，但不能替代真实 Tool 调用，也不能把未执行步骤显示为已完成。页面不展示完整系统提示、完整证据正文或模型原始思维链。

多轮上下文只允许来自当前操作者、当前项目和同一会话中已经完成的用户/助手消息；失败轮次的中间文本、工具返回正文、其他会话及其他项目内容不得进入后续模型输入。服务端必须限制带入轮数或总字符数，超限时采用明确裁剪，不在当前阶段建设自动会话摘要或长期记忆。

### 7.7 事实边界

- Web 问答只以当前范围内已发布的知识文档为项目事实证据；
- 需求、PR、diff/patch、代码和测试材料仅由本地 Agent 用于生成 Markdown 候选知识，不上传为平台问答证据；
- 客户端声明的 PR、commit 等来源元数据仅用于追溯，未经平台验证时不得冒充已验证证据；
- 已发布文档之间存在无法解释的冲突时必须拒答并展示冲突来源；
- 系统不保证知识文档与用户当前代码完全一致，涉及现行实现时必须提示用户核对本地最新代码；
- Claude Code 通过 MCP 获取知识后，必须以用户本地最新代码作为实现事实。

### 7.8 MCP 服务

MCP 使用远程 Streamable HTTP。先完成 Web Markdown 提交与冲突整理验收，再把同一提交 Service 暴露为 MCP Tool；查询和提交使用分离的权限边界。

#### 7.8.1 `knowledge_search`

用途：检索当前项目和通用业务知识。

建议输入：

```json
{
  "project": "network-designer",
  "query": "场景包导入后为什么需要刷新拓扑？",
  "top_k": 5
}
```

#### 7.8.2 `document_read`

用途：读取指定知识文档的完整内容或分页内容。

#### 7.8.3 `knowledge_draft_submit`

用途：使用独立写入权限向指定项目提交一份或多份 Markdown 候选知识，复用 Web 上传能力创建待处理 `DRAFT` 文档。该 Tool 不创建任务会话、不触发 Agent，也不得发布正式知识。

#### 7.8.4 MCP 返回要求

每条结果尽量包含：

- 项目标识，或标明属于通用业务知识；
- 文档标题；
- 命中片段；
- 原 Wiki URL 或上传文件名；
- 可选的 PR、commit 或文件路径来源元数据；
- 索引或更新时间；
- 相关性分数；
- 内容是否被截断。

查询 MCP 不调用 DeepSeek 生成最终答案，只返回原始上下文和引用，由本地 Agent 自行综合。Markdown 提交 MCP 只负责把文档放入待处理草稿列表，后续由管理员在 Web 选择合并范围。

### 7.9 最小 Web 页面

MVP 只建设以下页面：

1. **登录页**；
2. **项目列表页**，包含“通用业务知识”入口；
3. **项目详情页**，包含文档目录、Markdown 上传和待处理草稿列表、草稿勾选与“合并整理”入口、对话式知识任务、可折叠 Agent/Tool 运行过程、安全 Markdown 最终回复、多文档修订、Diff 审核与发布；
4. **问答页**，包含多轮项目会话、可折叠处理过程、流式回答、来源展示、历史会话和知识缺口反馈。

不建设仪表盘、个人中心、组织管理和复杂统计页面。

## 8. 可信回答要求

### 8.1 必须拒答的情况

- 没有检索到相关的已发布业务知识；
- 只有低相关内容，无法支持结论；
- 用户要求确认当前代码实现，但已发布文档没有足够依据；
- 问题超出当前项目和通用业务知识范围；
- 来源之间存在无法解释的冲突。

### 8.2 拒答内容

拒答时应：

- 明确说明“当前知识库没有足够依据”；
- 展示少量可能相关的来源；
- 涉及实现时提示用户核对本地最新代码；
- 允许用户创建知识缺口反馈；
- 不允许模型用通用知识补写项目事实。

### 8.3 内容安全

导入的 Wiki、人工文档、候选 Markdown、来源说明和用户指导均视为不可信数据。其中包含的指令不能改变系统行为，也不能触发命令、任意网络访问、跨项目读取或正式知识发布。

## 9. 数据来源

| 来源 | MVP 接入方式 | 后续方向 |
|---|---|---|
| 人工整理文档 | Web 新建、编辑或上传 Markdown/文本 | 多人协作、审核、版本 |
| 公司原 Wiki | 系统外转为 Markdown 后一次性导入 | 专用连接器和增量同步 |
| 需求、PR 与本地代码 | 由本地开发 Agent 读取并生成 Markdown 候选知识；原始工程材料不导入 LoreDock | 不在服务端扩展需求/PR/代码生成流程 |
| 候选 Markdown | 先通过 Web 提交一份或多份，随后增加复用同一 Service 的 MCP 提交入口 | 保持同一任务会话、冲突整理、草稿和审核流程 |
| 通用业务知识 | 管理员新建或批量导入 | 负责人、复审和适用范围治理 |
| 模型生成内容 | DeepSeek `deepseek-v4-flash` 通过版本化 Tool 增量更新待审核 Markdown 草稿，并以 Diff 审批 | 多人协同评论、逐 hunk 合并和复杂分支修订 |
| Welink 群聊/会议 | 不接入，仅预留来源类型 | 人工选择内容、脱敏、摘要和审核后入库 |

## 10. 非功能需求

### 10.1 部署与模型

- 系统部署在公司内部环境；
- 后端采用团队可维护的 Java 技术栈；
- 支持 Docker Compose 启动；
- Embedding 和向量检索可在 CPU 环境运行；
- Web 答案生成调用 DeepSeek `deepseek-v4-flash` OpenAI 兼容接口；
- 模型接口与业务逻辑解耦，接口不可用时文档浏览和搜索仍可使用。
- Agent Runtime、Skill 定义和底层模型接口解耦，替换模型不应改变知识与权限边界。
- 知识整理 Agent 只使用服务端显式提供的 ToolCallback 候选集合；增加或修改工具调用与整理策略优先修改 `knowledge-curator` Workflow Skill，不在 Java 中复制业务流程；
- 运行、公开事件和最终产物元数据持久化到 PostgreSQL，大型 Markdown 产物通过 ObjectStorage 保存；

### 10.2 性能目标

- 普通知识搜索目标响应时间不超过 3 秒；
- MCP 检索目标响应时间不超过 3 秒；
- Web 问答支持流式输出，生成耗时以 DeepSeek `deepseek-v4-flash` 接口实测为准；
- 单次 MCP 和文档读取返回设置长度上限；
- 单个索引任务失败不得破坏现有可查询索引。
- Agent 单次运行必须设置最大步骤数、超时和上下文长度，超限后安全终止并保留错误记录。
- 单 Agent 运行设置步骤、模型调用、Tool 调用、Token 和超时上限；证据不足时保存未确认项并进入人工处理，不允许无限循环；
- 前端以服务端运行快照为事实来源，SSE 中断或页面刷新后可重新获取当前状态；

### 10.3 安全底线

- Web 和 MCP 均不能匿名访问；
- 管理写操作和普通查询操作分离；
- MCP 查询 Token 只读；Markdown 提交使用独立写入权限，且只能创建待审核输入；
- 知识 Agent 按 Skill 只能使用服务端通过 `ToolCallback`/`ToolCallbackResolver` 为当前运行提供的工具，不能执行 Shell、任意 HTTP 请求或数据库管理操作；
- 项目记忆、Skill、人工反馈和导入材料中的文本不能扩大 Agent 工具、项目范围、文件系统、网络或发布权限；
- Agent 产生的内容只能写入草稿、整理报告或知识缺口，发布操作必须由管理员执行；
- 本地 Workflow Skill 和下载内容不能获得服务端未注册工具、执行携带脚本或扩大项目范围；
- Token 和模型密钥不得写入知识文档、PR 材料或日志；
- 默认排除 `.env`、私钥、证书和明显密钥文件；
- 记录导入、重建索引和问答错误，不记录完整密钥和不必要的完整代码内容。

### 10.4 可恢复性

- 原始上传文件与索引状态分离；
- 索引可以删除后重新构建；
- 重新索引失败时继续使用上一个成功索引；
- 项目和知识数据应支持备份。
- Agent 运行、事件和最终产物引用应支持备份；
- 短时 QA 在后端异常退出后明确失败，由用户创建新运行，不恢复模型流和 Tool 调用内部状态；
- 知识挖掘、冲突整理和等待人工的长任务使用 PostgreSQL Checkpoint，重启后从最近已提交节点继续；
- 恢复不得重复已经提交的草稿、报告、冲突候选、人工决定或其他业务副作用，也不得留下已发布一半的知识；

## 11. MVP 验收

### 11.1 数据验收

- 成功创建两个项目；
- 成功导入场景包文档和一批由原 Wiki 转换的 Markdown；
- 成功通过 Web 向一个项目上传一份或多份 Markdown，并在待处理草稿列表看到各自独立的 `DRAFT` 文档；
- 成功创建至少一篇通用业务知识。

### 11.2 检索验收

开发前准备 15～20 个真实问题，并为每个问题标注应命中的已发布知识文档：

- 约 10 个场景包导入导出问题；
- 约 5 个项目启动、架构或通用业务问题；
- 至少 3 个系统不应回答的问题；
- 至少 2 个使用口语或相似表达的问题。

建议验收目标：

- 至少 80% 的有答案问题在 Top-5 结果中出现正确来源；
- 所有包含项目事实的 Web 答案均展示至少一个来源；
- 无依据问题不编造答案；
- 当前项目查询不返回其他项目文档；
- 询问文档未覆盖的当前代码实现时能够明确拒答并提示核对本地代码。

### 11.3 Markdown 提交与冲突整理验收

- 管理员可在 Web 中选择项目并上传一份或多份 Markdown；上传后不自动运行 Agent，勾选同项目的一份或多份待处理草稿并点击“合并整理”后才获得知识任务会话；
- Agent 实际调用目录列出、语义检索、关键词匹配和全文读取 Tool，命中范围不越过当前项目和允许的通用知识；
- 至少一个重复、冲突、过期或缺口判断在最终回复中说明依据，并且不污染工作文档正文；
- 可明确解决的问题通过版本化 `draft_update` 修改工作文档，无法确定的冲突在最终回复中向人工提问，不自动选择冲突一方；
- 每个任务可新增或修改多篇工作文档；新文档或绑定已有文档的修订均展示本轮与累计服务端 Diff；
- 一轮结束后管理员可在同一会话追加指导，新 run 理解有界的历史问答并基于当前工作区最新修订继续；
- 工作草稿发布前不出现在普通用户检索和 Web 问答中，管理员明确确认当前全部有效修订后才原子发布并触发索引更新。

### 11.4 Agent 与 Skill 验收

- Web 问答运行记录显示使用了 `project-qa` Skill、内容摘要和实际 Agent/Tool 轨迹；
- 知识库整理运行记录显示使用了 `knowledge-curator` Skill；
- Skill 可以从受控本地目录加载，修改文件后下一次新运行生效且不需要重新编译；
- 下载的定义无法调用服务端 ToolCallback 候选集合之外的工具或执行携带脚本；
- 单一 Agent 可以按 Skill 自主选择已注册 Tool，不由 Java 固定检索、复核、冲突分析和草稿修改顺序；
- Agent 达到最大步骤数或超时后能够安全停止，不产生半发布状态；
- Agent 只能保存草稿、报告和知识缺口，不能直接发布文档；
- `project-qa` 无法调用代码搜索或代码片段读取工具；
- 冲突整理的主要结论能追溯到平台 Tool 返回的来源，运行中不出现子 Agent 或未注册权限；
- 管理员可补充本次整理方向、修改草稿、发布或取消；
- IDEA 停止并重新启动后端后，活动 run 明确失败且可在原任务中新建一轮；已提交工作修订继续保留；
- 运行中停止只在安全边界生效，后续用户指导不会被注入正在执行的模型或 Tool 调用；
- 一轮知识整理完成后，管理员可以在同一任务会话追加指令，新运行携带有界问答历史并从当前工作区继续形成新的修订与 Diff；
- `draft_update` 使用基础修订号和幂等键；并发或重试导致的旧修订写入被拒绝，不得覆盖管理员或另一运行已经提交的修改；
- 运行详情展示可公开决策摘要、Agent/Tool/来源和校验事实，不展示完整系统提示、证据正文或模型原始思维链。

### 11.4.1 Web 问答过程与多轮验收

- 当前单 Agent 问答可折叠展示模型阶段、实际 Tool 调用、查询摘要、命中文档标题与数量、引用校验和最终结果；
- 处理过程和最终回答通过 SSE 增量更新，终态仍以服务端详情快照校正；
- 用户可以创建新会话、在当前会话连续追问并查看按会话组织的历史问题与最终回答；
- 后续轮次只使用同一项目、同一操作者、同一会话内的有界已完成消息，不使用失败中间文本或其他会话内容；
- 后端在活动轮次中断后可以明确失败，不要求恢复其详细过程；既有已完成问答仍可查看并继续新一轮。

### 11.5 本地提炼边界验收

- 使用“场景包导入导出”真实需求和 PR，在 LoreDock 之外的本地 Agent 中生成一份 Markdown 候选知识；
- Web 只上传候选 Markdown 和可选来源说明，不上传需求原文、PR diff、完整代码或测试输出；
- 服务端不运行 `change_documenter`，不建设变更知识单元、需求到文件映射或 PR 材料解析流程；
- 候选 Markdown 发布前必须先经过平台冲突整理和人工 Diff 审核。

### 11.6 MCP 验收

- Claude Code 可使用只读 Token 连接查询 MCP；
- 可以调用知识搜索和文档读取两个只读工具；
- 同一业务问题能够返回与 Web 使用的同源知识；
- 结果包含项目、来源、文件路径、commit 和更新时间；
- Claude Code 可以结合本地代码完成一次相似需求的文件定位；
- 网页提交流程稳定后，带独立写入权限的 MCP 可提交一份或多份 Markdown，并返回创建的待处理草稿 ID；该操作不返回会话或 run；
- MCP Markdown 提交不能绕过冲突整理、人工审核或直接发布正式知识；
- 查询 MCP 不调用 DeepSeek 生成最终答案。

### 11.7 权限验收

- 只读账号不能新增、上传、编辑或重新索引；
- 管理员能够完成所有内容维护操作；
- 无效 MCP Token 无法检索或提交内部内容，只读 Token 不得调用 Markdown 提交工具。

## 12. 20 天交付边界

建议按以下顺序交付，后续功能不得阻塞前面的核心链路：

1. 项目和文档数据准备；
2. 管理员导入与编辑、普通用户浏览；
3. 业务文档关键词与向量检索；
4. `project-qa` 的可折叠处理过程、真实 Tool/来源事件、流式结果与多轮项目会话；
5. 接入 Spring AI Alibaba 的本地 Skill、Hook 和原生模型/Tool 循环，不重复建设对应运行时基础；
6. 使用 Spring AI ToolCallback 机制把上传 Markdown 读取、多文档工作区、知识目录、语义检索、关键词匹配、文档全文读取、草稿增量更新和 Diff 工具化；
7. 通过 Web 上传一份或多份 Markdown 到待处理草稿列表，管理员勾选后由单一 `knowledge-curator` Agent 完成可多轮继续的合并、冲突整理和待审核修订；
8. 管理员审核每份草稿的明确 Diff，确认修订后发布并更新索引；
9. 增加复用 Web 草稿上传 Service 的 MCP Markdown 提交入口，并保留已有知识搜索与文档读取工具；
10. Docker Compose、测试、文档和现场演示脚本。
