# 项目业务上下文知识库 MVP 需求文档

| 属性 | 内容 |
|---|---|
| 文档版本 | v1.3 |
| 文档日期 | 2026-08-01 |
| 文档状态 | 需求基线稿 |

## 1. 产品定义

本产品是面向组内开发人员的“项目业务上下文知识库”。

它将人工项目文档、公司原 Wiki 内容、需求材料和 PR 实现信息整理为可持续维护的业务知识，为开发人员提供可检索、可引用的 Web 问答，同时通过 MCP 向本地 Claude Code 提供业务上下文。

本产品不试图替代本地代码阅读或自动理解整个代码库：

- 云端知识库负责回答“业务是什么、为什么这样设计、有哪些约束和历史经验”；
- Web 问答只使用管理员发布的知识文档作为项目事实证据，不承诺回答当前代码实现；
- 本地 Claude Code 以用户本地代码为当前事实，知识库仅补充代码中缺失的业务上下文。

## 2. 背景与问题

组内存在近百个代码仓库，每个仓库通常有 20～30 万行代码。很多项目维护超过五年，但缺少系统文档，业务逻辑、设计原因、兼容规则和历史坑主要依赖口头传递。

公司已有 Wiki，但检索体验较差，开发人员难以通过自然语言快速找到相关内容。即使文档存在，也常因标题、目录、用词或页面结构不同而难以检索。

本次试点选择一个 Java + Vue 3 的本地网络设计工具。该项目约 20 万行代码、业务复杂、几乎没有规范文档。当前已有一份“场景包导入导出”链路文档，内容包括：

- 入口与调用链；
- 场景包格式；
- 导入导出业务规则；
- 兼容性要求；
- 容易遗漏的步骤；
- 历史设计原因；
- 测试和验证方法。

这份文档将作为 MVP 的核心知识样本和演示场景。

## 3. 建设目标

### 3.1 最高优先级目标

在 20 天结束时完成以下现场演示：

1. 在公司内部环境启动系统；
2. 导入场景包文档和部分原公司 Wiki 内容；
3. 在 Web 中连续提出真实业务问题，实时看到 Agent、Tool、RAG 来源和引用校验过程，并只基于已发布文档得到带来源的回答；
4. 由本地 `knowledge_curator` Skill 自主调用预定义子 Agent，检查已有知识的重复、冲突、过期和缺口，生成待审核的整理报告或草稿；
5. 导入一次真实需求文档及其 PR、diff 和测试材料，由复用同一 Tool/子 Agent 平台的 `change_documenter` 生成业务知识草稿；
6. 管理员核对来源、冲突、实现材料和测试证据后发布文档；
7. 在 Claude Code 中通过 MCP 查询同一问题，获取原始业务知识和引用；
8. Claude Code 结合本地最新代码，辅助定位一次类似需求涉及的文件和修改范围；
9. 对文档缺少依据的问题明确拒答，并记录知识缺口。

### 3.2 产品目标

- 统一管理项目知识和通用业务知识；
- 改善原 Wiki 内容的检索体验；
- 将业务知识从口头传播转为可持续维护的内容；
- 将需求及其 PR 实现过程沉淀为可追溯知识，使存量项目随每次真实变更逐步补齐文档；
- 让 Web 用户和本地 Agent 使用同一份知识和引用；
- 为未来接入更多项目、Git 平台和 Welink 内容保留扩展空间。

### 3.3 非目标

MVP 不追求：

- 自动生成完整项目 Wiki；
- 构建 IDE 级代码理解系统；
- 一次性接入近百个仓库；
- 证明长期用户活跃度；
- 替代公司原 Wiki；
- 替代 Git、代码评审或本地 Agent。

### 3.4 当前阶段范围（快速迭代期）

项目当前处于核心流程快速迭代阶段，唯一开发主线是：**把需求文档、PR 实现材料和已有文档整理为可审核、可发布、可检索的业务知识，再用文档问答验证知识是否真正可用**。以下四类范围是对全文需求在当前阶段的取舍，后续文档、OpenSpec 和实现必须与之一致。

#### 必须实现（直接服务“可回答”主链路）

- 项目管理：创建、启停和项目范围解析；
- 知识文档全生命周期：导入/编辑、发布/归档、项目/通用范围隔离；
- 知识索引与混合检索：分块、离线 Embedding、关键词与向量候选、RRF、范围复核；
- 需求与 PR 知识提取：导入需求、PR 元数据、diff/patch 和测试说明，生成可追溯的待审核业务知识草稿；
- 知识库整理：检查重复、冲突、过期和知识缺口，生成待审核的整理报告或草稿；
- Web 项目问答：创建、历史、详情、SSE 续读、仅带文档引用的回答、无文档证据拒答；
- 知识缺口反馈：幂等记录、问答关联、管理员状态流转；
- 长任务恢复：知识挖掘、冲突整理和等待人工审核的长任务使用 Spring AI Alibaba Graph Checkpoint 保存节点级状态，服务重启后从最近已提交节点继续；
- 认证与会话：固定 ADMIN/MEMBER 账户、Sa-Token 会话；
- 支撑能力：本地对象存储、通用后台任务、系统状态与健康检查。

#### 允许简化

- 认证：固定配置账户，不提供注册、找回密码和细粒度权限；
- Agent 流程：协调 Agent 只从本地文件中预定义的子 Agent 和服务端已注册工具中动态选择，不允许模型创建任意角色或扩大工具权限；
- 运行监控：持久化可公开的 Agent、工具、来源和校验摘要并通过 SSE 增量展示，不保存完整提示、证据正文或模型原始思维链；
- 多轮问答：只保存同一会话内用户问题与经校验的最终回答作为后续上下文，不在当前阶段实现活动运行的检查点恢复或详细过程恢复；
- 导入结果：批次统计与条目结果合并为有界 JSON 字段，不单独建表；
- 问答终态说明：失败/终止由服务端稳定错误码映射脱敏 `failureMessage`，不暴露模型原文。

#### 明确延后

- MCP 工具与身份校验：当前阶段不做 MCP 摘要、身份校验和模型生成；
- 代码快照上传、版本维护、全文索引、代码片段读取及其管理页面；已有代码模块保留但不接入当前 MVP 页面、问答和 MCP；
- 前端的分支新增、选择和分支级知识维护；后端已有分支表与接口暂时保留，所有 Web 流程省略分支并由后端统一解析为默认 `main`；
- 任意动态创建子 Agent、分布式 Agent、A2A 和可视化 Graph 编排平台；
- 数据库或 Web Skill 市场、Agent 定义历史版本、发布与回滚体系；Skill 和 Agent Spec 以受控本地文件维护；
- 短时 QA 运行的检查点续跑、单次模型流或 Tool 调用内部的精确续传、项目长期记忆，以及多实例自动抢占恢复；
- 生产级审计、完整可观测平台、多级恢复和穷举容错；
- 移动端与窄屏专项布局。

#### 明确不做

- 按微服务、DDD、六边形或多 Maven 子模块重建项目；
- 替代本地代码阅读或自动理解整个代码库；
- 自研 Agent 运行时、安全协议、加密算法或通用基础框架；
- 当前阶段新增与“可回答”主链路无关的新 HTTP 功能或前端页面；
- 在 Web 问答中使用代码快照、PR diff 或模型常识作为项目事实证据；
- 为覆盖率或测试数量给无业务逻辑小类补测试。

## 4. 用户与权限

### 4.1 管理员

管理员负责：

- 创建和维护项目；
- 上传、新建和编辑知识文档；
- 导入需求、PR、diff/patch 和测试说明并生成知识草稿；
- 触发知识整理并审核整理建议；
- 设置知识所属范围；
- 触发或重建索引；
- 查看知识缺口反馈。

MVP 只需要一个管理员账号。

### 4.2 组内成员

组内成员可以：

- 浏览项目和知识目录；
- 搜索已发布知识；
- 使用 Web 问答；
- 查看回答引用；
- 提交“没有回答、回答错误或知识已过期”反馈。

MVP 使用一个组内共享只读账号，不提供注册、个人资料和细粒度权限。

### 4.3 Claude Code

Claude Code 通过共享 MCP Token 使用只读工具，可以：

- 检索当前项目和通用业务知识；
- 读取指定知识文档；

MCP 不允许修改知识、修改代码、执行命令或访问其他内部系统。

## 5. 知识范围模型

### 5.1 通用业务知识

适用于多个项目的业务概念、术语、流程、规范和约束。

示例：

- 网络场景、设备、拓扑等通用术语；
- 公司级文件格式规范；
- 通用兼容策略；
- 通用测试和发布要求。

### 5.2 项目级知识

适用于一个项目。

示例：

- 项目用途和模块划分；
- 总体架构；
- 业务流程和历史原因；
- 开发、调试和测试方法；
- 与其他系统的关系。

### 5.3 PR 实现材料

PR 实现材料用于生成知识草稿，不作为 Web 问答或 MCP 的直接检索证据。材料至少关联项目、PR 标识和可选的 base/head commit，可包含 diff/patch、变更文件列表、测试说明及人工补充内容。Git 分支名可以出现在原始 PR 材料中，但 LoreDock 不把它建模为项目内知识范围。

MVP 不保存和维护仓库的每个代码版本。commit 仅作为来源元数据，系统不承诺 PR 材料与用户当前本地代码一致；需要确认当前实现时，开发人员必须核对本地最新代码。

## 6. 查询范围规则

### 6.1 项目查询

用户发起项目查询时只需选择项目。

默认检索范围为：

```text
通用业务知识
+ 当前项目的项目级知识
```

不得召回其他项目的内容。

### 6.2 全局查询

只有用户明确进入“通用业务知识”或选择“全局搜索”时，才检索通用业务知识。MVP 不提供默认跨项目召回。

MVP 不直接解析网页、Word、PDF 和附件。原 Wiki 内容需在系统外转换成 Markdown 或纯文本后导入。

项目页面顶部“工作空间”可返回项目列表；公共侧栏的问答入口在当前项目上下文进入项目问答，因此仍可使用该项目范围允许的通用业务知识。无当前项目时必须先选择项目，不建设独立的无项目全局问答数据模型。

#### 7.3.1 知识生成与定期整理

系统使用 DeepSeek `deepseek-v4-flash` 的 OpenAI 兼容接口辅助生成和整理知识。完成单 Agent 问答过程展示与多轮会话后，下一条核心开发主线是把知识搜索、文档读取、材料读取、草稿增量更新、版本差异、冲突报告和人工审核等平台能力统一注册为安全 Tool，再由本地文件中的协调 Skill 和预定义子 Agent 完成知识挖掘与冲突整理。知识任务以系统或管理员触发的长期对话运行；模型最终消息只说明进展、结论和下一步，文档内容必须通过版本化草稿 Tool 修改，不把一次全量 Markdown 输出直接当成待审核事实。模型产物不得自动进入正式知识索引。

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-KG-01 | P0 | 生成知识草稿 | 管理员导入需求、PR 元数据、diff/patch 和测试说明后获得结构化 Markdown 业务知识草稿 |
| FR-KG-02 | P0 | 生成依据 | 草稿记录使用的需求材料、PR、diff/patch、测试说明、可选 commit、生成时间和模型信息 |
| FR-KG-03 | P0 | 不确定项 | 生成结果单独列出无法确认、来源冲突和需要人工补充的事项 |
| FR-KG-04 | P0 | 审核发布 | 管理员可编辑草稿，确认后发布并触发知识索引更新 |
| FR-KG-05 | P0 | 禁止自动发布 | 模型生成或整理得到的内容不能绕过管理员审核成为正式知识 |
| FR-KG-06 | P0 | 手动知识整理 | 管理员可触发检查，生成过期、重复、冲突和知识缺口报告 |
| FR-KG-07 | P1 | 定期整理任务 | 系统可按周运行知识整理并保存报告，不自动修改正式文档 |
| FR-KG-08 | P0 | 修订建议 | 整理报告可生成合并、拆分、补充、归档或更新建议，并可转为待审核草稿 |
| FR-KG-09 | P0 | 多 Agent 知识挖掘 | 协调 Agent 可按任务需要调用检索、证据审查和文档整理子 Agent，主要结论均可追溯到平台 Tool 返回的来源 |
| FR-KG-10 | P0 | 冲突整理编排 | 协调 Agent 可根据检索结果决定继续检索、调用冲突审查、生成待核实项或形成整理建议，不在 Java 中固定业务步骤 |
| FR-KG-11 | P0 | 对话式知识任务 | 手动或定时触发均创建可查看的知识任务会话；系统触发信息作为首条消息，后续 Agent、Tool、来源、草稿变更和用户指导归属同一会话 |
| FR-KG-12 | P0 | 安全暂停与引导 | 管理员可请求暂停运行；系统在当前模型/Tool 步骤结束后的 Checkpoint 进入等待状态，再接收用户指导并继续，不在调用执行中途注入消息 |
| FR-KG-13 | P0 | 增量草稿更新 | Agent 先读取当前草稿修订，再通过带基础修订号、幂等键和来源引用的结构化 `draft_update` 操作插入、替换或删除 Markdown 区块；不得用最终消息绕过 Tool 全量覆盖草稿 |
| FR-KG-14 | P0 | Diff 审批 | 每次草稿更新形成不可变修订及来源关联；管理员按基线与当前修订的 Markdown Diff 审核，发布的必须是明确选中的最新修订 |
| FR-KG-15 | P0 | 完成后继续调整 | 一轮整理完成后会话保持可继续；管理员追加修改意见会基于当前草稿修订创建新的 Agent 运行和修订历史，不覆盖既有过程 |

MVP 的知识整理只覆盖以下四类问题：

- 多篇文档内容疑似重复；
- 已发布文档之间的规则或适用范围疑似冲突；
- 文档来源、更新时间或人工反馈表明内容可能过期；
- 问答记录中反复出现没有可靠答案的知识缺口。

整理结果只生成报告、建议或待审核草稿，不直接合并、归档或覆盖正式文档。MVP 审批当前修订的完整 Diff，不建设 Git 式分支、自动三方合并或逐 hunk 合并器；需要局部调整时，管理员通过同一任务会话要求 Agent 再修改，或直接编辑草稿形成新修订。定期任务失败不得影响已发布知识的正常检索。

#### 7.3.2 知识 Agent、Skill、Agent Spec 与平台 Tool

Web 问答、知识生成和知识整理复用同一套受控模型适配、工具注册、项目范围、运行记录和错误语义。业务编排尽量由 Skill 和预定义子 Agent 驱动；Java 只保留 LoreDock 业务 Tool、权限与范围、幂等写入、引用完整性、业务产物持久化和正式知识发布边界，不为“先检索、再审查、再整理”等业务顺序编写固定流程。

大型 Agent 能力在需求确定阶段就必须判断“框架原生提供还是 LoreDock 自定义”，不能先把自研写成需求、再到实现阶段寻找复用方案。本项目以锁定版本的 Spring AI Alibaba Agent Framework 与 Graph 为运行时事实来源：需求和 OpenSpec 必须先核对本地依赖源码/API及官方资料，明确框架能力、业务扩展与真实缺口。框架已经提供的能力不得由 LoreDock 重复实现：

| 能力 | 直接使用的 Spring AI Alibaba 能力 | LoreDock 只负责 |
|---|---|---|
| 本地 Skill | `FileSystemSkillRegistry`、`SkillsAgentHook`、`SkillsInterceptor` | 受控目录配置、允许 Skill 和运行摘要 |
| 文件化子 Agent | `AgentSpecLoader`、`AgentSpecReactAgentFactory`、`TaskToolsBuilder` | 提供 Agent Spec 文件并校验其 Tool 名称 |
| 动态子 Agent 调用 | `TaskTool`、`TaskOutputTool`、`AgentTool` | 决定哪些预定义子 Agent 和业务 Tool 可用 |
| Tool 注册与解析 | Spring AI `ToolCallback`、`ToolCallbackProvider`、`ToolCallbackResolver` | 实现 LoreDock 业务 Tool 及其服务端权限和范围校验 |
| Agent 循环与限制 | `ReactAgent`、框架 Hook/Interceptor、模型/Tool 调用限制 Hook | 配置已确认上限并持久化安全结果摘要 |
| 长任务暂停与恢复 | `PostgresSaver`、`RunnableConfig.threadId`、Graph interrupt、Human-in-the-Loop | 稳定业务 threadId、幂等副作用和页面状态投影 |

除非当前锁定版本经验证存在不能满足已确认行为的明确缺口，LoreDock 不建设通用 Agent Runtime、Skill Registry/Loader、Agent Spec Loader、子 Agent 调度器、Tool Registry 框架、Graph Checkpoint 或 Human-in-the-Loop 机制。

Skill 和 Agent Spec 都使用本地文件：

- Skill 采用独立目录及 `SKILL.md`，可以包含 `references/`、`examples/` 等只读资源；
- 子 Agent 使用带 YAML frontmatter 的 Markdown Agent Spec，至少声明名称、用途和允许工具；
- 开发环境从仓库内受控目录读取，部署环境可从本地挂载目录读取；通过 Git、ZIP 或人工下载放入目录后，下一次新运行可以加载修改后的内容，不要求重新编译；
- 运行开始时固定本次使用的 Skill、Agent Spec 内容摘要和允许工具，执行期间文件变化只影响后续新运行；
- 不建设数据库 Skill 版本、在线市场、Web 编辑发布、自动下载执行或复杂回滚体系。

从外部取得的 Skill 和 Agent Spec 视为不可信输入。文件只能引用服务端通过 `ToolCallback`/`ToolCallbackResolver` 明确提供且当前任务授权的工具；未知工具必须在模型调用前明确失败，Shell、任意 HTTP、数据库管理、任意文件系统和正式知识发布 Tool 不得进入候选集合。下载包携带的脚本默认不得执行。

协调 Agent 可以通过 Spring AI Alibaba 的 Agent Tool、TaskTool 或等价子 Agent 能力，自行决定是否以及何时调用本地文件中预定义的检索、证据审查、冲突分析和回答/文档整理 Agent。模型不得创建未注册角色、为子 Agent 增加工具或切换到其他项目范围。固定顺序的 `SequentialAgent` 只用于产品明确要求的确定性流程，不作为知识挖掘与冲突整理的默认实现。

MVP 规划以下面向用户的协调 Skill：

| Skill | 优先级 | 用途 | 允许结果 |
|---|---|---|---|
| `project_qa` | P0 | 围绕所选项目检索已发布文档并生成带引用回答 | Web 回答或拒答 |
| `change_documenter` | P0 | 整理需求文档、PR 变更和测试证据，建立需求到实现的映射 | 变更知识草稿 |
| `knowledge_curator` | P0 | 挖掘现有知识、检查过期/重复/冲突/缺口并提出整理方案 | 整理报告、待审核草稿或建议 |

预定义子 Agent 至少覆盖：

- `knowledge_researcher`：使用知识搜索和文档读取 Tool，自行决定查询词和必要的补充检索；
- `evidence_reviewer`：检查候选结论、证据覆盖、版本混淆和待核实项；
- `conflict_reviewer`：比较多个已发布来源，输出冲突点、适用范围差异和处理建议；
- `answer_writer`/`document_writer`：只根据已取得证据和审查结果形成最终回答或待审核文档。

通过 Spring AI ToolCallback 机制注册的 LoreDock 平台 Tool 至少逐步提供：

- 搜索知识和读取指定文档；
- 查询知识缺口、人工反馈和文档元数据；
- 读取需求材料、PR 元数据、变更文件列表、diff 和测试证据；
- 创建空草稿、读取当前修订与 Markdown 区块结构；
- 使用 `baseRevision`、幂等键和结构化区块操作更新草稿，并记录来源、变更摘要和不可变修订；
- 查询任意两个草稿修订或正式文档基线之间的 Diff；
- 保存引用关系、整理报告、冲突候选和知识缺口；
- 查询 Agent 运行与已提交的安全产物。

搜索、读取和子 Agent 调用都由模型根据当前 Skill 自行决定；服务端不根据问题类型硬编码搜索词、检索次数或子 Agent 顺序。定时任务只负责在确定项目范围内触发指定 Skill，不复制 Skill 内的知识整理流程。

知识挖掘、冲突整理和等待人工确认属于可恢复长任务。每个任务拥有长期会话：首次系统/人工触发创建一个独立 Agent run，等待状态下的用户指导恢复同一个 run，一轮正常完成后的追加调整再创建新的 run。消息、公开执行事件、草稿修订和引用都按会话串联，但每个 run 仍保留独立状态、用量和错误事实。系统直接使用 Spring AI Alibaba Graph 的 `PostgresSaver`、稳定 `RunnableConfig.threadId`、interrupt 和 Human-in-the-Loop，把框架状态保存到项目 PostgreSQL；服务重启后由应用识别未完成运行，并从最近已提交 Checkpoint 的下一节点继续。Graph 是 Agent Framework 的状态与恢复底座，LoreDock 不复制 Checkpoint 或暂停恢复执行器，也不把知识业务顺序硬编码为固定节点。

管理员请求暂停时，页面先显示 `PAUSE_REQUESTED`，该状态只投影框架执行事实；框架在安全边界产生 interrupt 并提交 Checkpoint 后，页面才显示 `WAITING_FOR_USER`，用户指导再通过 human feedback 恢复同一 thread。系统不得尝试中断正在传输的模型响应后继续半段文本，也不得在 Tool 副作用是否提交不明时直接切换指令。Checkpoint 之后可能重放的写 Tool 必须使用稳定业务幂等键，已经提交的草稿修订、报告、冲突候选或人工决定不得重复写入。短时 `project_qa` 仍采用中断后失败并新建运行重试。

草稿是独立于对话文本的受控产物。首次生成先创建空草稿或以待修订正式文档作为基线；Agent 使用 `draft_read` 获取当前修订和区块标识，再以 `draft_update(baseRevision, idempotencyKey, operations, sourceRefs)` 提交插入、替换或删除操作。`sourceRefs` 可以引用本次运行 evidenceId 或当前会话用户消息；新增项目事实必须至少引用有效证据，纯结构、措辞或用户明确要求的修改可以引用用户消息。服务端执行乐观修订校验、范围与来源校验，成功后生成新的不可变修订和可展示 Diff；基础修订过期时拒绝写入并要求 Agent 重新读取。Agent 的最终对话消息只引用草稿修订并总结所做修改，不能携带一份未经过 Tool 落库的“最终全文”替代草稿。

#### 7.3.3 需求到代码实现的知识沉淀

系统把一次需求及其实现材料组织为一个“变更知识单元”。它不是 PR 管理工具，而是把散落在需求文档、代码改动和测试记录中的信息整理成可长期检索的项目知识。

一个变更知识单元至少关联：

- 项目；
- 需求标题、需求正文或上传文件；
- PR 标题、编号或原始 URL；
- base commit、head commit；
- 变更文件列表和 diff/patch；
- 可选的 PR 描述、评审结论、测试说明和人工补充材料；
- Agent 生成的草稿、引用关系和管理员审核状态。

MVP 不依赖具体 Git 平台 API。管理员可以手动填写 PR 元数据并上传 diff/patch、变更文件列表或整理后的 Markdown。后续再接入公司实际使用的 Git 平台，自动拉取 PR 内容。

`change_documenter` 使用上传材料完成提取、编写和检查，生成的文档至少包含：

1. 需求背景、目标和明确的非目标；
2. 需求条目到代码文件或模块的对应关系；
3. 关键调用链和数据流；
4. 新增或修改的业务规则、接口、数据结构和配置；
5. 兼容性、异常处理和容易遗漏的步骤；
6. 测试与验证证据；
7. 实际实现与原需求之间的偏差；
8. 尚未确认的问题和后续建议；
9. PR、commit、文件路径和原始材料引用。

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-CHANGE-01 | P0 | 创建变更知识单元 | 管理员可选择项目，上传需求材料并填写 PR 基本信息 |
| FR-CHANGE-02 | P0 | 导入实现材料 | 支持上传 diff/patch、变更文件列表和 Markdown 格式的测试说明 |
| FR-CHANGE-03 | P0 | 需求实现映射 | Agent 输出需求条目与相关模块、文件路径和变更摘要的映射 |
| FR-CHANGE-04 | P0 | 材料边界 | Agent 只使用本次上传的需求、PR、diff/patch、变更文件列表、测试说明和人工补充材料，不依赖完整代码快照 |
| FR-CHANGE-05 | P0 | 偏差与缺口 | 无法确认的映射、未实现需求和实现偏差必须单独列出，不得猜测补全 |
| FR-CHANGE-06 | P0 | 草稿审核发布 | 产物首先进入草稿状态，管理员核对后才能发布并参与检索 |
| FR-CHANGE-07 | P0 | 双向追溯 | 发布文档可以查看对应需求、PR、commit 和文件路径；变更知识单元也可查看产出的文档 |
| FR-CHANGE-08 | P1 | 批量沉淀历史变更 | 可连续导入多个历史需求和 PR，但不要求一次批量处理全部历史记录 |
| FR-CHANGE-09 | P0 | 草稿检查 | 草稿发布前展示来源检查结果；无来源事实、版本混淆和无法确认的映射必须被阻断或标记为待核实 |
| FR-CHANGE-10 | P0 | 人工整理方向 | 管理员可在证据不足、检查阻断或一轮完成后向任务会话追加方向，由新运行基于当前修订增量修改，或直接编辑形成新修订 |

MVP 可以基于 diff/patch 生成草稿，但必须把实现结论限定为该 PR 材料所描述的变更，不得宣称其代表用户当前本地代码。需要确认现行实现时，用户必须核对本地代码。

### 7.4 代码快照管理

代码快照上传、版本维护、全文索引和片段读取不属于当前 MVP。已有后端代码模块可以保留作为实验性架子，但必须满足：

- 不注册到 Web 问答 Agent 或 MCP 工具；
- 不在当前前端提供上传、重建索引或快照维护入口；
- 不要求用户维护项目历史版本的完整代码副本；
- 不作为知识检索、问答引用或知识整理的事实来源；
- 不因缺少活动代码快照影响文档检索和问答。

| FR-QA-08 | P0 | 知识缺口反馈 | 用户可记录问题和缺口类型，不建设完整工单流程 |
| FR-QA-09 | P0 | 可折叠处理过程 | 当前运行按 SSE 展示协调阶段、模型/Tool 调用、搜索摘要、命中文档标题、来源数量、引用校验和最终结果；过长名称截断并可查看完整值 |
| FR-QA-10 | P0 | 多轮项目会话 | 用户可在同一项目会话中连续追问；每一轮创建独立 Agent 运行并只携带该会话内有界的用户问题与经校验最终回答 |
| FR-QA-11 | P0 | 会话历史 | 最近记录按会话而非孤立问题组织，用户可恢复同一项目中的历史问题、最终回答、引用和时间 |
| FR-QA-12 | P0 | 多轮最小恢复边界 | 当前阶段不恢复中断中的模型/Tool 过程；服务重启后活动轮次明确失败，已完成轮次的问题和回答仍可查看并可继续新一轮 |

“处理过程”是由真实 Agent、Tool、证据和服务端校验事件组成的可公开执行轨迹。模型提供的计划或决策摘要可以作为带明确标签的补充信息，但不能替代真实 Tool 调用，也不能把未执行步骤显示为已完成。页面不展示完整系统提示、完整证据正文或模型原始思维链。

多轮上下文只允许来自当前操作者、当前项目和同一会话中已经完成的用户/助手消息；失败轮次的中间文本、工具返回正文、其他会话及其他项目内容不得进入后续模型输入。服务端必须限制带入轮数或总字符数，超限时采用明确裁剪，不在当前阶段建设自动会话摘要或长期记忆。

### 7.7 事实边界

- Web 问答只以当前范围内已发布的知识文档为项目事实证据；
- PR、diff/patch 和测试材料只用于生成待审核知识草稿，不直接进入问答检索；
- 已发布文档之间存在无法解释的冲突时必须拒答并展示冲突来源；
- 系统不保证知识文档与用户当前代码完全一致，涉及现行实现时必须提示用户核对本地最新代码；
- Claude Code 通过 MCP 获取知识后，必须以用户本地最新代码作为实现事实。

### 7.8 MCP 服务

MCP 是 MVP 正式入口，使用远程 Streamable HTTP，以 Claude Code 完成验收。

#### 7.8.1 `knowledge_search`

用途：检索当前项目和通用业务知识。

建议输入：

```json
{
  "project": "network-designer",
  "query": "场景包导入后为什么需要刷新拓扑？",
  "top_k": 5
}
```

#### 7.8.2 `document_read`

用途：读取指定知识文档的完整内容或分页内容。

#### 7.8.3 MCP 返回要求

每条结果尽量包含：

- 项目标识，或标明属于通用业务知识；
- 文档标题；
- 命中片段；
- 原 Wiki URL 或上传文件名；
- 可选的 PR、commit 或文件路径来源元数据；
- 索引或更新时间；
- 相关性分数；
- 内容是否被截断。

MCP 不调用 DeepSeek 生成最终答案，只返回原始上下文和引用，由 Claude Code 自行综合。

### 7.9 最小 Web 页面

MVP 只建设以下页面：

1. **登录页**；
2. **项目列表页**，包含“通用业务知识”入口；
3. **项目详情页**，包含文档目录、变更知识单元、需求和 PR 材料导入、对话式知识任务、Agent 运行过程、草稿修订与 Diff 审批和整理报告；
4. **问答页**，包含多轮项目会话、可折叠处理过程、流式回答、来源展示、历史会话和知识缺口反馈。

不建设仪表盘、个人中心、组织管理和复杂统计页面。

## 8. 可信回答要求

### 8.1 必须拒答的情况

- 没有检索到相关的已发布业务知识；
- 只有低相关内容，无法支持结论；
- 用户要求确认当前代码实现，但已发布文档没有足够依据；
- 问题超出当前项目和通用业务知识范围；
- 来源之间存在无法解释的冲突。

### 8.2 拒答内容

拒答时应：

- 明确说明“当前知识库没有足够依据”；
- 展示少量可能相关的来源；
- 涉及实现时提示用户核对本地最新代码；
- 允许用户创建知识缺口反馈；
- 不允许模型用通用知识补写项目事实。

### 8.3 内容安全

导入的 Wiki、人工文档、需求材料、PR 描述、diff 和源代码均视为不可信数据。其中包含的指令不能改变系统行为，也不能触发命令、网络访问或数据修改。

## 9. 数据来源

| 来源 | MVP 接入方式 | 后续方向 |
|---|---|---|
| 人工整理文档 | Web 新建、编辑或上传 Markdown/文本 | 多人协作、审核、版本 |
| 公司原 Wiki | 系统外转为 Markdown 后一次性导入 | 专用连接器和增量同步 |
| 需求与 PR | 手动录入元数据，上传 Markdown、diff/patch 和变更文件列表 | 对接公司 Git 平台并按合并事件触发知识草稿 |
| 本地代码 | 不直接导入；仅在 PR 材料中接收有限 diff/patch 和文件列表 | 根据实际收益评估 Git 平台连接或代码检索 |
| 通用业务知识 | 管理员新建或批量导入 | 负责人、复审和适用范围治理 |
| 模型生成内容 | DeepSeek `deepseek-v4-flash` 通过版本化 Tool 增量更新待审核 Markdown 草稿，并以 Diff 审批 | 多人协同评论、逐 hunk 合并和复杂分支修订 |
| Welink 群聊/会议 | 不接入，仅预留来源类型 | 人工选择内容、脱敏、摘要和审核后入库 |

## 10. 非功能需求

### 10.1 部署与模型

- 系统部署在公司内部环境；
- 后端采用团队可维护的 Java 技术栈；
- 支持 Docker Compose 启动；
- Embedding 和向量检索可在 CPU 环境运行；
- Web 答案生成调用 DeepSeek `deepseek-v4-flash` OpenAI 兼容接口；
- 模型接口与业务逻辑解耦，接口不可用时文档浏览和搜索仍可使用。
- Agent Runtime、Skill 定义和底层模型接口解耦，替换模型不应改变知识与权限边界。
- 协调 Agent 只通过 Spring AI Alibaba `TaskTool`/`AgentTool` 从本地文件预定义的子 Agent 与服务端 ToolCallback 候选集合中动态选择；增加或修改编排策略优先修改 Skill/Agent Spec，不在 Java 中复制业务流程；
- 运行、公开事件和最终产物元数据持久化到 PostgreSQL，大型 Markdown 产物通过 ObjectStorage 保存；

### 10.2 性能目标

- 普通知识搜索目标响应时间不超过 3 秒；
- MCP 检索目标响应时间不超过 3 秒；
- Web 问答支持流式输出，生成耗时以 DeepSeek `deepseek-v4-flash` 接口实测为准；
- 单次 MCP 和文档读取返回设置长度上限；
- 单个索引任务失败不得破坏现有可查询索引。
- Agent 单次运行必须设置最大步骤数、超时和上下文长度，超限后安全终止并保留错误记录。
- 多 Agent 共享运行级步骤、模型调用、并发、Token 和超时上限；证据不足时保存未确认项并进入人工处理，不允许无限循环；
- 前端以服务端运行快照为事实来源，SSE 中断或页面刷新后可重新获取当前状态；

### 10.3 安全底线

- Web 和 MCP 均不能匿名访问；
- 管理写操作和普通查询操作分离；
- MCP 只读；
- 知识 Agent 按 Skill 只能使用服务端通过 `ToolCallback`/`ToolCallbackResolver` 为当前运行提供的工具，不能执行 Shell、任意 HTTP 请求或数据库管理操作；
- 项目记忆、Skill、人工反馈和导入材料中的文本不能扩大 Agent 工具、项目范围、文件系统、网络或发布权限；
- Agent 产生的内容只能写入草稿、整理报告或知识缺口，发布操作必须由管理员执行；
- 本地 Skill/Agent Spec 和下载内容不能获得服务端未注册工具、执行携带脚本或扩大项目范围；
- Token 和模型密钥不得写入知识文档、PR 材料或日志；
- 默认排除 `.env`、私钥、证书和明显密钥文件；
- 记录导入、重建索引和问答错误，不记录完整密钥和不必要的完整代码内容。

### 10.4 可恢复性

- 原始上传文件与索引状态分离；
- 索引可以删除后重新构建；
- 重新索引失败时继续使用上一个成功索引；
- 项目和知识数据应支持备份。
- Agent 运行、事件和最终产物引用应支持备份；
- 短时 QA 在后端异常退出后明确失败，由用户创建新运行，不恢复模型流和 Tool 调用内部状态；
- 知识挖掘、冲突整理和等待人工的长任务使用 PostgreSQL Checkpoint，重启后从最近已提交节点继续；
- 恢复不得重复已经提交的草稿、报告、冲突候选、人工决定或其他业务副作用，也不得留下已发布一半的知识；

## 11. MVP 验收

### 11.1 数据验收

- 成功创建两个项目；
- 成功导入场景包文档和一批由原 Wiki 转换的 Markdown；
- 成功导入一组需求、PR、diff/patch 和测试说明材料；
- 成功创建至少一篇通用业务知识。

### 11.2 检索验收

开发前准备 15～20 个真实问题，并为每个问题标注应命中的已发布知识文档：

- 约 10 个场景包导入导出问题；
- 约 5 个项目启动、架构或通用业务问题；
- 至少 3 个系统不应回答的问题；
- 至少 2 个使用口语或相似表达的问题。

建议验收目标：

- 至少 80% 的有答案问题在 Top-5 结果中出现正确来源；
- 所有包含项目事实的 Web 答案均展示至少一个来源；
- 无依据问题不编造答案；
- 当前项目查询不返回其他项目文档；
- 询问文档未覆盖的当前代码实现时能够明确拒答并提示核对本地代码。

### 11.3 知识生成与整理验收

- 管理员能够基于需求、PR、diff/patch 和测试说明生成一篇 Markdown 业务知识草稿；
- 草稿展示需求与 PR 来源、可选 commit、生成时间和无法确认的事项；
- 草稿发布前不会出现在普通用户检索和 Web 问答中；
- 管理员编辑并发布后，重新索引即可检索到该文档；
- 手动知识整理能够输出至少一种过期、重复、冲突或知识缺口提示；
- 手动和定时知识整理都创建可查看的任务会话，系统触发、Agent/Tool 过程、用户指导和草稿修订按时间连续展示；
- Agent 对草稿的每次修改都通过版本化 `draft_update` 形成新修订和 Diff，最终对话文本不能绕过 Tool 覆盖草稿；
- 管理员可以在安全步骤边界暂停知识任务、加入指导后继续，也可以在一轮完成后追加意见开启新的调整运行；
- 管理员审核明确基线到所选草稿修订的 Diff 后发布，旧修订和来源关系仍可追溯；
- 每周任务只生成报告或草稿，不自动修改已发布知识，失败不得影响已发布知识和检索。

### 11.4 Agent 与 Skill 验收

- Web 问答运行记录显示使用了 `project_qa` Skill、内容摘要和实际 Agent/Tool 轨迹；
- 需求实现整理运行记录显示使用了 `change_documenter` Skill；
- 知识库整理运行记录显示使用了 `knowledge_curator` Skill；
- Skill 和 Agent Spec 可以从受控本地目录加载，修改文件后下一次新运行生效且不需要重新编译；
- 下载的定义无法调用服务端 ToolCallback 候选集合之外的工具或执行携带脚本；
- 协调 Agent 可以按 Skill 自主选择预定义检索、证据审查、冲突分析和整理 Agent，不由 Java 固定调用顺序；
- Agent 达到最大步骤数或超时后能够安全停止，不产生半发布状态；
- Agent 只能保存草稿、报告和知识缺口，不能直接发布文档；
- `project_qa` 无法调用代码搜索或代码片段读取工具；
- 知识挖掘与冲突整理的主要结论能追溯到平台 Tool 返回的来源，子 Agent 不能自行增加角色或权限；
- 管理员可补充本次整理方向、修改草稿、发布或取消；
- IDEA 停止并重新启动后端后，短时 QA 明确失败并可重新发起；知识挖掘或冲突整理长任务从 PostgreSQL 最近 Checkpoint 的下一节点继续；
- 恢复长任务不会重复已提交的草稿、报告、冲突候选或人工决定；正在进行的模型/Tool 调用允许按节点重新执行但必须受幂等和运行上限保护；
- 暂停请求在当前模型/Tool 步骤结束并提交 Checkpoint 后进入等待，用户指导不会被注入正在执行的调用；
- 一轮知识整理完成后，管理员可以在同一任务会话追加指令，新运行从当前草稿修订继续并形成新的修订与 Diff；
- `draft_update` 使用基础修订号和幂等键；并发或恢复导致的旧修订写入被拒绝，不得覆盖管理员或另一运行已经提交的修改；
- 运行详情展示可公开决策摘要、Agent/Tool/来源和校验事实，不展示完整系统提示、证据正文或模型原始思维链。

### 11.4.1 Web 问答过程与多轮验收

- 当前单 Agent 问答可折叠展示模型阶段、实际 Tool 调用、查询摘要、命中文档标题与数量、引用校验和最终结果；
- 处理过程和最终回答通过 SSE 增量更新，终态仍以服务端详情快照校正；
- 用户可以创建新会话、在当前会话连续追问并查看按会话组织的历史问题与最终回答；
- 后续轮次只使用同一项目、同一操作者、同一会话内的有界已完成消息，不使用失败中间文本或其他会话内容；
- 后端在活动轮次中断后可以明确失败，不要求恢复其详细过程；既有已完成问答仍可查看并继续新一轮。

### 11.5 需求到实现沉淀验收

- 使用“场景包导入导出”真实需求文档、对应 PR 信息和 diff 创建一个变更知识单元；
- Agent 通过版本化草稿 Tool 增量生成包含需求条目、变更文件、实现摘要、测试证据和未确认项的知识草稿；
- 运行过程展示材料读取、知识提取、草稿生成、结构检查及人工决定；
- 每个主要实现结论能够追溯到需求材料、PR、commit 或文件路径；
- 对无法从材料确认的实现关系明确标记，不生成虚假映射；
- 管理员审核发布后，该文档可被 Web 和 MCP 检索到；
- 产物明确说明其实现结论仅对应导入的 PR 材料，不代表用户当前本地代码。

### 11.6 MCP 验收

- Claude Code 可使用共享 Token 连接 MCP；
- 可以调用知识搜索和文档读取两个只读工具；
- 同一业务问题能够返回与 Web 使用的同源知识；
- 结果包含项目、来源、文件路径、commit 和更新时间；
- Claude Code 可以结合本地代码完成一次相似需求的文件定位；
- MCP 不调用 DeepSeek 生成最终答案。

### 11.7 权限验收

- 只读账号不能新增、上传、编辑或重新索引；
- 管理员能够完成所有内容维护操作；
- 无效 MCP Token 无法检索内部内容。

## 12. 20 天交付边界

建议按以下顺序交付，后续功能不得阻塞前面的核心链路：

1. 项目和文档数据准备；
2. 管理员导入与编辑、普通用户浏览；
3. 业务文档关键词与向量检索；
4. `project_qa` 的可折叠处理过程、真实 Tool/来源事件、流式结果与多轮项目会话；
5. 接入 Spring AI Alibaba 的本地 Skill/Agent Spec、Task/Agent Tool、Hook、Human-in-the-Loop 和持久化 Graph Checkpoint，不重复建设对应运行时基础；
6. 使用 Spring AI ToolCallback 机制把知识搜索、文档读取、任务会话、草稿读取/增量更新、修订 Diff 和报告保存等 LoreDock 平台能力工具化；
7. `knowledge_curator` 通过预定义子 Agent 完成可暂停、可继续调整的对话式知识挖掘、冲突整理和待审核修订；
8. 需求文档、PR、diff/patch 和测试材料导入；
9. `change_documenter` 复用同一多 Agent/Tool 基础生成业务知识草稿并由管理员审核发布；
10. Claude Code MCP 的知识搜索和文档读取工具；
11. 每周知识整理任务触发同一 `knowledge_curator` Skill；
12. Docker Compose、测试、文档和现场演示脚本。
