# 项目业务上下文知识库 MVP 需求文档

| 属性 | 内容 |
|---|---|
| 文档版本 | v1.1 |
| 文档日期 | 2026-08-01 |
| 文档状态 | 需求基线稿 |
| 建设周期 | 20 天 |
| 部署范围 | 公司内部环境 |

| 核心客户端 | Web、Claude Code MCP |

## 1. 产品定义

本产品是面向组内开发人员的“项目业务上下文知识库”。

它将人工项目文档、公司原 Wiki 内容、需求材料和 PR 实现信息整理为可持续维护的业务知识，为开发人员提供可检索、可引用的 Web 问答，同时通过 MCP 向本地 Claude Code 提供业务上下文。

本产品不试图替代本地代码阅读或自动理解整个代码库：

- 云端知识库负责回答“业务是什么、为什么这样设计、有哪些约束和历史经验”；
- Web 问答只使用管理员发布的知识文档作为项目事实证据，不承诺回答当前代码实现；
- 本地 Claude Code 以用户本地代码为当前事实，知识库仅补充代码中缺失的业务上下文。

## 2. 背景与问题

组内存在近百个代码仓库，每个仓库通常有 20～30 万行代码。很多项目维护超过五年，但缺少系统文档，业务逻辑、设计原因、兼容规则和历史坑主要依赖口头传递。

公司已有 Wiki，但检索体验较差，开发人员难以通过自然语言快速找到相关内容。即使文档存在，也常因标题、目录、用词或页面结构不同而难以检索。

本次试点选择一个 Java + Vue 3 的本地网络设计工具。该项目约 20 万行代码、业务复杂、几乎没有规范文档。当前已有一份“场景包导入导出”链路文档，内容包括：

- 入口与调用链；
- 场景包格式；
- 导入导出业务规则；
- 兼容性要求；
- 容易遗漏的步骤；
- 历史设计原因；
- 测试和验证方法。

这份文档将作为 MVP 的核心知识样本和演示场景。

## 3. 建设目标

### 3.1 最高优先级目标

在 20 天结束时完成以下现场演示：

1. 在公司内部环境启动系统；
2. 导入场景包文档和部分原公司 Wiki 内容；
3. 导入一次真实需求文档及其 PR、diff 和测试材料，由 `change_documenter` 生成业务知识草稿；
4. 管理员核对需求、实现材料和测试证据后发布文档；
5. 由 `knowledge_curator` 检查已有知识的重复、冲突、过期和缺口，生成待审核的整理报告或草稿；
6. 在 Web 中提出真实业务问题，只基于已发布文档得到带来源的回答；
7. 在 Claude Code 中通过 MCP 查询同一问题，获取原始业务知识和引用；
8. Claude Code 结合本地最新代码，辅助定位一次类似需求涉及的文件和修改范围；
9. 对文档缺少依据的问题明确拒答，并记录知识缺口。

### 3.2 产品目标

- 统一管理项目知识和通用业务知识；
- 改善原 Wiki 内容的检索体验；
- 将业务知识从口头传播转为可持续维护的内容；
- 将需求及其 PR 实现过程沉淀为可追溯知识，使存量项目随每次真实变更逐步补齐文档；
- 让 Web 用户和本地 Agent 使用同一份知识和引用；
- 为未来接入更多项目、Git 平台和 Welink 内容保留扩展空间。

### 3.3 非目标

MVP 不追求：

- 自动生成完整项目 Wiki；
- 构建 IDE 级代码理解系统；
- 一次性接入近百个仓库；
- 证明长期用户活跃度；
- 替代公司原 Wiki；
- 替代 Git、代码评审或本地 Agent。

### 3.4 当前阶段范围（快速迭代期）

项目当前处于核心流程快速迭代阶段，唯一开发主线是：**把需求文档、PR 实现材料和已有文档整理为可审核、可发布、可检索的业务知识，再用文档问答验证知识是否真正可用**。以下四类范围是对全文需求在当前阶段的取舍，后续文档、OpenSpec 和实现必须与之一致。

#### 必须实现（直接服务“可回答”主链路）

- 项目与分支管理：创建、启停、范围解析和默认 `main` 分支；
- 知识文档全生命周期：导入/编辑、发布/归档、项目/分支/通用范围隔离；
- 知识索引与混合检索：分块、离线 Embedding、关键词与向量候选、RRF、范围复核；
- 需求与 PR 知识提取：导入需求、PR 元数据、diff/patch 和测试说明，生成可追溯的待审核业务知识草稿；
- 知识库整理：检查重复、冲突、过期和知识缺口，生成待审核的整理报告或草稿；
- Web 项目问答：创建、历史、详情、SSE 续读、仅带文档引用的回答、无文档证据拒答；
- 知识缺口反馈：幂等记录、问答关联、管理员状态流转；
- 认证与会话：固定 ADMIN/MEMBER 账户、Sa-Token 会话；
- 支撑能力：本地对象存储、通用后台任务、系统状态与健康检查。

#### 允许简化

- 认证：固定配置账户，不提供注册、找回密码和细粒度权限；
- Agent 流程：`change_documenter` 和 `knowledge_curator` 内部采用少量固定步骤，不拆分动态多 Agent 编排平台；
- 运行监控：只持久化粗粒度运行事件和证据，不保存逐分片/逐工具调用明细；
- 导入结果：批次统计与条目结果合并为有界 JSON 字段，不单独建表；
- 问答终态说明：失败/终止由服务端稳定错误码映射脱敏 `failureMessage`，不暴露模型原文。

#### 明确延后

- MCP 工具与身份校验：当前阶段不做 MCP 摘要、身份校验和模型生成；
- 代码快照上传、版本维护、全文索引、代码片段读取及其管理页面；已有代码模块保留但不接入当前 MVP 页面、问答和 MCP；
- 多 Agent 动态编排、独立角色管理和可视化 Graph 平台；
- 知识、代码或 Agent 定义的历史版本、发布、回滚和恢复体系；
- 生产级审计、完整可观测平台、多级恢复和穷举容错；
- 移动端与窄屏专项布局。

#### 明确不做

- 按微服务、DDD、六边形或多 Maven 子模块重建项目；
- 替代本地代码阅读或自动理解整个代码库；
- 自研 Agent 运行时、安全协议、加密算法或通用基础框架；
- 当前阶段新增与“可回答”主链路无关的新 HTTP 功能或前端页面；
- 在 Web 问答中使用代码快照、PR diff 或模型常识作为项目事实证据；
- 为覆盖率或测试数量给无业务逻辑小类补测试。

## 4. 用户与权限

### 4.1 管理员

管理员负责：

- 创建和维护项目；
- 创建分支信息；
- 上传、新建和编辑知识文档；
- 导入需求、PR、diff/patch 和测试说明并生成知识草稿；
- 触发知识整理并审核整理建议；
- 设置知识所属范围；
- 触发或重建索引；
- 查看知识缺口反馈。

MVP 只需要一个管理员账号。

### 4.2 组内成员

组内成员可以：

- 浏览项目和知识目录；
- 搜索已发布知识；
- 使用 Web 问答；
- 查看回答引用；
- 提交“没有回答、回答错误或知识已过期”反馈。

MVP 使用一个组内共享只读账号，不提供注册、个人资料和细粒度权限。

### 4.3 Claude Code

Claude Code 通过共享 MCP Token 使用只读工具，可以：

- 检索当前项目和通用业务知识；
- 读取指定知识文档；

MCP 不允许修改知识、修改代码、执行命令或访问其他内部系统。

## 5. 知识范围模型

### 5.1 通用业务知识

适用于多个项目的业务概念、术语、流程、规范和约束。

示例：

- 网络场景、设备、拓扑等通用术语；
- 公司级文件格式规范；
- 通用兼容策略；
- 通用测试和发布要求。

### 5.2 项目级知识

适用于一个项目的所有分支。

示例：

- 项目用途和模块划分；
- 总体架构；
- 业务流程和历史原因；
- 开发、调试和测试方法；
- 与其他系统的关系。

### 5.3 分支级知识

仅适用于指定分支的临时设计、功能变化或实现说明。

### 5.4 PR 实现材料

PR 实现材料用于生成知识草稿，不作为 Web 问答或 MCP 的直接检索证据。材料至少关联项目、目标分支、PR 标识和可选的 base/head commit，可包含 diff/patch、变更文件列表、测试说明及人工补充内容。

MVP 不保存和维护仓库的每个代码版本。commit 仅作为来源元数据，系统不承诺 PR 材料与用户当前本地代码一致；需要确认当前实现时，开发人员必须核对本地最新代码。

## 6. 查询范围规则

### 6.1 项目查询

用户发起项目查询时必须选择项目，分支默认使用 `main`。

默认检索范围为：

```text
通用业务知识
+ 当前项目的项目级知识
+ 当前项目、当前分支的分支级知识
```

不得召回其他项目或其他分支的内容。

### 6.2 全局查询

只有用户明确进入“通用业务知识”或选择“全局搜索”时，才检索通用业务知识。MVP 不提供默认跨项目召回。

### 6.3 分支知识不存在

如果请求分支没有已发布的分支级知识，仍可返回通用业务知识和当前项目的项目级知识，但不得使用其他分支文档或模型常识冒充当前分支事实。

### 7.1 登录

| 编号 | 优先级 | 需求 | 验收标准 |

| FR-AUTH-01 | P0 | 管理员登录 | 正确账号可进入管理功能，错误密码被拒绝 |

| FR-AUTH-03 | P0 | MCP Token | 无 Token 或错误 Token 的 MCP 请求被拒绝 |

### 7.2 项目与分支管理

| 编号 | 优先级 | 需求 | 验收标准 |

| FR-PROJ-01 | P0 | 创建项目 | 可填写项目名称、标识、简介和主要技术栈 |

| FR-PROJ-04 | P1 | 项目停用 | 管理员可停止项目出现在普通查询入口 |

MVP 完整验收两个项目：网络设计工具项目和一个小型对照项目。网络设计工具项目验收两个分支：`main` 和场景包演示分支。

| 编号 | 优先级 | 需求 | 验收标准 |

| FR-DOC-02 | P0 | 编辑知识 | 管理员可修改标题、正文、标签、来源和适用范围 |
| FR-DOC-03 | P0 | 上传文档 | 支持 Markdown、纯文本和包含 Markdown 的 ZIP |
| FR-DOC-04 | P0 | 知识范围 | 文档可设置为通用、项目级或分支级 |

| FR-DOC-06 | P0 | 文档浏览 | 普通成员可按项目和目录浏览文档 |

MVP 不直接解析网页、Word、PDF 和附件。原 Wiki 内容需在系统外转换成 Markdown 或纯文本后导入。

#### 7.3.1 知识生成与定期整理

系统使用 DeepSeek `deepseek-v4-flash` 的 OpenAI 兼容接口辅助生成和整理知识。当前 MVP 以两个知识生产 Agent 为核心：`change_documenter` 从需求和 PR 实现材料中提取业务知识，`knowledge_curator` 整理已有知识库文档。模型输出只能保存为草稿、报告或知识缺口，不得自动进入正式知识索引。

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-KG-01 | P0 | 生成知识草稿 | 管理员导入需求、PR 元数据、diff/patch 和测试说明后获得结构化 Markdown 业务知识草稿 |
| FR-KG-02 | P0 | 生成依据 | 草稿记录使用的需求材料、PR、diff/patch、测试说明、分支、可选 commit、生成时间和模型信息 |
| FR-KG-03 | P0 | 不确定项 | 生成结果单独列出无法确认、来源冲突和需要人工补充的事项 |
| FR-KG-04 | P0 | 审核发布 | 管理员可编辑草稿，确认后发布并触发知识索引更新 |
| FR-KG-05 | P0 | 禁止自动发布 | 模型生成或整理得到的内容不能绕过管理员审核成为正式知识 |
| FR-KG-06 | P0 | 手动知识整理 | 管理员可触发检查，生成过期、重复、冲突和知识缺口报告 |
| FR-KG-07 | P1 | 定期整理任务 | 系统可按周运行知识整理并保存报告，不自动修改正式文档 |
| FR-KG-08 | P0 | 修订建议 | 整理报告可生成合并、拆分、补充、归档或更新建议，并可转为待审核草稿 |

MVP 的知识整理只覆盖以下四类问题：

- 多篇文档内容疑似重复；
- 已发布文档之间的规则或适用范围疑似冲突；
- 文档来源、更新时间或人工反馈表明内容可能过期；
- 问答记录中反复出现没有可靠答案的知识缺口。

整理结果只生成报告、建议或待审核草稿，不直接合并、归档或覆盖正式文档。定期任务失败不得影响已发布知识的正常检索。

#### 7.3.2 知识 Agent 与 Skill

Web 问答、知识生成和知识整理复用同一套受控模型适配、工具权限、项目范围、运行记录和错误语义。Web 项目问答只检索已发布文档；知识生产只保留 `change_documenter` 和 `knowledge_curator` 两个面向用户的 Agent，不建设动态 Agent 创建、角色市场、跨服务 Agent 或可视化 Graph 编排器。

`change_documenter` 的固定流程为：

```text
准备输入
→ 读取需求、PR、diff/patch 和测试材料
→ 提取业务目标、规则、实现影响、验证证据和未确认项
→ 生成带来源的结构化知识草稿
→ 执行一次结构与引用检查
→ 待审核草稿
```

`knowledge_curator` 读取当前范围的已发布文档、知识缺口和人工反馈，输出整理报告以及可选的待审核修订草稿。两个 Agent 都不得读取完整仓库或主动访问外部 Git 平台；前端和运行接口不展示原始思维链，只展示阶段、来源摘要、结构化产物、检查问题、Token、耗时和错误。

Skill 是可版本化的任务说明，至少定义：

- Skill 名称、版本和适用场景；
- 必要输入和允许使用的工具；
- 推荐执行步骤和最大执行步数；
- 输出结构、引用要求和拒答条件；
- 哪些结果只能保存为草稿或报告；
- 示例输入、示例输出和验收样例。

MVP 规划以下 Agent Skill：

| Skill | 优先级 | 用途 | 允许结果 |
|---|---|---|---|
| `project_qa` | P0 | 围绕所选项目和分支检索已发布文档并生成带引用回答 | Web 回答或拒答 |
| `change_documenter` | P0 | 整理需求文档、PR 变更和测试证据，建立需求到实现的映射 | 变更知识草稿 |
| `knowledge_curator` | P0 | 检查过期、重复、冲突和知识缺口，并提出整理方案 | 整理报告、待审核草稿或建议 |

知识 Agent 的内部工具限定为：

- 搜索知识并读取完整文档；
- 查询知识缺口、人工反馈和文档元数据；
- 读取需求材料、PR 元数据、变更文件列表、diff 和测试证据；
- 保存草稿、引用关系和整理报告；
- 记录运行轨迹、失败原因和 Token 用量。

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-AGENT-01 | P0 | 统一 Agent Runtime | Web 问答和文档生成均通过同一套模型、工具调用和运行记录机制执行 |
| FR-AGENT-02 | P0 | Skill 注册 | 系统可加载启用的 Skill，并记录名称和版本 |
| FR-AGENT-03 | P0 | Skill 选择 | Web 问答自动使用 `project_qa`；需求与 PR 整理使用 `change_documenter`；知识库整理使用 `knowledge_curator` |
| FR-AGENT-04 | P0 | 工具白名单 | 每个 Skill 只能调用其声明的内部工具，不允许任意执行命令或访问网络 |
| FR-AGENT-05 | P0 | 运行限制 | 每次运行设置最大步骤数、超时时间、检索条数和上下文长度 |
| FR-AGENT-06 | P0 | 可追溯运行 | 保存 Skill 版本、模型、工具调用摘要、输入来源、最终引用和运行状态 |
| FR-AGENT-07 | P0 | 写入隔离 | Agent 只能创建草稿、报告和知识缺口，不能直接修改或发布正式知识 |
| FR-AGENT-08 | P0 | 知识整理 Skill | 手动任务能够调用 `knowledge_curator`，并将报告或修订建议保存为待审核产物 |
| FR-AGENT-09 | P1 | 定期整理 | 定期任务可以调用 `knowledge_curator`，失败不影响正式知识检索 |
| FR-AGENT-10 | P0 | 固定知识生产流程 | 两个知识生产 Agent 均使用应用定义的少量固定步骤，模型不得动态增加角色或改写主流程 |
| FR-AGENT-11 | P0 | 人在回路 | 证据不足或检查阻断时保存未确认项，管理员可补充方向、修改草稿、发布或取消 |
| FR-AGENT-12 | P0 | 运行过程展示 | Web 展示阶段、来源摘要、产物、检查问题、错误和人工决定，不展示模型原始思维链 |

Skill 以 classpath 中的 Markdown 文件维护。MVP 不建设数据库 Skill 版本、项目记忆版本、动态 Agent 配置或复杂检查点恢复体系。系统安全提示、工具白名单、项目范围、运行限制和发布权限由后端结构化配置强制执行，不允许被 Skill、人工反馈或导入材料覆盖。

内部 Agent 工具与对外 MCP 工具可以复用同一查询服务，但二者的授权边界必须分开。

#### 7.3.3 需求到代码实现的知识沉淀

系统把一次需求及其实现材料组织为一个“变更知识单元”。它不是 PR 管理工具，而是把散落在需求文档、代码改动和测试记录中的信息整理成可长期检索的项目知识。

一个变更知识单元至少关联：

- 项目和目标分支；
- 需求标题、需求正文或上传文件；
- PR 标题、编号或原始 URL；
- base commit、head commit；
- 变更文件列表和 diff/patch；
- 可选的 PR 描述、评审结论、测试说明和人工补充材料；
- Agent 生成的草稿、引用关系和管理员审核状态。

MVP 不依赖具体 Git 平台 API。管理员可以手动填写 PR 元数据并上传 diff/patch、变更文件列表或整理后的 Markdown。后续再接入公司实际使用的 Git 平台，自动拉取 PR 内容。

`change_documenter` 使用上传材料完成提取、编写和检查，生成的文档至少包含：

1. 需求背景、目标和明确的非目标；
2. 需求条目到代码文件或模块的对应关系；
3. 关键调用链和数据流；
4. 新增或修改的业务规则、接口、数据结构和配置；
5. 兼容性、异常处理和容易遗漏的步骤；
6. 测试与验证证据；
7. 实际实现与原需求之间的偏差；
8. 尚未确认的问题和后续建议；
9. PR、分支、commit、文件路径和原始材料引用。

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-CHANGE-01 | P0 | 创建变更知识单元 | 管理员可选择项目和分支，上传需求材料并填写 PR 基本信息 |
| FR-CHANGE-02 | P0 | 导入实现材料 | 支持上传 diff/patch、变更文件列表和 Markdown 格式的测试说明 |
| FR-CHANGE-03 | P0 | 需求实现映射 | Agent 输出需求条目与相关模块、文件路径和变更摘要的映射 |
| FR-CHANGE-04 | P0 | 材料边界 | Agent 只使用本次上传的需求、PR、diff/patch、变更文件列表、测试说明和人工补充材料，不依赖完整代码快照 |
| FR-CHANGE-05 | P0 | 偏差与缺口 | 无法确认的映射、未实现需求和实现偏差必须单独列出，不得猜测补全 |
| FR-CHANGE-06 | P0 | 草稿审核发布 | 产物首先进入草稿状态，管理员核对后才能发布并参与检索 |
| FR-CHANGE-07 | P0 | 双向追溯 | 发布文档可以查看对应需求、PR、commit 和文件路径；变更知识单元也可查看产出的文档 |
| FR-CHANGE-08 | P1 | 批量沉淀历史变更 | 可连续导入多个历史需求和 PR，但不要求一次批量处理全部历史记录 |
| FR-CHANGE-09 | P0 | 草稿检查 | 草稿发布前展示来源检查结果；无来源事实、版本混淆和无法确认的映射必须被阻断或标记为待核实 |
| FR-CHANGE-10 | P0 | 人工整理方向 | 管理员可在证据不足或检查阻断时补充本次整理方向并重新生成或直接编辑草稿 |

MVP 可以基于 diff/patch 生成草稿，但必须把实现结论限定为该 PR 材料所描述的变更，不得宣称其代表用户当前本地代码。需要确认现行实现时，用户必须核对本地代码。

### 7.4 代码快照管理

代码快照上传、版本维护、全文索引和片段读取不属于当前 MVP。已有后端代码模块可以保留作为实验性架子，但必须满足：

- 不注册到 Web 问答 Agent 或 MCP 工具；
- 不在当前前端提供上传、重建索引或快照维护入口；
- 不要求用户维护各分支和历史版本的完整代码副本；
- 不作为知识检索、问答引用或知识整理的事实来源；
- 不因缺少活动代码快照影响文档检索和问答。

### 7.5 搜索

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-SRCH-01 | P0 | 知识关键词检索 | 支持对标题、正文和标签进行关键词查询 |
| FR-SRCH-02 | P0 | 知识语义检索 | 支持中文自然语言查询和相似表达召回 |
| FR-SRCH-04 | P0 | 范围隔离 | 查询不混入其他项目或分支结果 |
| FR-SRCH-05 | P0 | 来源展示 | 每条结果展示所属范围、标题、片段和来源 |
| FR-SRCH-06 | P1 | 条件过滤 | 支持按标签、知识类型和来源类型过滤 |

业务知识使用关键词与向量语义检索。当前 MVP 不提供代码检索入口。

### 7.6 Web 问答

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-QA-01 | P0 | 项目问答 | 用户选择项目和分支后可提出自然语言问题 |
| FR-QA-02 | P0 | Agent 检索增强生成 | DeepSeek `deepseek-v4-flash` 使用 `project_qa` Skill，通过受限工具检索和补充读取后生成回答 |
| FR-QA-03 | P0 | 引用 | 项目事实回答至少包含一个可查看的已发布知识文档来源 |
| FR-QA-04 | P0 | 文档边界提示 | 回答明确基于已发布文档，不保证与用户当前本地代码实现一致 |
| FR-QA-05 | P0 | 流式响应 | 支持逐步展示回答；模型暂时不可用时显示明确错误 |
| FR-QA-06 | P0 | 无依据拒答 | 证据不足时明确说明无法回答，不使用通用模型知识猜测项目事实 |
| FR-QA-07 | P0 | 文档冲突提示 | 已发布文档之间存在无法解释的冲突时拒答并展示冲突来源 |
| FR-QA-08 | P0 | 知识缺口反馈 | 用户可记录问题和缺口类型，不建设完整工单流程 |

### 7.7 事实边界

- Web 问答只以当前范围内已发布的知识文档为项目事实证据；
- PR、diff/patch 和测试材料只用于生成待审核知识草稿，不直接进入问答检索；
- 已发布文档之间存在无法解释的冲突时必须拒答并展示冲突来源；
- 系统不保证知识文档与用户当前代码完全一致，涉及现行实现时必须提示用户核对本地最新代码；
- Claude Code 通过 MCP 获取知识后，必须以用户本地最新代码作为实现事实。

### 7.8 MCP 服务

MCP 是 MVP 正式入口，使用远程 Streamable HTTP，以 Claude Code 完成验收。

#### 7.8.1 `knowledge_search`

用途：检索当前项目、分支和通用业务知识。

建议输入：

```json
{
  "project": "network-designer",
  "branch": "feature/import-export",
  "query": "场景包导入后为什么需要刷新拓扑？",
  "top_k": 5
}
```

#### 7.8.2 `document_read`

用途：读取指定知识文档的完整内容或分页内容。

#### 7.8.3 MCP 返回要求

每条结果尽量包含：

- 项目标识，或标明属于通用业务知识；
- 分支；
- 文档标题；
- 命中片段；
- 原 Wiki URL 或上传文件名；
- 可选的 PR、commit 或文件路径来源元数据；
- 索引或更新时间；
- 相关性分数；
- 内容是否被截断。

MCP 不调用 DeepSeek 生成最终答案，只返回原始上下文和引用，由 Claude Code 自行综合。

### 7.9 最小 Web 页面

MVP 只建设以下页面：

1. **登录页**；
2. **项目列表页**，包含“通用业务知识”入口；
3. **项目详情页**，包含文档目录、变更知识单元、需求和 PR 材料导入、知识草稿生成与审核、Agent 运行列表与详情和整理报告；
4. **问答页**，包含项目与分支选择、问答、来源展示和知识缺口反馈。

不建设仪表盘、个人中心、组织管理和复杂统计页面。

## 8. 可信回答要求

### 8.1 必须拒答的情况

- 没有检索到相关的已发布业务知识；
- 只有低相关内容，无法支持结论；
- 用户要求确认当前代码实现，但已发布文档没有足够依据；
- 问题超出当前项目和通用业务知识范围；
- 来源之间存在无法解释的冲突。

### 8.2 拒答内容

拒答时应：

- 明确说明“当前知识库没有足够依据”；
- 展示少量可能相关的来源；
- 涉及实现时提示用户核对本地最新代码；
- 允许用户创建知识缺口反馈；
- 不允许模型用通用知识补写项目事实。

### 8.3 内容安全

导入的 Wiki、人工文档、需求材料、PR 描述、diff 和源代码均视为不可信数据。其中包含的指令不能改变系统行为，也不能触发命令、网络访问或数据修改。

## 9. 数据来源

| 来源 | MVP 接入方式 | 后续方向 |
|---|---|---|
| 人工整理文档 | Web 新建、编辑或上传 Markdown/文本 | 多人协作、审核、版本 |
| 公司原 Wiki | 系统外转为 Markdown 后一次性导入 | 专用连接器和增量同步 |
| 需求与 PR | 手动录入元数据，上传 Markdown、diff/patch 和变更文件列表 | 对接公司 Git 平台并按合并事件触发知识草稿 |
| 本地代码 | 不直接导入；仅在 PR 材料中接收有限 diff/patch 和文件列表 | 根据实际收益评估 Git 平台连接或代码检索 |
| 通用业务知识 | 管理员新建或批量导入 | 负责人、复审和适用范围治理 |
| 模型生成内容 | DeepSeek `deepseek-v4-flash` 生成待审核 Markdown 草稿 | 模板化生成、变更驱动更新和多人审核 |
| Welink 群聊/会议 | 不接入，仅预留来源类型 | 人工选择内容、脱敏、摘要和审核后入库 |

## 10. 非功能需求

### 10.1 部署与模型

- 系统部署在公司内部环境；
- 后端采用团队可维护的 Java 技术栈；
- 支持 Docker Compose 启动；
- Embedding 和向量检索可在 CPU 环境运行；
- Web 答案生成调用 DeepSeek `deepseek-v4-flash` OpenAI 兼容接口；
- 模型接口与业务逻辑解耦，接口不可用时文档浏览和搜索仍可使用。
- Agent Runtime、Skill 定义和底层模型接口解耦，替换模型不应改变知识与权限边界。
- 两个知识生产 Agent 使用应用定义的少量固定步骤，不依赖模型动态创建角色或自由修改流程；
- 运行、公开事件和最终产物元数据持久化到 PostgreSQL，大型 Markdown 产物通过 ObjectStorage 保存；

### 10.2 性能目标

- 普通知识搜索目标响应时间不超过 3 秒；
- MCP 检索目标响应时间不超过 3 秒；
- Web 问答支持流式输出，生成耗时以 DeepSeek `deepseek-v4-flash` 接口实测为准；
- 单次 MCP 和文档读取返回设置长度上限；
- 单个索引任务失败不得破坏现有可查询索引。
- Agent 单次运行必须设置最大步骤数、超时和上下文长度，超限后安全终止并保留错误记录。
- 文档工作流只执行一次生成和结构检查；证据不足时保存未确认项并进入人工处理，不允许无限循环；
- 前端以服务端运行快照为事实来源，SSE 中断或页面刷新后可重新获取当前状态；

### 10.3 安全底线

- Web 和 MCP 均不能匿名访问；
- 管理写操作和普通查询操作分离；
- MCP 只读；
- 知识 Agent 按 Skill 使用工具白名单，不能执行 Shell、任意 HTTP 请求或数据库管理操作；
- 项目记忆、Skill、人工反馈和导入材料中的文本不能扩大 Agent 工具、项目范围、文件系统、网络或发布权限；
- Agent 产生的内容只能写入草稿、整理报告或知识缺口，发布操作必须由管理员执行；
- Token 和模型密钥不得写入知识文档、PR 材料或日志；
- 默认排除 `.env`、私钥、证书和明显密钥文件；
- 记录导入、重建索引和问答错误，不记录完整密钥和不必要的完整代码内容。

### 10.4 可恢复性

- 原始上传文件与索引状态分离；
- 索引可以删除后重新构建；
- 重新索引失败时继续使用上一个成功索引；
- 项目和知识数据应支持备份。
- Agent 运行、事件和最终产物引用应支持备份；
- 后端异常退出后不得留下已发布一半的知识；未完成运行可明确失败并由管理员重新发起；

## 11. MVP 验收

### 11.1 数据验收

- 成功创建两个项目；
- 网络设计工具项目包含 `main` 和一个场景包演示分支；
- 成功导入场景包文档和一批由原 Wiki 转换的 Markdown；
- 成功导入一组需求、PR、diff/patch 和测试说明材料；
- 成功创建至少一篇通用业务知识。

### 11.2 检索验收

开发前准备 15～20 个真实问题，并为每个问题标注应命中的已发布知识文档：

- 约 10 个场景包导入导出问题；
- 约 5 个项目启动、架构或通用业务问题；
- 至少 3 个系统不应回答的问题；
- 至少 2 个使用口语或相似表达的问题。

建议验收目标：

- 至少 80% 的有答案问题在 Top-5 结果中出现正确来源；
- 所有包含项目事实的 Web 答案均展示至少一个来源；
- 无依据问题不编造答案；
- 当前分支查询不返回其他分支文档；
- 询问文档未覆盖的当前代码实现时能够明确拒答并提示核对本地代码。

### 11.3 知识生成与整理验收

- 管理员能够基于需求、PR、diff/patch 和测试说明生成一篇 Markdown 业务知识草稿；
- 草稿展示需求与 PR 来源、分支、可选 commit、生成时间和无法确认的事项；
- 草稿发布前不会出现在普通用户检索和 Web 问答中；
- 管理员编辑并发布后，重新索引即可检索到该文档；
- 手动知识整理能够输出至少一种过期、重复、冲突或知识缺口提示；
- 每周任务只生成报告或草稿，不自动修改已发布知识，失败不得影响已发布知识和检索。

### 11.4 Agent 与 Skill 验收

- Web 问答运行记录显示使用了 `project_qa` Skill 及其版本；
- 需求实现整理运行记录显示使用了 `change_documenter` Skill；
- 知识库整理运行记录显示使用了 `knowledge_curator` Skill；
- Agent 无法调用当前 Skill 白名单以外的工具；
- Agent 达到最大步骤数或超时后能够安全停止，不产生半发布状态；
- Agent 只能保存草稿、报告和知识缺口，不能直接发布文档；
- `project_qa` 无法调用代码搜索或代码片段读取工具；
- 两个知识生产 Agent 只使用应用定义的固定步骤，不动态增加角色；
- 管理员可补充本次整理方向、修改草稿、发布或取消；
- IDEA 停止并重新启动后端后，不出现已发布一半的知识；未完成运行可明确失败并重新发起；
- 运行详情不展示模型原始思维链。

### 11.5 需求到实现沉淀验收

- 使用“场景包导入导出”真实需求文档、对应 PR 信息和 diff 创建一个变更知识单元；
- Agent 生成包含需求条目、变更文件、实现摘要、测试证据和未确认项的知识草稿；
- 运行过程展示材料读取、知识提取、草稿生成、结构检查及人工决定；
- 每个主要实现结论能够追溯到需求材料、PR、commit 或文件路径；
- 对无法从材料确认的实现关系明确标记，不生成虚假映射；
- 管理员审核发布后，该文档可被 Web 和 MCP 检索到；
- 产物明确说明其实现结论仅对应导入的 PR 材料，不代表用户当前本地代码。

### 11.6 MCP 验收

- Claude Code 可使用共享 Token 连接 MCP；
- 可以调用知识搜索和文档读取两个只读工具；
- 同一业务问题能够返回与 Web 使用的同源知识；
- 结果包含项目、分支、来源、文件路径、commit 和更新时间；
- Claude Code 可以结合本地代码完成一次相似需求的文件定位；
- MCP 不调用 DeepSeek 生成最终答案。

### 11.7 权限验收

- 只读账号不能新增、上传、编辑或重新索引；
- 管理员能够完成所有内容维护操作；
- 无效 MCP Token 无法检索内部内容。

## 12. 20 天交付边界

建议按以下顺序交付，后续功能不得阻塞前面的核心链路：

1. 项目、分支和文档数据准备；
2. 管理员导入与编辑、普通用户浏览；
3. 业务文档关键词与向量检索；
4. 需求文档、PR、diff/patch 和测试材料导入；
5. `change_documenter` 生成业务知识草稿、管理员审核发布；
6. `knowledge_curator` 生成整理报告和待审核修订草稿；
7. `project_qa` 基于已发布文档完成 Web 带引用问答和无依据拒答；
8. Claude Code MCP 的知识搜索和文档读取工具；
9. 分支隔离、文档冲突提示和知识缺口反馈；
10. Docker Compose、测试、文档和现场演示脚本；
11. 每周知识整理任务及其报告/草稿审核入口。

## 13. 最终交付物

- 可运行的 MVP 源代码；
- Docker Compose 部署配置；
- README 与初始化说明；
- 本需求文档；
- 系统架构与数据模型说明；
- `project_qa`、`change_documenter` 和 `knowledge_curator` Skill 定义与使用说明；
- Claude Code MCP 配置示例；
- 15～20 个问题的检索效果报告；
- 知识生成与整理演示样例；
- 场景包需求到 PR 实现的完整知识沉淀样例；
- 固定现场演示脚本；
- 已知限制与后续路线说明。

## 14. 后续路线

MVP 验收后，再按实际使用反馈考虑：

1. 根据真实使用收益评估代码快照、代码检索和版本维护是否需要重新启用；
2. 公司 Wiki 专用连接器和增量同步；
3. 对接公司 Git 平台，在 PR 合并后自动创建待整理任务；
4. Welink 群聊和会议纪要的人工选择、脱敏、摘要、审核和入库；
5. OIDC、个人账号和项目权限；
6. 普通成员编辑、版本历史和审核发布；
7. 更完整的知识过期检测、负责人提醒和多级审核；
8. 更多 MCP 客户端兼容验证；
9. 在真实需求中评估是否需要代码向量、符号索引或调用关系。
10. 评估动态 Supervisor、分布式 Agent、A2A、多实例抢占和自动恢复是否具有真实收益；
11. 扩展多文件、分支级或用户级记忆，并评估自动提炼记忆的审核机制。
