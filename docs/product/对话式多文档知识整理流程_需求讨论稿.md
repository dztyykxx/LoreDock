# 对话式多文档知识整理流程 MVP 需求

> 状态：已确认，进入实现
>
> 日期：2026-08-02
>
> 本文记录知识整理任务本轮 MVP 的产品目标、交互、业务规则与验收边界。涉及外部行为、接口和数据模型的实现以对应有效 OpenSpec 为准。

## 1. 目标

当前知识整理任务虽然支持多轮运行和单草稿修订，但页面把对话、底层事件和单份 Diff 固定挤在双栏中。Agent 的可见回复大多只有“运行已完成”，用户无法在运行中理解关键判断，也无法审核一次运行对多篇知识文档产生的变化。

本轮 MVP 要跑通以下闭环：

```text
选择候选输入并提出整理要求
→ Agent 实时输出公开决策并调用受控 Tool
→ 一轮新增或修改多篇工作文档
→ 用户查看本轮变更与当前累计 Diff
→ 用户继续对话创建下一轮修改
→ 管理员一次性原子发布全部工作文档
```

成功标准：

1. 一个知识任务在单轮完成或失败后仍可继续对话，直到发布、确认无需变更或放弃。
2. Agent 在运行中输出少量、真实、可持久化的公开决策说明，而不是只在结束后返回状态占位文案。
3. 同一任务可以新增或修改多篇文档，下一轮从服务端工作区的最新修订继续。
4. 同一次 Tool 调用在 UI 中聚合为一张可展开卡片，允许核验脱敏后的真实业务输入输出。
5. 用户可以区分“本轮改了什么”和“当前累计待发布什么”。
6. 所有有效工作文档按管理员审核的明确修订集合原子发布；Agent 永远没有发布权限。

## 2. 用户与核心概念

### 2.1 用户

首版只面向项目管理员。普通成员不进入知识任务审核页面，也不能创建、继续、停止、关闭或发布任务。

### 2.2 知识任务

知识任务是长期业务会话，不等同于单次 Agent run。任务状态只有：

- `PROCESSING`：可以继续对话，尚未关闭；
- `PUBLISHED`：累计变更已发布，任务只读；
- `CLOSED_NO_CHANGE`：管理员确认无需变更，任务只读；
- `ABANDONED`：管理员放弃，任务只读。

Run 保留排队、运行、完成、失败、取消等独立状态。Run 完成不得把整个任务显示为“已完成”。

### 2.3 会话工作区

每个任务拥有一个逻辑工作区。工作区不复制整个知识库，而是由该任务下全部有效 `knowledge_draft` 及其最新修订组成。

工作文档只支持：

- `ADD`：新增正式知识；
- `MODIFY`：修改已有正式文档正文。

首版不支持删除、归档、替代、重命名、移动或创建知识目录。

限制：

- 单任务最多选择 20 份候选输入；
- 单任务最多产生 10 份有效工作文档；
- 只有空修订的工作草稿不进入变更集，也不能发布。

### 2.4 每轮变更与累计变更

- 每轮 Patch Set：该 run 开始到结束期间，每篇工作文档的净变化；
- 累计变更：当前全部工作文档最新修订相对其正式基线或空基线的变化；
- 最终发布对象始终是累计变更，不是某一个历史 Patch Set。

Patch Set 从工作草稿及不可变修订的 `created_by_run_id` 计算，不增加独立 Patch Set 表。

## 3. 创建与候选输入

1. 管理员在待处理草稿中选择 1～20 份候选输入，并填写整理目标。
2. 服务端固定候选文档 ID、当时修订、项目、操作者、目标 Skill 和创建幂等键。
3. 候选输入从 `PENDING` 进入 `PROCESSING`。
4. 系统创建知识任务、首条用户或系统触发消息和第一轮 run。
5. 页面第一轮顶部显示一张默认折叠的“输入材料 · N 份”上下文卡，后续轮次不重复展示。

候选文档的发布生命周期与整理状态相互独立。整理状态只使用：

- `PENDING`：尚未进入有效任务；
- `PROCESSING`：属于仍在处理的任务；
- `CURATED`：管理员已通过发布或确认无需变更完成整理。

## 4. Agent 运行与对话

### 4.1 默认行为

收到用户消息后，Agent 默认直接检索并修改工作区，不要求每轮写入前人工确认。证据冲突、目标不明确或可能错误覆盖时，Agent 在最终公开回复中提出具体问题并正常结束当前 run；用户补充信息后创建新 run。

工作文档只保存有依据、可直接发布的长期知识。待确认问题、风险警告、冲突处理过程和本轮执行说明必须由模型在最终回复中说明，不得调用专用警告记录 Tool，也不得作为“待确认事项”等章节写入工作文档正文。

首版不恢复同一个 run，不建设 Agent 主动 Checkpoint 等待协议，也不允许运行中注入新用户消息。

### 4.2 公开决策消息

不展示或持久化原始思维链。Skill 要求 Agent 通过公开可见的 AssistantMessage 主动进行正常对话，通常覆盖：

1. 开始时说明本轮准备如何处理；
2. 发现关键重复、冲突、过期或缺口时说明判断；
3. 写入前说明准备新增或修改哪些文档；
4. Tool 全部结束后，用一条不含 Tool Call 的完整最终回复总结实际结果、风险和待确认问题。

每条消息用简短自然语言说明“当前结论、主要依据、下一步”，不机械复述 Tool 名称。公开沟通只使用模型原生 AssistantMessage，不增加消息 Tool。后端从框架每轮 `AGENT_MODEL_FINISHED` 聚合消息取得完整正文，不把最后一个流式 token 当作结果。公开决策必须由模型真实撰写，后端不得根据其他 Tool 事件伪造。系统提示词、隐藏消息、模型供应商推理字段和 ToolContext 不进入页面。

新一轮使用独立 run/thread，但会在启动上下文中携带有界的历史用户消息和各轮模型最终回复，以理解用户对上一轮结论的指代。历史公开过程、Tool Call、Tool 参数和 Tool 结果不重复注入；工作文档与执行事实始终通过最新工作区 Tool 读取。

### 4.3 运行中交互

- 运行中输入框禁用；
- 用户可以请求“停止本轮”；
- 停止在安全步骤边界生效，本轮进入 `CANCELLED`；
- 已经提交的工作文档修订继续保留；
- 后续用户消息创建新 run，不恢复旧 Checkpoint。

### 4.4 时间线层级

一条连续时间线按发生顺序展示：

- 用户消息；
- Agent 公开决策与最终回复；
- Tool Invocation 卡片；
- 每轮文件变更卡；
- 轻量系统状态记录。

每个已结束 Run 的公开过程消息和 Tool Invocation 统一放入默认折叠的“执行过程 · 工具调用 N 次”区块，最终 Agent 回复保留在折叠区外并按安全 Markdown 预览；管理员展开整轮过程后看到按时间排序的公开说明和紧凑 Tool 卡，再按需展开单次调用的参数与结果。运行中的当前 Run 默认展开，仍允许手动折叠。这样任务完成后页面优先呈现最终回复和文档变更，不被大量 Tool 调用挤占。

每轮使用轻量分隔条标明轮次和 Run 状态，不使用巨型嵌套运行卡。运行开始、完成、失败、取消和发布成功使用窄条系统记录，不伪装成聊天气泡。

## 5. Tool Invocation

### 5.1 聚合

同一个模型 `toolCallId` 从开始到完成或失败只产生一个前端 Tool Invocation。服务端可以保留细粒度内部事件，但页面投影必须按稳定调用 ID 聚合并原位更新状态。

折叠状态展示：

- Tool 名称；
- 业务用途；
- 状态；
- 耗时；
- 结果摘要；
- 稳定 Tool 编号。

展开后展示：

- 模型实际提交的业务参数；
- 模型实际收到的业务结果或业务错误；
- 是否截断。

### 5.2 安全与长度

- 不保存或展示服务端 ToolContext、权限、操作者、内部安全字段和未传给模型的参数；
- 输入与输出分别最多保存约 12,000 个字符；
- 超限内容截断并设置 `truncated=true`；
- 首版不做分页、附件下载和 Tool 结果人工确认。

## 6. 多文档工作区 Tool

正式知识继续使用现有 `knowledge_*` Tool。工作区增加：

```text
workspace_document_list
```

至少返回：

```json
[
  {
    "draftId": 31,
    "operation": "MODIFY",
    "baselineDocumentId": 18,
    "baselineRevision": 6,
    "title": "OpenSpec 使用规范",
    "directory": "研发规范",
    "currentRevision": 4,
    "lastChangedRunId": 12
  }
]
```

公开沟通不增加 Tool。模型在调用业务 Tool 的 AssistantMessage 中直接附带简短公开说明，最后再返回一条不含 Tool Call 的完整最终回复。

规则：

1. 每轮开始先列出当前全部有效工作文档；
2. 使用现有 `draft_read` 读取最新或指定历史修订；
3. `knowledge_*` 只读取当前正式知识，不增加通用 `view` 参数；
4. 工作区不建设临时向量索引；
5. 会话、项目、操作者和 run 由 ToolContext 固定，模型不能指定其他范围。

## 7. 文档创建、修改与来源

### 7.1 输出边界

Agent 按稳定知识主题决定输出数量，不按候选输入文件数量机械拆分：

- 多份输入可以合并进一篇；
- 一份输入可以按明显不同的稳定主题拆为多篇；
- 已有主题匹配的正式文档时优先 `MODIFY`；
- 只有没有合理归属、强行合并会破坏主题聚合时才 `ADD`；
- 不得为了减少文件数把无关规则塞进综合大文档。

### 7.2 MODIFY

第一次创建正式文档工作副本时固定：

- `baseline_document_id`；
- `baseline_revision`；
- 标题、目录和标签。

此后只允许修改 Markdown 正文，不允许更换基线或修改标题、目录和标签。每次有效更新形成不可变工作修订。

### 7.3 ADD

创建新文档时必须提供：

- 标题；
- 已存在的知识目录。

标签可以为空。Agent 必须先读取项目知识目录，不能自行创建目录。空草稿完成至少一次有效正文写入后才进入变更集。

### 7.4 来源

每次有效写入继续记录候选输入、已发布证据或用户消息的稳定 ID。来源通过 Tool 事实与模型最终回复展示，首版不建设单独的来源页。

## 8. 文件变更卡与 Diff 抽屉

### 8.1 本轮文件变更卡

每轮结束后紧跟一张变更卡：

```text
本轮修改 3 个文档                         +42 -16

新增  开发实践复盘.md                      +28  -0
修改  OpenSpec 使用规范.md                 +10 -12
修改  后端开发约束.md                       +4  -4
```

规则：

- 同一文档本轮多次写入合并为一行；
- 只显示该轮净变化；
- 没有有效变化时显示“本轮未产生文档变更”；
- 失败或取消但已经产生修订时标明“本轮未完成，已保留部分修改”；
- 点击文档打开该轮起止修订 Diff。

### 8.2 累计审核条

页面顶部吸顶显示：

- 当前待发布文档数量；
- 累计新增和删除行数；
- 是否存在失败、取消或正式基线冲突；
- “审核并发布”入口。

点击后先展示累计文档清单，再选择文档打开正式/空基线到当前修订的 Diff。存在未处理的失败变更或冲突时禁止发布。

### 8.3 Diff 抽屉

- 从页面右侧按需打开，约占桌面窗口一半；
- 只展示新增/修改状态、标题、比较修订、增删统计和服务端 Unified Diff；
- 支持上一个、下一个文件和关闭；
- 前端可以按行给 `+`、`-`、`@@` 添加简单颜色；
- 不引入 Diff 编辑器，不做当前内容预览、左右分栏、语法高亮、虚拟滚动、逐文件已读或大 Diff 专项能力。

首版按桌面端设计，最低有效宽度 1280px；较窄窗口中抽屉覆盖主页面。

## 9. 实时同步

1. 页面先通过 REST 获取任务完整快照；
2. 随后以数据库事件序号连接知识任务 SSE；
3. 每条完整公开决策消息、Tool 状态变化、Patch Set、Run 状态和任务状态变化产生持久化事件；
4. 不推送逐 Token 文本；
5. 断线后携带最后事件序号续接；
6. 页面刷新时重新获取 REST 快照，前端内存不作为业务事实来源；
7. 用户停留在底部时自动跟随新事件；用户向上查看后停止自动滚动并显示“有新消息”。

## 10. 原子发布

### 10.1 审核请求

管理员提交任务当前全部有效工作文档的明确修订集合和发布幂等键：

```json
{
  "idempotency_key": "publish-...",
  "documents": [
    {"draft_id": 31, "reviewed_revision": 4},
    {"draft_id": 32, "reviewed_revision": 2}
  ]
}
```

服务端要求请求集合与当前全部有效工作文档完全一致。少传、多传、重复、空草稿或任一当前修订变化均拒绝发布。

### 10.2 MODIFY 发布

- 保持同一正式 `document_id`；
- 在固定基线修订仍是当前正式修订时更新正文并增加正式修订号；
- 标题、目录和标签保持不变；
- 正式基线变化时整批冲突，不静默覆盖。

### 10.3 ADD 发布

- 创建新的正式文档 ID；
- 在项目内校验最终目录和标题不冲突；
- 工作草稿 ID 不成为正式文档 ID。

### 10.4 事务与幂等

服务端按稳定顺序锁定任务、工作草稿和正式基线，并在一个事务内完成：

1. 验证任务仍为 `PROCESSING`；
2. 验证完整审核集合；
3. 执行全部 ADD/MODIFY；
4. 标记草稿已发布；
5. 把任务改为 `PUBLISHED`；
6. 把候选输入改为 `CURATED`；
7. 写入发布记录；
8. 创建一个持久化索引任务。

任何一步失败全部回滚。相同幂等键与相同请求返回第一次结果；同键不同请求冲突。

索引在事务提交后异步执行。索引失败不回滚正式知识，页面显示“索引更新失败，后台待重试”。

## 11. 无变更关闭与放弃

### 11.1 确认无需变更

当当前工作区没有有效文档时，管理员可以填写简短结论并“确认无需变更”：

- 任务进入 `CLOSED_NO_CHANGE`；
- 候选输入进入 `CURATED`；
- 写入关闭系统记录；
- Agent 的文字判断不能自动执行此操作。

### 11.2 放弃任务

管理员可以放弃仍为 `PROCESSING` 的任务：

- 任务进入 `ABANDONED`；
- 候选输入回到 `PENDING`；
- 保留消息、Run、Tool 和工作修订供历史查看；
- 任务变为只读。

发布、无需变更关闭或放弃后，后续修改必须基于正式知识或待处理输入创建新任务。

## 12. 页面视觉层级

- 默认使用约 840～960px 宽的居中对话主列；
- 用户消息为右侧紧凑浅灰气泡；
- Agent 使用左侧头像、名称和无大面积底色的 Markdown 正文；
- 公开决策带轻量“决策过程”标签；
- Tool 使用紧凑灰色可展开行；
- 文件变更卡使用白底细边框，作为每轮最醒目的结构化内容；
- 输入框固定在主内容底部；
- 模型调用数、Tool 调用数和 Run ID 收入运行详情，不占据页面首屏；
- 延续 Geist 字体、现有主色、细边框、低阴影和中等圆角。

## 13. 明确非目标

- 原始思维链、供应商 reasoning 字段展示或持久化；
- Tool 结果人工确认和 Tool 级审批；
- 人工暂停并恢复同一 run、Agent 主动 Checkpoint 恢复；
- 运行中注入新消息；
- 撤销、单文件撤销、历史恢复和破坏性重置；
- 人工编辑工作文档；
- 删除、归档、替代、重命名、移动和创建目录；
- 会话级临时向量索引；
- 单文件或部分发布、逐 hunk 合并和三方合并；
- 当前内容预览、复杂 Diff 组件和大 Diff 专项优化；
- Tool 结果分页或附件下载；
- 手机端知识审核；
- 同一任务跨多个正式发布周期继续修改。

## 14. 最小验收场景

在真实模型与数据库环境中：

1. 管理员选择两份候选输入并创建任务；
2. Agent 先列出工作区，读取输入和正式知识；
3. 时间线实时出现至少两条有业务含义的公开决策消息；
4. Tool 调用以单卡片原位更新，并能展开核验业务输入输出；
5. Agent 修改一篇已有正式文档并新增一篇文档；
6. 第一轮文件卡正确展示两篇文档的净变化；
7. 管理员追加指导，第二轮基于最新工作区继续修改；
8. 顶部累计审核条展示两篇最终待发布文档；
9. 管理员审核明确修订集合并一次发布；
10. 两篇文档在同一事务成功，任务与候选输入进入终态，并只创建一个索引任务。
