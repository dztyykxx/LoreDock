# 本地 PR 可复用业务流程提炼 Skill MVP 方案

| 属性 | 内容 |
|---|---|
| 建议名称 | `change-documenter` |
| 目标用户 | 使用 Claude Code、Codex 等本地 Agent 的开发者 |
| 目标版本 | 明日可用 MVP |
| 输入 | 需求文档、Git 仓库、PR 的 base/head commit，可选测试与补充说明 |
| 输出 | 一篇或多篇可提交 LoreDock 的候选业务知识 Markdown，以及一份本地审核报告 |

## 1. 核心目标

该 Skill 只提炼在后续需求、维护、问答和新人理解中仍然有价值的**可复用业务流程与业务规则**。

它不负责解释“代码是怎么写的”，也不生成按类、方法、文件或模块组织的实现文档。代码、Diff 和测试只是核对业务行为是否真实交付的证据。

只有当实现逻辑本身构成稳定业务流程或对外契约时才进入候选知识，例如：

- 业务状态如何流转；
- 哪个角色在什么条件下可以执行操作；
- 一个批次或审批流程何时成功、部分失败或整体回滚；
- 幂等、重复提交和并发冲突对用户产生什么结果；
- 异步任务如何进入处理中、成功或失败状态；
- 错误码对应的业务含义和用户恢复动作；
- 数据字段代表的稳定业务语义。

## 2. 明确不做

MVP 不做以下事情：

- 不从 base 重新实现一套 Agent 对照代码；
- 不切换或覆盖开发者当前分支，不修改 PR 代码；
- 不生成类图、调用链、文件清单或逐文件改动说明；
- 不记录框架用法、DTO 映射、临时重构和容易过期的实现细节；
- 不把需求中未交付的内容写成已实现业务事实；
- 不把代码中偶然出现、缺少测试或业务依据的行为直接固化为规则；
- 不自动发布正式知识；默认也不自动提交 MCP，必须先由用户查看候选文档。

## 3. 触发方式

Skill 应在用户表达以下意图时触发：

- “根据这个需求和 PR 提炼业务知识”；
- “把这次改动整理成可复用业务流程”；
- “生成可以提交 LoreDock 的候选文档”；
- “总结这个 PR 真正新增或改变的业务规则”；
- “检查需求和实际交付差异，并沉淀业务知识”。

不应因为用户只要求代码评审、Bug 定位、变更摘要或发布说明而触发。

## 4. 输入契约

### 4.1 必填输入

- Git 仓库路径；
- 一份或多份需求文档路径；
- base commit 与 head commit，或能可靠解析二者的 PR 引用。

### 4.2 可选输入

- PR 描述、评审结论或验收说明；
- 指定测试文件、测试命令或测试结果；
- 目标 LoreDock 项目标识；
- 建议知识目录；
- 用户特别关注的业务主题。

### 4.3 输入不足

- 无法解析 base/head 时停止，不猜测比较范围；
- 没有需求文档时可以分析 PR，但必须将结果标记为“仅根据实际交付提炼”；
- 没有测试证据时仍可输出代码明确表达的可观察行为，但审核报告必须说明验证缺口；
- 当前工作区存在未提交修改时只读分析指定 commit，不清理、不覆盖、不自动纳入证据。

## 5. 可复用业务知识判断标准

一条内容进入候选业务文档前，应同时回答：

1. 它描述的是角色、触发条件、业务步骤、分支、状态、规则、权限、数据语义或失败恢复吗？
2. 即使未来重命名类、拆分模块或更换框架，它仍然成立吗？
3. 它能帮助后续需求分析、验收、客服答疑、开发理解或故障判断吗？
4. 它有需求、实际代码、测试或评审材料中的可靠证据吗？

任一内容如果只回答“改了哪个类、调用了什么方法、用了哪个库”，默认排除。

允许一个 PR 最终输出零篇候选文档。纯重构、依赖升级、格式调整或没有形成稳定业务行为时，Skill 应明确报告“没有值得沉淀的新增业务知识”，而不是强行生成文档。

## 6. 事实与证据分级

| 情况 | 候选业务文档 | 本地审核报告 |
|---|---|---|
| 需求、实现和测试一致 | 写入已确认业务流程或规则 | 记录来源与验证覆盖 |
| 需求有描述，但 PR 未交付 | 不写成现行规则 | 记录“需求未落地” |
| PR 存在额外业务行为且证据明确 | 可作为“实际交付行为”写入 | 标明需求未覆盖 |
| 需求与 PR 冲突 | 只写双方都能确认的部分 | 列出冲突和待人工决定项 |
| 只有实现细节，没有业务意义 | 不写入 | 可在排除项中简述原因 |
| 证据不足或存在多种解释 | 不写入 | 提出具体待确认问题 |

候选业务文档必须保持干净：不包含调查过程、证据冲突、待确认问题和实现细节。这些内容统一进入本地审核报告，避免后续被误发布为业务事实。

## 7. MVP 工作流

### 7.1 确认比较范围

1. 检查仓库与当前工作区状态，只记录，不修改；
2. 解析需求文件、base、head 和 PR 元数据；
3. 验证 base/head 存在，并记录 merge-base、提交范围和生成时间；
4. 使用只读 Git 命令分析 commit、Diff 和测试变更，不 checkout 用户分支。

### 7.2 先理解需求意图

从需求中提取：

- 背景与目标；
- 参与角色；
- 触发条件与前置条件；
- 主流程；
- 分支、异常与恢复动作；
- 权限与范围；
- 状态和数据语义；
- 验收标准与非目标。

此阶段形成“预期行为清单”，不直接写最终文档。

### 7.3 核对真实交付

按业务行为而不是文件顺序阅读 PR：

1. 先看提交说明、Diff 统计和测试变化，定位可能影响用户行为的区域；
2. 读取实现中决定业务状态、规则、权限、结果和失败语义的必要代码；
3. 忽略纯重构、框架配置、机械映射和无业务影响的内部调整；
4. 用测试、接口契约和状态转换核对每条预期行为是否真实交付；
5. 建立“需求预期—实际交付—验证证据—结论”的行为矩阵。

### 7.4 划分稳定主题

- 按稳定业务主题拆文档，不按需求章节、commit 或代码文件拆分；
- 多个来源说明同一个业务流程时合并；
- 同一 PR 包含明显独立的流程时允许输出多篇；
- 一个主题至少应包含可理解的触发、流程或规则，不能只是一条孤立实现事实。

### 7.5 生成并自检

1. 先生成本地审核报告；
2. 只把已确认、可复用的内容写入候选业务文档；
3. 执行实现细节过滤和证据检查；
4. 向用户列出候选文件、主题、依据和未写入原因；
5. 用户确认后，可选调用 `knowledge_draft_submit` 逐篇提交；不自动启动整理任务或发布。

## 8. 输出结构

### 8.1 候选业务文档

每篇候选文档使用以下结构，允许删除不适用的小节：

```markdown
# <稳定业务主题>

## 背景与目标

## 适用范围与角色

## 触发条件与前置条件

## 业务流程

## 分支与失败处理

## 业务规则与数据语义

## 权限、一致性与重复操作

## 验收示例

## 来源
```

“来源”只记录需求标识或文件名、PR 标识、base/head commit 和验证方式，不复制需求正文、PR Diff 或代码内容。

### 8.2 本地审核报告

审核报告不提交为业务知识，建议结构：

```markdown
# PR 业务知识提炼审核报告

## 输入与比较范围
## 候选文档清单
## 需求与实际交付矩阵
## 未交付或偏差
## 待确认问题
## 被排除的实现细节
## 测试与证据覆盖
## 建议提交动作
```

## 9. 质量门禁

候选文档提交前逐篇检查：

- 不出现无必要的类名、方法名、源码路径和行号；
- 不按文件列表复述 PR；
- 每条关键规则都能追溯到至少一种可靠证据；
- 需求未落地内容没有被写成现行能力；
- 冲突和待确认问题只存在于审核报告；
- 文档描述在合理代码重构后仍然成立；
- 标题表达稳定业务主题，而不是需求编号或 PR 标题；
- 没有业务知识时允许零输出。

## 10. Skill 包建议

```text
change-documenter/
├── SKILL.md
├── references/
│   ├── extraction-rubric.md
│   └── evidence-rules.md
├── assets/
│   ├── business-knowledge-template.md
│   └── review-report-template.md
└── evals/
    └── evals.json
```

为同时支持 Claude Code 与 Codex，需要在调查阶段确认仓库级 Skill 的发现目录和共享方式。优先维护一份规范源，避免 `.claude/skills` 与 `.codex/skills` 两份内容长期漂移；如果软链接兼容性不稳定，MVP 可先机械同步两份完全相同的 Skill 包。

## 11. 最小验证样例

### 样例一：真实新增业务流程

输入包含新导入流程、权限、批次状态和失败恢复。期望输出完整业务流程，但不出现 Controller、Service、DTO 和数据库表名。

### 样例二：纯代码重构

输入只包含类拆分、命名调整和依赖升级。期望输出零篇候选业务文档，审核报告说明没有新增或改变可复用业务知识。

### 样例三：需求与实际交付不一致

需求要求失败后自动重试，PR 实际只记录失败并允许人工重试。期望候选文档只描述已确认的人工恢复流程，审核报告单独标记“自动重试未交付”。

### 样例四：一个 PR 包含多个稳定主题

输入同时改变审批流程和导入错误处理。期望按主题输出两篇文档，而不是按代码文件或一个 PR 强行合并。

## 12. 下一轮调查清单

新对话优先确认以下问题后再实现：

1. Claude Code 与 Codex 当前版本各自支持的仓库级 Skill 目录、软链接和引用资源行为；
2. PR 输入首版只支持本地 base/head，还是同时支持 `gh pr view/diff`；
3. 第一份真实验收需求、PR 和预期知识主题；
4. 输出目录约定，以及审核报告是否进入 Git；
5. MCP 提交默认关闭，还是在用户确认后逐篇询问提交；
6. 是否需要支持没有需求文档的历史 PR；
7. 如何从真实样例中提炼可自动检查的质量断言。
