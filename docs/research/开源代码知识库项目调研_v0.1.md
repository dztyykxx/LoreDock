# 开源代码知识库项目调研

| 属性 | 内容 |
|---|---|
| 文档版本 | v0.1 |
| 调研日期 | 2026-07-29 |
| 调研状态 | 候选筛选稿，尚未确定技术底座 |
| 目标 | 为组内代码项目建设可内网部署、可持续维护、可供人和本地 Agent 使用的知识库 |
| 技术约束 | 后端优先 Python 或 Java；不选 .NET 作为二次开发底座；初期以 CPU 为主 |

## 1. 结论摘要

本轮查看了 19 个相关开源仓库或项目，覆盖代码 Wiki 生成器、代码搜索/知识图谱/MCP、企业知识平台三类。

当前结论不是“选定某一个仓库”，而是：

1. 暂未发现一个采用 Python 或 Java、同时成熟满足以下五项能力的一体化开源项目：
   - 自动理解代码并生成结构化 Wiki；
   - Git 增量更新和文档过期治理；
   - 多仓库、用户、权限、审核和审计；
   - 可供团队本地 Agent 使用的远程 Streamable HTTP MCP；
   - 完整内网部署和本地模型支持。
2. [FSoft CodeWiki](https://github.com/FSoft-AI4Code/CodeWiki) 更像文档生成引擎，不是企业知识平台。它值得验证生成效果，但不应现在就确定为底座；仓库根目录未发现许可证文件，而 README 声称 MIT，二次开发前必须让作者明确许可证。
3. [XWiki](https://github.com/xwiki/xwiki-platform) + [XWiki AI/LLM](https://github.com/xwiki-contrib/ai-llm) 是本轮新增的 Java 方向。它的 Wiki、权限、版本、协作基础成熟，最新 MCP 扩展具备 Streamable HTTP、OIDC 和按当前用户权限过滤，且 RAG 支持 CPU 本地嵌入；但它不负责理解 Git 代码并自动生成项目文档，需要接入独立代码分析/生成 Worker。
4. [CodeGraphContext](https://github.com/CodeGraphContext/CodeGraphContext) 是较匹配团队技术栈的 Python 代码图谱/MCP 组件，具备多语言解析、增量监听和远程 MCP-over-SSE；但它不是 Wiki，也没有企业级多用户和权限模型，并且当前源码中的 API Key 依赖没有覆盖直接注册的 MCP 路由，需要自行补安全网关。
5. [Sourcebot](https://github.com/sourcebot-dev/sourcebot) 的多仓库代码搜索、引用和远程 MCP 很接近需求，可作为检索体验基准；但它使用 Functional Source License，并非 OSI 开源许可证，仓库权限同步和 MCP OAuth 等能力涉及企业版，不适合作为默认的自由二次开发底座。
6. [CodeAlmanac](https://github.com/AlmanacCode/codealmanac) 对“沉淀决策、流程、约束、历史坑”这个需求理解得很好，且知识以 Git 中的 Markdown 保存；但当前官方明确是本地单机产品，没有公开 MCP、托管登录或中央权限，可借鉴知识模型和维护机制。
7. 从当前证据看，更现实的路线是“平台层 + 代码智能/生成层”的组合，而不是押注一个仓库。至少应对 3 条组合路线做真实项目 PoC，再决定是否 fork。

## 2. 需求与硬约束

### 2.1 必须解决的问题

- 将项目架构、模块职责、核心流程、配置、部署和排障知识从口头交流转为可维护的 Wiki；
- 从代码和 Git 变化自动生成或更新部分内容；
- 允许成员补充代码中不存在的“为什么、约束、历史坑和操作经验”；
- Web 用户和本地 Agent 使用同一份知识、身份、权限和引用体系；
- MCP 必须适合中央服务，目标传输为 Streamable HTTP，而不是只支持本地 stdio；
- 回答要能追溯到 Wiki 页面、仓库、commit、文件、符号和行号；
- 内网部署，后端应由团队现有 Java/Python 人员维护；
- CPU 环境下仍能完成索引和检索，生成任务允许异步、低并发执行。

### 2.2 一票否决或强风险项

- 主体后端只有 .NET 且组内无人长期维护；
- 无明确许可证却计划直接 fork；
- 商业公司内部使用被许可证限制；
- 权限只在页面展示层处理，检索或 MCP 可越权；
- MCP 只有 stdio，无法作为统一的组内远程知识服务；
- 只能对公开 GitHub 仓库工作，无法接入公司内网 Git；
- 每次代码变化都必须全量重建，无法控制 CPU 成本。

## 3. 评估方法

本轮不仅查看 README，也对重点候选检查了后端源码、路由、认证、MCP transport、增量实现和许可证文件。

评估维度如下：

| 维度 | 关注点 |
|---|---|
| 代码理解 | AST、符号、调用关系、模块划分、代码引用 |
| Wiki 生成 | 项目概览、模块文档、流程、图表、中文输出 |
| 持续更新 | Git diff、commit、文件监听、缓存、过期标记 |
| 知识协作 | 人工编辑、版本、审核、反馈、负责人、Markdown/Git |
| 企业能力 | 多仓库、用户、OIDC/LDAP、权限、审计、任务管理 |
| Agent 接入 | MCP 类型、远程 transport、工具范围、鉴权、权限继承 |
| 内网适配 | 私有 Git、本地 LLM、CPU 嵌入、离线安装 |
| 可维护性 | Java/Python 匹配度、代码复杂度、改造边界、活跃度 |
| 法务风险 | 许可证是否明确、是否允许公司内部修改和使用 |

说明：表中的“强/中/弱/无”是基于当前公开代码的方向判断，不代替实际 PoC。

## 5. 重点项目源码核查

### 5.1 CodeWiki：生成能力值得测，但此前选得过早

官方仓库：[FSoft-AI4Code/CodeWiki](https://github.com/FSoft-AI4Code/CodeWiki)

已确认能力：

- Python 实现，支持多语言仓库的分层分析、模块文档、跨模块关系和 Mermaid；
- 可输出 Markdown/HTML，可将文档放到独立分支；
- 命令包含基于当前状态更新和与指定 commit 比较的模式；
- 可接 OpenAI-compatible、Anthropic、Bedrock、Azure，以及 Codex/Claude CLI 订阅模式；
- 包含 MCP 代码，但源码使用 `mcp.server.stdio.stdio_server`，当前是本地 stdio MCP；
- MCP 主要围绕“文档生成会话”设计，进程内会话存储有数量和过期限制，不是中央只读知识查询网关；
- Web 端是较轻的 FastAPI 任务提交和生成结果展示，没有完整用户、仓库权限、审核、审计和多租户模型。

主要风险：

- README 标注 MIT，但截至本次调研，仓库根目录没有 LICENSE 文件，GitHub 也未识别出许可证。没有许可证文件不等于可以默认按 MIT fork；必须先获得上游明确授权或补充许可证。
- 需要补的不是几个页面，而是平台层：身份、权限、多仓库、任务、检索、知识协作、远程 MCP、审计和运维。

定位：保留为“文档生成质量基准与候选 Worker”，不再预设为整个平台底座。

### 5.2 DeepWiki Open：界面完整，但状态与权限模型偏单机

官方仓库：[AsyncFuncAI/deepwiki-open](https://github.com/AsyncFuncAI/deepwiki-open)

已确认能力：

- Next.js/TypeScript 前端，Python FastAPI 后端；
- 支持 GitHub、GitLab、Bitbucket、私有仓库 Token 和本地目录；
- 支持 Ollama 和 OpenAI-compatible 模型；
- 提供较完整的 Wiki 浏览、图表和仓库问答体验。

主要缺口：

- 没有内置 MCP；
- 未发现可靠的 Git diff 增量文档生命周期；
- 当前访问控制更接近共享授权码，不是个人身份、仓库级 RBAC 和权限同步；
- 缺少企业级持久任务、审核、审计和多仓库治理。

定位：前端体验和生成流程的 PoC 候选，不宜直接假设为企业平台。

### 5.3 RepoWiki：轻量 Python 原型，改造自由度高但成熟度低

官方仓库：[he-yufeng/RepoWiki](https://github.com/he-yufeng/RepoWiki)

已确认能力：

- Python CLI/FastAPI + React；
- 支持 30 多种语言的文件级扫描；
- 输出 Markdown、JSON 和单文件 HTML；
- 使用依赖图/PageRank 提取重要文件，支持中文生成；
- SQLite 缓存按内容哈希跳过未变化文件，具备轻量增量基础；
- MIT 许可证。

主要缺口：

- 没有 MCP、OIDC、RBAC、审计和成熟多仓库平台；
- 项目非常新、代码规模和贡献者基础较小；
- 代码语义深度、复杂跨仓调用分析和大仓稳定性需要实测。

定位：全 Python 轻量路线的 PoC 候选；优势是容易读懂和改，风险是很多平台能力要自己建设。

### 5.4 RepoAgent：较早的增量文档研究实现

官方仓库：[OpenBMB/RepoAgent](https://github.com/OpenBMB/RepoAgent)

已确认能力：

- Python，Apache-2.0；
- 用 AST 生成对象级文档，分析调用关系；
- 能检测 Git 新增、修改、删除并替换对应 Markdown；
- 支持 pre-commit 触发和 `repoagent diff` 查看待更新文档；
- 可通过 `base-url` 指向 OpenAI-compatible 服务。

主要缺口：

- 重点仍是 Python 代码，README 将更多语言和本地模型列为未来工作；
- 没有成熟 Web Wiki、企业权限和 MCP；
- 文档粒度更偏对象级，是否能形成易读的项目级架构知识需实测。

定位：增量文档算法和 Git 集成参考，不单独承担平台。

### 5.5 CodeAlmanac：对“口口相传知识”的建模最值得借鉴

官方仓库：[AlmanacCode/codealmanac](https://github.com/AlmanacCode/codealmanac)

已确认能力：

- Python 3.12+，Apache-2.0；
- Wiki 是仓库中的普通 Markdown，面向决策、流程、不变量、历史坑和实体关系；
- 可从文件、目录、Git diff、commit 范围、GitHub PR/Issue 和本地 Agent 会话中吸收知识；
- `garden` 处理过期、重复、断链、弱证据等知识质量问题；
- 内容通过 Git 评审，避免数据库锁定；
- 本地只读查看器支持页面、搜索、主题、反向链接和多 Wiki 切换。

官方当前契约也明确：

- local-only；
- 无 hosted login/connect/upload；
- 无公开 SDK 或 MCP package；
- 主要复用本地 Codex 或 Claude 登录会话运行维护 Agent。

定位：知识分类、证据、Git 审核和“持续园艺”机制的强参考；若中央化使用，需要重做服务端、身份和 MCP。

### 5.6 XWiki + AI/LLM：目前最完整的 Java 平台层候选

官方仓库：

- [xwiki/xwiki-platform](https://github.com/xwiki/xwiki-platform)
- [xwiki-contrib/ai-llm](https://github.com/xwiki-contrib/ai-llm)
- [MCP 扩展说明](https://extensions.xwiki.org/xwiki/bin/view/Extension/LLM/llm-mcp-server/)
- [LLM 索引说明](https://extensions.xwiki.org/xwiki/bin/view/Extension/LLM/Index%20for%20the%20LLM%20Application/)

已确认能力：

- XWiki Platform 是成熟 Java Wiki 平台，具备页面版本、用户/组、空间、权限、编辑和扩展机制；
- AI/LLM 项目采用 LGPL-2.1，当前仍标为 Beta，版本 0.9；
- RAG 索引支持语义检索与关键词检索，可索引 XWiki 空间或通过 REST 加入文档；
- 可配置 OpenAI-compatible 服务；在 Linux x86-64 上还支持由 XWiki 服务器 CPU 直接运行嵌入模型，示例为 `sentence-transformers/all-MiniLM-L6-v2`；
- MCP 使用标准 Streamable HTTP；源码基于 Java MCP SDK 的 `HttpServletStatelessServerTransport`；
- MCP 通过 OAuth 2.0 Protected Resource Metadata 发现 XWiki OIDC Provider，Bearer Token 解析后绑定到具体 XWiki 用户；
- 搜索、读取和写入工具继续执行当前用户的文档权限检查；写入类工具默认关闭，并可按 Wiki 配置；
- MCP 已提供 `search_collections`、`list_collections`、`query_documents`、`get_document`、`get_tree` 等检索工具，也包含可关闭的编辑工具。

主要缺口与风险：

- 它不知道 Git 仓库的 AST、符号、调用关系、commit 和代码行；
- 需要开发 Git 同步/导入扩展，把生成的 Markdown、来源元数据和权限映射写入 XWiki；
- AI/LLM 与 MCP 扩展仍为 Beta，近期变更频繁，必须做版本锁定和升级测试；
- XWiki + Solr + 数据库比轻量 FastAPI 方案更重，CPU/内存占用需要实测；
- 如果启用 MCP 写工具，权限设计和 Agent 操作风险会显著增加；MVP 应只开放读工具和反馈工具。

定位：平台层重点候选，尤其适合团队愿意长期维护 Java 的情况；需要配一个独立代码分析/生成 Worker。

### 5.7 CodeGraphContext：Python 代码图谱组件有价值，但安全层未完成

官方仓库：[CodeGraphContext/CodeGraphContext](https://github.com/CodeGraphContext/CodeGraphContext)

已确认能力：

- Python、MIT；
- Tree-sitter 支持 23 种语言，并可选 SCIP 提高调用和继承解析精度；
- 建立文件、类、函数、调用、继承、导入等代码图；
- 支持 FalkorDB Lite、Kuzu/LadybugDB、远程 FalkorDB、Neo4j 等存储；
- `cgc watch` 可监听变化并重新索引受影响文件；
- 支持多仓库注册、上下文发现和切换；
- 有本地 stdio MCP，也有 FastAPI 的 MCP-over-SSE 端点；
- HTTP API 可以配置单一 `CGC_API_KEY`。

源码中需要特别注意：

- `require_api_key` 被挂在 `/api/v1` 的普通 API Router 上；
- MCP SSE 路由由 FastAPI App 直接 `add_api_route` 注册，没有经过该 Router 的依赖；
- 因此不能假设配置了 `CGC_API_KEY` 就自动保护了 MCP 端点，中央部署前需增加统一认证中间件或反向代理鉴权；
- 它只有单 API Key，没有个人身份、仓库授权和审计；
- transport 还是旧式 SSE，不是目标的 Streamable HTTP。

定位：Python 代码结构索引/符号工具候选；必须放在平台权限边界之后，不能直接暴露到组内网络。

### 5.8 Sourcebot：产品体验强，但许可证和企业功能边界要谨慎

官方仓库与文档：

- [sourcebot-dev/sourcebot](https://github.com/sourcebot-dev/sourcebot)
- [MCP Server 文档](https://docs.sourcebot.dev/docs/features/mcp-server)
- [仓库同步文档](https://docs.sourcebot.dev/docs/configuration/repos)

已确认能力：

- 支持 GitHub、GitLab Self-Managed、Bitbucket、Gitea、通用/本地 Git；
- 多仓库代码搜索、跳转、引用和问答体验完整；
- 能定时重新同步仓库；
- MCP 位于 `/api/mcp`，使用 Streamable HTTP，可搜索代码、读取文件和解析定义。

主要风险：

- 根许可证为 Functional Source License 1.1，而不是 OSI 开源许可证；允许内部使用，但限制提供竞争性产品/服务，且各版本在两年后才转 Apache-2.0；
- MCP OAuth 需要企业许可；
- 与上游代码仓库同步用户权限的功能也属于企业能力；
- 不生成团队 Wiki，也不沉淀人工决策和历史经验。

定位：作为“代码检索、引用和 MCP 体验”的基准；是否允许公司内部长期 fork，需由法务和采购一起判断。

### 5.9 MaxKB：Python 企业平台可用，但 MCP 角色不能误判

官方仓库：[1Panel-dev/MaxKB](https://github.com/1Panel-dev/MaxKB)

已确认能力：

- Python/Django + Vue，工作空间、应用、知识库、成员和较细权限结构完整；
- 支持本地模型、文档 RAG 和 PostgreSQL/pgvector；
- GPL-3.0。

源码核查后的 MCP 判断：

- `mcp_tools` 接口主要用于连接外部 MCP Server、读取其工具列表，再让 MaxKB 的应用/工作流调用；
- `tool_code.py` 能将自定义工具生成 FastMCP 服务，并通过 MaxKB Chat API 执行工具逻辑；
- 这不等同于“把某个知识库以受权限控制的检索 MCP 暴露给同事 Agent”；该能力仍需设计专用 MCP Server、身份映射和知识库权限过滤。

定位：Python 企业应用壳候选；若使用，需要另接代码分析、Wiki 文档生成和只读知识 MCP。

### 5.10 RAGFlow、Onyx、Dify：通用 RAG 强，代码知识生命周期弱

- [RAGFlow](https://github.com/infiniflow/ragflow)：Apache-2.0，混合检索和文档解析能力强，也有 MCP 配置；但官方起步资源建议较高，不具备代码 AST/符号/调用和 Wiki 增量生成语义。
- [Onyx](https://github.com/onyx-dot-app/onyx)：连接器和企业搜索成熟，核心部分为 MIT；但 GitHub 权限同步和高级 RBAC 位于企业代码，且面向通用文档而非代码 Wiki。
- [Dify](https://github.com/langgenius/dify)：工作流、Agent、RAG 和 API 生态强，但不是 Wiki，也不理解 Git diff 与代码结构；许可证包含品牌和多租户相关附加条款。

定位：它们适合提供通用 RAG 或工作流能力，不应因为“有知识库”就直接当作代码知识库底座。

## 6. 许可证筛查

| 风险级别 | 项目 | 说明 |
|---|---|---|
| 低 | DeepWiki Open、RepoWiki、CodeGraphContext | MIT，常规保留版权和许可证通知 |
| 低 | RepoAgent、CodeAlmanac、Potpie、RAGFlow、GitMCP | Apache-2.0，注意 NOTICE 和修改声明 |
| 中 | XWiki Platform、XWiki AI/LLM | LGPL-2.1；作为独立平台/扩展使用通常可行，修改和分发边界需法务确认 |
| 中 | MaxKB | GPL-3.0；内部部署与对外分发的义务不同，fork 策略需法务确认 |
| 中-高 | Dify | 修改版 Apache，包含多租户和品牌展示限制 |
| 高 | Sourcebot | FSL-1.1，源代码可见但不是传统开源；竞争性产品限制和未来转许可机制需确认 |
| 高 | GitNexus | PolyForm Noncommercial，公司内部商业环境使用不能默认获得授权 |
| 高 | CodeWiki | README 声称 MIT，但仓库无 LICENSE 文件，授权链不完整 |
| 高 | RepoDoc | 未发现 LICENSE 文件，仅作研究参考 |
| 不适用 | OpenDeepWiki | MIT，但因 .NET 维护能力不匹配而排除底座 |

许可证判断只用于技术筛选，不构成法律意见。进入 fork 前应由公司法务基于实际部署、修改和分发方式复核。

## 7. 可继续进入 PoC 的组合路线

这里列的是待验证路线，不是排序和最终建议。

### 路线 A：XWiki 平台 + Python 代码生成/图谱 Worker

组成建议：

- XWiki Platform + AI/LLM：用户、组、空间、版本、编辑、RAG、OIDC、远程 MCP；
- CodeWiki 或 RepoWiki：生成项目概览、模块文档和图表；
- CodeGraphContext：符号、调用关系、代码片段和变更影响；
- 自研 Git Sync Worker：私有仓库、commit/diff、Markdown 导入、来源元数据、权限映射。

优点：

- Java 平台层成熟，和团队维护能力匹配；
- MCP 的身份和文档权限基础最好；
- 人工 Wiki 与自动文档可以在同一平台治理；
- 可用 CPU 本地 embedding。

风险：

- 组合集成量不小；
- XWiki AI/MCP 仍为 Beta；
- 代码行、commit、符号需要自定义数据模型和工具；
- 整体资源消耗高于轻量 Python 方案。

### 路线 B：全 Python 轻量自研平台

组成建议：

- RepoWiki 或 CodeWiki：文档生成；
- CodeGraphContext：代码图和符号检索；
- FastAPI：仓库、用户、任务、审核、审计和 Streamable HTTP MCP；
- PostgreSQL + 全文索引/向量扩展；
- Markdown/Git：知识的可迁移来源。

优点：

- 技术栈统一，容易控制数据模型和 MCP；
- 初期资源最容易压低；
- 可以严格围绕组内需求实现，不背通用平台复杂度。

风险：

- 实际上是“用开源组件自建产品”，不是简单 fork；
- 用户权限、Wiki 编辑器、版本、审核和运维都要开发；
- RepoWiki 成熟度低，CodeWiki 又有许可证不确定性。

### 路线 C：MaxKB 平台壳 + 代码插件

组成建议：

- MaxKB：工作空间、知识库、应用、成员权限和问答；
- RepoWiki/CodeWiki/CodeGraphContext：代码分析；
- 自研知识 MCP：向本地 Agent 暴露受权检索。

优点：

- Python/Django，企业管理界面和 RAG 基础较完整；
- 比完全自研更快拥有后台和工作空间。

风险：

- MaxKB 的内容模型不是 Git Wiki；
- 现有 MCP 主要用于消费外部工具，不直接解决 Agent 查询知识库；
- GPL-3.0 和上游升级边界需评估；
- 代码引用、commit 和过期治理仍需大改。

### 路线 D：Sourcebot 代码检索 + 独立 Wiki

组成建议：

- Sourcebot：多仓代码搜索、同步、代码引用和 MCP；
- XWiki 或自研 Markdown Wiki：人工知识和生成文档；
- 统一身份代理：协调两个系统的授权。

优点：

- 最快达到较好的代码搜索和 Agent 体验；
- 代码检索部分产品化程度高。

风险：

- FSL 和企业版边界；
- 权限同步/OAuth 可能产生商业依赖；
- 两套知识和引用体系容易割裂。

## 8. 建议的 PoC，而不是现在选型

### 8.1 PoC 对象

建议保留四个对照组：

1. **XWiki + AI/LLM**：验证 Java 平台、OIDC、权限、CPU embedding 和远程 MCP；
2. **CodeWiki**：只验证生成质量、耗时、增量和引用，同时先向上游确认许可证；
3. **RepoWiki + CodeGraphContext**：验证全 Python 轻量组合的可行性；
4. **Sourcebot**：只作为代码检索/MCP 体验和性能基线，同时记录许可证与企业功能依赖。

DeepWiki Open、CodeAlmanac、RepoAgent 和 MaxKB不必全部搭建完整环境，可先抽取其 UI、知识模型、Git 维护和权限设计作为参考；如果上述四组结果不理想，再升级为实装 PoC。

### 8.2 统一测试仓库

选择一个真实、具有代表性的内部项目：

- Java 或 Python 为主；
- 10 万～50 万行代码更有区分度；
- 至少包含 3 个模块、一条跨模块业务流程、数据库/消息/API 等常见依赖；
- 有一段近期 Git 历史，可模拟新增、修改、移动和删除；
- 准备一位熟悉项目的负责人作为事实审核者。

### 8.3 统一问题集

建立 30～50 个真实问题，至少覆盖：

- 项目如何启动；
- 一个请求从入口到数据库的调用链；
- 某个业务规则在哪里实现、为什么这样设计；
- 哪些模块依赖某个接口或数据结构；
- 一个常见故障如何定位；
- 最近一次代码变化影响哪些文档；
- 一个无依据问题，系统是否明确回答“不知道”；
- 无权限用户是否能通过搜索、API 或 MCP 发现仓库内容。

### 8.4 记录指标

| 指标组 | 指标 |
|---|---|
| 质量 | 问题有效回答率、事实错误率、引用准确率、中文可读性 |
| 更新 | 变更识别率、误更新率、全量/增量耗时、是否覆盖人工内容 |
| Agent | MCP 配置复杂度、工具调用成功率、返回 token、commit/行号完整性 |
| 权限 | Web/MCP 越权测试、用户身份映射、权限变更生效时间 |
| 资源 | CPU、峰值内存、磁盘、首次索引耗时、单次查询延迟 |
| 维护 | 需修改的核心文件数、上游耦合、测试覆盖、升级冲突预估 |
| 法务 | 许可证是否明确、内部修改/部署是否可接受、企业功能依赖 |

### 8.5 进入下一轮的门槛

任一组合只有满足以下条件，才进入底座候选：

- 许可证明确并经内部确认；
- 能在目标 CPU/内存内稳定运行；
- Web 与 MCP 不发生仓库越权；
- 增量更新不会覆盖人工知识；
- 真实问题集回答质量达到试点门槛；
- 关键改造集中在扩展层，未大面积侵入上游核心；
- 团队至少两人能够理解、调试并升级关键模块。

## 9. 当前保留名单

### 9.1 建议实装 PoC

- XWiki Platform + XWiki AI/LLM；
- CodeWiki（以许可证澄清为前提）；
- RepoWiki；
- CodeGraphContext；
- Sourcebot（仅作基准或许可可接受时使用）。

### 9.2 建议设计参考

- CodeAlmanac：决策、流程、不变量、坑点、证据和持续维护；
- DeepWiki Open：代码 Wiki 的浏览和问答交互；
- OpenWiki：Docs-as-Code、CI 自动更新和文档 PR；
- RepoAgent/RepoDoc：增量文档生成；
- GitMCP/codebase-memory-mcp/GitNexus：Agent 工具和代码图谱体验；
- OpenDeepWiki：功能清单和交互参考，不复用 .NET 后端。

### 9.3 暂不优先

- RAGFlow、Onyx、Dify：通用 RAG 平台能力强，但偏离代码 Wiki 核心；
- GitNexus：公司使用的非商业许可证障碍；
- RepoDoc：许可证缺失且研究原型；
- 单纯使用通用向量知识库：无法满足符号、commit、行号、调用关系和 Git 增量需求。
