## 1. 前置准备

### 1.1 启动本地开发环境

```bash
cd <repo>
# 确保 docker 运行；脚本只启动 PostgreSQL/pgvector，后端与前端在宿主机运行
./scripts/dev.sh
```

- 前端：http://localhost:5173
- 后端：http://localhost:8080
- 数据库：仅 `docker compose stop database` 才会停止；`dev.sh` 退出不会清库
- 必须 JDK 21（`.env` 中 `LOREDOCK_JAVA_HOME` 指定的 OpenJDK 21）+ Node.js 24

### 1.2 开启 Agent 并配置模型（本机 `.env`，不入库）

`.env.example` 默认关闭 Agent，请在本地 `.env` 改为：

```bash
LOREDOCK_AGENT_ENABLED=true
LOREDOCK_AGENT_CHAT_PROVIDER=openai          # 与 spring.ai.model.chat=openai 对应
LOREDOCK_AGENT_MODEL_NAME=<你的模型名>
LOREDOCK_AGENT_MODEL_BASE_URL=<你的 OpenAI 兼容端点>
LOREDOCK_AGENT_MODEL_API_KEY=<你的密钥>
```

> 注意：`KnowledgeAgentDefinitionService` 启动时会加载并校验四份 Agent 定义（角色齐全、Tool 白名单一致），
> 定义或白名单有误会导致**启动失败**，这是符合设计预期（fail-fast），不是 bug。

### 1.3 准备测试材料

- 登录管理员账号，**至少一篇** `DRAFT` 状态的 Markdown 待处理草稿作为候选材料；
- 为了跑通“有充分来源”的正向路径，请在知识库中先有一篇**已发布**的、能支撑候选草稿内容的正式知识文档；
- 想观察“冲突/不足”，则准备一篇候选草稿内容与现有正式知识冲突、或没有来源的草稿。

> 若没有手工材料，可将 `LOREDOCK_DEMO_SEED_ENABLED=true` 使用演示种子数据；或用 SQL 参考
> `KnowledgeCurationPersistenceIT.seedInputDraft` 造一条 `DRAFT` 草稿。

## 2. 正向整理路径（场景 1：有充分来源的新知识）

**步骤**
1. 进入“待处理草稿”页，勾选一篇候选草稿；编辑目标（可写“把这部分整理成正式知识并说明来源”）；点击**启动**。
2. 展开本轮“执行过程”折叠区，并打开“第 1 轮”下的执行过程。

**预期（逐条打勾）**
- [ ] 阶段卡片按实际顺序出现，且名称映射正确：
  - `调度 Agent · 识别任务`（coordinator / START）
  - `检索 Agent · 检索知识`（retriever）
  - `调度 Agent · 决定下一步`（coordinator / DECIDE）
  - `草稿 Agent · 创建草稿`（drafter）
  - `审查 Agent · 审查草稿`（reviewer）
  - `调度 Agent · 汇总结果`（coordinator / FINISH）
- [ ] 每个阶段卡片有 `运行中 / 已完成 / 失败` 任一状态；正常路径最终为“已完成”。
- [ ] 检索、审查之间能看到 Tool 卡片（`knowledge_search`、`draft_read`、`draft_diff` 等），可展开看参数/结果摘要。
- [ ] 出现“本轮文档变更”（Patch Set），并能打开 Diff 抽屉查看统一 Diff。
- [ ] 最终回复显示为知识整理 Agent 的完整结论卡片；**没有**自动发布——发布按钮仍需人工点击“原子发布”。
- [ ] 阶段卡片只用公开摘要，不显示 Prompt、思维链、Checkpoint、完整 Graph State 或 Tool 原始 JSON。

**产出**：本轮产生带来源的草稿修订与 Diff，状态为“已完成”，未自动发布。

---

## 3. 审查返工（场景 2：审查持续不通过 → 最多两轮）

**步骤**
1. 同“场景 1”启动一个整理；当审查 Agent 判定需要返工时（需要模型输出 `REVISE` 而非 `PASS`，可用冲突/缺来源材料诱导，或用 `KnowledgeCurationGraphRunIT#reworkStopsAtTwoRoundsThroughGraph` 的脚本化输入作为预期）。
2. 观察同一次 run 内是否出现两轮草稿/审查。

**预期**
- [ ] 第一次审查显示“需要返工”，随后出现第 2 次“草稿 Agent”，再出现第 2 次“审查 Agent”。
- [ ] 两轮的阶段记录都保留，**不覆盖第一轮**（同一 run 内同类阶段事件出现两次，页面显示“第 2 轮草稿”“第 2 轮审查”）。
- [ ] 达到 `draftRound = 2` 后不再进入第三轮；最后一轮交给人工判断（调度 Agent 最终回复提出具体问题）。
- [ ] 全程无自动发布。

> 判定上限：`draftRound` 最大为 2，任何一轮都不会进入第 3 次草稿写入。

---

## 4. 普通闲聊短路（场景 3：只出现调度 Agent 和最终回复）

**步骤**
1. 先完成一个退出的 run（避免任务仍在运行）。
2. 在底部输入框输入一句纯问候（如“你好，在吗？”），点击**发送并继续**，开启新一轮。

**预期**
- [ ] 本轮“执行过程”里只有一张阶段卡：`调度 Agent · 识别任务`，状态“已完成”；**没有**检索/草稿/审查的占位卡或阶段卡。
- [ ] Tool 卡片数量为 0（无 `knowledge_search`、`draft_*` 调用）。
- [ ] 本轮最终回复就是调度 Agent 那份问候的可见回复（卡片显示为知识整理 Agent）。
- [ ] 本轮**不产生任何草稿修订**，也无“本轮文档变更”卡片。

> 若模型把问候误判为整理请求而进入检索，这是设计允许的兜底（见设计 §5.3“无法可靠判断时也进入 RETRIEVE”）——
> 这种情况下仍不许出现“三个空专家步骤”，且不得写草稿。请把实际观察记录到“验收记录”。

---

## 5. 刷新 / SSE 重连恢复（场景 4）

**步骤**
1. 在任一整理 run 运行中（出现阶段卡片后），**刷新浏览器页面**；等待完成后再次刷新。

**预期**
- [ ] 刷新后执行过程仍从持久化事件恢复，阶段卡顺序、Tool 卡片、Diff 都还在，不丢失。
- [ ] 重复刷新不产生重复的阶段卡或 Tool 卡片（页面用 `runId + sequence` 去重）。
- [ ] 运行中的任务默认展开“执行过程”；终态任务默认收起，但展开后完整。

---

## 6. 信息边界（场景 5）

**步骤**：分别在运行中、刚完成、完成多轮后检查页面与浏览器网络请求。

**预期**
- [ ] 页面任何位置都不出现：模型 Prompt、思维链、Checkpoint 内容、完整 Graph State、Tool 原始返回 JSON、内部 `subgraph_*` 节点名或 `_AGENT_MODEL_` 字样。
- [ ] 阶段卡只用服务端白名单字段（阶段、稳定 Agent 名、公开摘要、状态）；Tool 卡只用参数/结果**摘要**。
- [ ] 聊天记录里专家结果以“协作 Agent”身份出现，只展示公开摘要，不是完整结构化 JSON。

---

## 7. 冲突或证据不足（场景 6：`ASK_USER`，不写未确认事实）

**步骤**：用一篇与现有知识冲突、或找不到来源的候选草稿启动整理。

**预期**
- [ ] 调度 Agent 决定“询问用户”，阶段卡出现 `调度 Agent · 决定下一步` 且为“询问用户”。
- [ ] 最终回复是具体的、可回答的人工问题；**不进入草稿 Agent**，没有草稿修订，无“本轮文档变更”。
- [ ] 继续补充意见后能开启新一轮并沿用原会话与工作区。

---

## 8. 暂停 / 停止 / 继续（场景 7：既有接口无回归）

**步骤**：运行中点击“停止本轮”，或请求暂停。

**预期**
- [ ] “停止本轮”后 run 状态变为已停止/终态，不会继续写入；已提交的草稿修订保留。
- [ ] 停止后输入框可继续“发送并继续”，开启新一轮 run，不丢失会话历史。
- [ ] 进到等待人工后，补充指导能创建新 run（沿用既有机制），过程能恢复显示。
