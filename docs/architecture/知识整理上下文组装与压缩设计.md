# 知识整理上下文组装与压缩设计

| 项目 | 内容 |
|---|---|
| 文档状态 | 已确认的设计，待纳入 OpenSpec 实施任务 |
| 适用范围 | 知识整理会话的主 Agent、完整整理子图与专家直调 |
| 目标 | 在不丢失证据、人工决定、草稿修订和恢复语义的前提下，控制模型单次上下文成本 |
| 相关设计 | [知识整理多路 Agent 会话编排设计](./知识整理多路Agent会话编排设计.md) |

## 1. 背景与问题

知识整理任务已经支持跨轮会话、完整整理子图和主 Agent 直调专家。现有 Graph Checkpoint 可以恢复执行，但父 Graph 的 `messages` 使用追加策略，逐轮混入 Agent 原始结构化输出、阶段上下文副本和旧轮历史。后续模型调用因而携带与当前任务无关的旧工作过程。

上下文成本的根因不是 Checkpoint 本身。Checkpoint 是恢复用持久化状态；真正传给模型的是从状态中恢复并交给当前 Agent 的消息。设计必须把“可恢复的完整事实”与“本次模型调用的有限工作视图”分开管理。

## 2. 目标与非目标

### 2.1 目标

- 单次模型总上下文预算固定为 128k Token；发送前输入上下文硬上限为 96k Token；保留 24k 输出预算和 8k 协议/估算安全余量；
- 每一次模型调用前按当前 Agent、当前节点和当前任务重新组装最小上下文，不把父 Graph 的历史 `messages` 原样传递；
- 先使用可验证的确定性裁剪；只有仍无法满足预算时，才使用受限的 LLM 压缩兜底；
- 压缩不得丢失或改写人工确认、证据引用、草稿 `draftId + revision`、未解决问题与恢复所需状态；
- 每次模型调用记录估算与实际输入/输出 Token、压缩方式和压缩效果，且不记录 Prompt 或正文。

### 2.2 非目标

- 不把 Graph Checkpoint 当作模型上下文，也不要求删除其恢复所需的业务状态；
- 不使用 LLM 摘要替代来源事实、草稿正文、人工决定或写入对账；
- 不新增通用 Agent Runtime、消息队列、跨会话长期记忆或新的外部基础设施；
- 不以超限后的盲目重试替代上下文治理。

## 3. 预算与状态边界

```text
128k 模型总窗口
├─ 96k：发送前输入硬上限
├─ 24k：模型输出预留
└─  8k：协议与估算安全余量

72k：开始确定性压缩
96k：禁止发送未压缩输入
```

上下文有两种所有者：

| 内容 | 所有者 | 是否直接进入模型 |
|---|---|---|
| `stage`、`nextNode`、重试次数、草稿 revision、来源引用 | Graph State / Checkpoint | 否，按当前节点选择性投影 |
| 完整 Tool 回执、公开事件、历史消息 | 数据库审计事实 | 否，按需读取或缩短投影 |
| 系统规则、当前指令、必要事实、人工决定、当前工作窗口 | Context Assembly | 是 |

Checkpoint 保存完整的可恢复事实；模型只接收一次调用所需的 `PreparedModelContext`。模型上下文不是跨轮事实的权威来源。

## 4. 模块输入输出

上下文组装只在 `agent` 模块内使用，首版采用具体 Service，不新增跨模块 API、Port 或通用框架抽象。

```java
record ContextAssemblyRequest(
        Long conversationId,
        Long runId,
        AgentNode agentNode,
        ContextPurpose purpose,
        String currentInstruction,
        ConversationContext conversation,
        WorkflowContext workflow,
        ContextBudget budget
) {
}

record PreparedModelContext(
        List<Message> messages,
        ContextReceipt receipt
) {
}
```

### 4.1 输入模型

```java
enum AgentNode {
    MAIN_AGENT, RETRIEVER, COORDINATOR, DRAFTER, REVIEWER
}

enum ContextPurpose {
    CHAT,
    DIRECT_RETRIEVE,
    DIRECT_DRAFT,
    DIRECT_REVIEW,
    FULL_CURATION_RETRIEVE,
    FULL_CURATION_DECIDE,
    FULL_CURATION_DRAFT,
    FULL_CURATION_REVIEW,
    FULL_CURATION_REPORT,
    REPAIR
}

record ConversationContext(
        String originalGoal,
        List<DialogueTurn> recentTurns,
        List<ConfirmedDecision> confirmedDecisions,
        List<PendingGuidance> unconsumedGuidance,
        boolean historyTruncated
) {
}

record WorkflowContext(
        List<SupportedFact> facts,
        List<UnresolvedQuestion> unresolvedQuestions,
        List<SourceReference> sourceRefs,
        List<DraftReference> drafts,
        DraftInstruction draftInstruction,
        ReviewTarget reviewTarget,
        RetryContext retry
) {
}
```

输入模型禁止接收父 Graph 的原始 `messages`、完整 Tool 回执或旧 Agent JSON。文档、证据和草稿正文用 `documentId`、`draftId`、`revision`、`blockId` 等稳定引用表达；需要正文时由当前 Agent 通过受限业务 Tool 重读。

### 4.2 输出模型

```java
enum ContextMode {
    FULL,
    DETERMINISTIC,
    LLM_COMPRESSED,
    BLOCKED
}

record ContextReceipt(
        AgentNode agentNode,
        ContextPurpose purpose,
        ContextMode mode,
        int estimatedInputTokens,
        int inputUtf8Bytes,
        int beforeCompressionTokens,
        int trimmedTokens,
        int compressedTokens,
        int droppedHistoryTurns,
        int replacedBodiesWithReferences,
        List<String> appliedPolicies
) {
}
```

`PreparedModelContext.messages` 是唯一可交给 `ReactAgent` / ChatModel 的模型输入。`ContextReceipt` 只用于日志、运行观测和测试，不含消息正文。

## 5. 节点级最小上下文

| 当前节点 | 必须输入 | 禁止继承 |
|---|---|---|
| Main Agent / CHAT | 最近角色化轮次、当前用户消息、已确认决定、任务状态摘要 | 完整整理 Tool 链、旧专家原始 JSON |
| Retriever | 当前检索目标、必要范围、未消费引导 | 旧检索结果、草稿/审查过程全文 |
| Coordinator | 当前目标、Retriever 规范化事实、人工决定、未解决问题 | Retriever Tool 原文、旧轮汇报 |
| Drafter | 当前目标、已支持事实及引用、写入指令、`draftId + baseRevision` | 完整检索链、旧 Reviewer 结论、无关会话 |
| Reviewer | 已支持事实和引用、写入指令、待审 `draftId + revision` | Drafter 的完整 Tool 历史、旧会话闲聊 |
| Repair | 当前节点原始候选的有界错误摘要、必要任务输入 | 全部旧候选、无关历史 |

例如 `FULL_CURATION_DRAFT` 的模型消息可被组装为：

```text
系统规则：Drafter 的固定职责与写入边界

【当前任务】
将草稿 7 和草稿 9 合并为一份文档

【人工已确认决定】
- SCENARIO_ID_CONFLICT 以已发布规则为准

【允许写入的事实】
- fact-1：…… sourceRef=[draft:7, knowledge:20]
- fact-2：…… sourceRef=[draft:9, knowledge:16]

【写入要求】
- 目录：项目资料/02-导入导出
- 当前草稿基线：draftId=14, revision=1
```

## 6. 内部核心流程

```text
ContextAssemblyService.assemble(request)
  │
  ├─ 1. 根据 agentNode + purpose 选择允许的语义块
  ├─ 2. 生成系统规则、当前任务、人工决定、事实、引用和工作窗口
  ├─ 3. 使用 Token 估算器计算候选输入预算
  ├─ 4. <= 72k：返回 FULL
  ├─ 5. 72k ~ 96k：执行确定性压缩并重新组装
  ├─ 6. > 96k：对可压缩块调用 LLM 压缩兜底并重新组装
  └─ 7. 仍 > 96k：返回 BLOCKED，调用方不发送模型请求
```

`BLOCKED` 映射到 `WAITING_FOR_USER`，保留当前语义稳定 Checkpoint，并提示管理员缩小草稿范围、指定目录或拆分任务。它不是模型解析失败，不进入同输入重试回路。

### 6.1 确定性压缩顺序

1. 移除旧 Tool 调用参数与 Tool 原文，保留 `toolCallId`、摘要、来源引用和截断标记；
2. 移除已完成节点的原始结构化 JSON，只保留已规范化的状态字段；
3. 用 `documentId`、`draftId`、`revision`、`blockId` 替换正文；
4. 按完整 User/Assistant 轮次从旧到新删除会话历史，不截断半轮；
5. 保留原始目标、当前指令、未消费引导、人工决定、未解决问题和当前写入/审查引用。

确定性压缩是默认路径，结果必须可复现并可由测试断言。

## 7. LLM 压缩兜底

只有完成第 6.1 节仍超过输入硬上限时，才调用无 Tool、无写权限、无 Saver 的压缩 Agent。它只可处理已完成轮次的对话解释和过程说明，不能处理来源事实、人工决定、草稿 revision 或当前节点输入。

```java
record CompressionRequest(
        String compressionGoal,
        List<CompressibleContextBlock> blocks,
        int targetTokens
) {
}

record CompressionResult(
        String summary,
        List<String> retainedReferenceIds,
        List<String> retainedDecisionIds,
        List<String> retainedQuestionIds
) {
}
```

压缩安全规则：

- 压缩请求本身也必须受预算限制；超长历史按可独立恢复的旧轮次分块压缩；
- `retainedReferenceIds`、`retainedDecisionIds` 和 `retainedQuestionIds` 必须是输入中已有 ID 的子集，校验失败即拒绝结果；
- 压缩摘要不成为事实来源；涉及草稿、证据或当前执行事实时必须根据引用重新读取；
- 同一“上下文块集合 + 目标预算”最多压缩一次，结果持久化为 `conversationSummary` 复用，不能每轮重复压缩；
- 压缩调用失败、结构化输出无效或压缩后仍超限时直接返回 `BLOCKED`，不得递归压缩或无限重试。

## 8. Token 估算与调用日志

部署应优先配置与模型一致的 Tokenizer；该结果为预算判定的权威计数。无法获得精确 Tokenizer 时，使用保守 UTF-8 字节上界和框架近似计数双重保护，日志必须标明估算模式，不能把估算误报为模型实际 usage。

每次模型请求前记录：

```text
agent_context_prepared
runId=45 agent=drafter purpose=FULL_CURATION_DRAFT callSeq=4
mode=DETERMINISTIC estimateMode=MODEL_TOKENIZER
estimatedInputTokens=81720 inputUtf8Bytes=70610
beforeTokens=118420 trimmedTokens=36700
droppedHistoryTurns=2 replacedBodiesWithReferences=6
```

每次模型响应后记录：

```text
agent_model_completed
runId=45 agent=drafter callSeq=4
estimatedInputTokens=81720
actualInputTokens=80642 actualOutputTokens=8526
mode=DETERMINISTIC
```

模型供应商未返回 usage 时，`actualInputTokens` 与 `actualOutputTokens` 记录为 `null`，不得写为 `0`。日志禁止包含 Prompt、Tool 原文、压缩摘要正文、模型原始输出、完整知识正文或完整草稿正文。

## 9. 验收场景

| 场景 | 必须观察到的结果 |
|---|---|
| 连续完整整理后发送闲聊 | Main Agent 只接收会话摘要和角色化历史，不携带旧 Tool 链；输入小于 96k |
| Drafter 写入 | 只接收支持事实、写入指令和基线 revision；不接收 Retriever 原文 |
| 输入超过 72k | 确定性压缩生效，日志有压缩前后 Token、策略和删除数量 |
| 确定性压缩后仍超限 | 只压缩允许的旧对话块；引用和人工决定仍可验证 |
| LLM 压缩输出非法 ID | 压缩结果被拒绝，不进入业务 Agent |
| LLM 压缩后仍超限 | run 进入 `WAITING_FOR_USER`，模型业务调用数不增加 |
| 模型不返回 usage | 日志打印估算值和 `actual*=null`，不伪造零值 |

## 10. 实施顺序

1. 定义输入/输出 record、预算配置和 `ContextReceipt`；
2. 以 Main Agent、Retriever、Drafter、Reviewer 的最小上下文矩阵替换父 `messages` 透传；
3. 实现确定性 Token 估算、72k 预警和 96k 拒绝守卫；
4. 实现确定性裁剪、跨轮角色化历史重建和状态引用替换；
5. 接入每次模型调用的准备/完成日志与测试证据；
6. 最后接入受限 LLM 压缩、ID 校验、一次性缓存和 `WAITING_FOR_USER` 兜底。
