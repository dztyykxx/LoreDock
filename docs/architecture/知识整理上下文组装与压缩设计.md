# 知识整理上下文组装与压缩设计

| 项目 | 内容 |
|---|---|
| 文档状态 | 已确认的设计，已按锁定版框架调用边界修订，待纳入 OpenSpec 实施任务 |
| 适用范围 | 知识整理会话的主 Agent、完整整理子图与专家直调 |
| 目标 | 在不丢失证据、人工决定、草稿修订和恢复语义的前提下，控制模型单次上下文成本 |
| 相关设计 | [知识整理多路 Agent 会话编排设计](./知识整理多路Agent会话编排设计.md) |

## 1. 背景与问题

知识整理任务已经支持跨轮会话、完整整理子图和主 Agent 直调专家。现有 Graph Checkpoint 可以恢复执行，但父 Graph 的 `messages` 使用追加策略，逐轮混入 Agent 原始结构化输出、阶段上下文副本和旧轮历史。后续模型调用因而携带与当前任务无关的旧工作过程。

上下文成本的根因不是 Checkpoint 本身。Checkpoint 是恢复用持久化状态；真正传给模型的是从状态中恢复并交给当前 Agent 的消息。设计必须把“可恢复的完整事实”与“本次模型调用的有限工作视图”分开管理。

## 2. 目标与非目标

### 2.1 目标

- 单次模型调用的总上下文预算默认 128k Token；发送前输入上下文硬上限默认 96k Token；默认保留 24k 输出预算和 8k 协议/估算安全余量；所有阈值均由统一部署配置提供，不绑定模型名称；
- 在每次 Graph/Agent 节点入口按当前 Agent、当前节点和任务重新组装最小语义上下文，不把父 Graph 的历史 `messages` 原样传递；节点内部 ReAct 循环的每次模型调用只执行预算守卫、保守裁剪与日志，不重新组装语义上下文；
- 先使用可验证的确定性裁剪；只有仍无法满足预算时，才使用受限的 LLM 压缩兜底；
- 压缩不得丢失或改写人工确认、证据引用、草稿 `draftId + revision`、未解决问题与恢复所需状态；
- 每次模型调用记录估算与实际输入/输出 Token、压缩方式和压缩效果，且不记录 Prompt 或正文。
- 上下文组装器按“稳定前缀在前、动态后缀在后”的规范顺序生成消息，使模型供应商已提供的前缀缓存尽可能命中；不为此自建 KV Cache 或改变框架请求链路。

### 2.2 非目标

- 不把 Graph Checkpoint 当作模型上下文，也不要求删除其恢复所需的业务状态；
- 不使用 LLM 摘要替代来源事实、草稿正文、人工决定或写入对账；
- 不新增通用 Agent Runtime、消息队列、跨会话长期记忆或新的外部基础设施；
- 不以超限后的盲目重试替代上下文治理。

## 3. 预算配置与状态边界

```text
128k：单次模型调用总窗口默认值
├─ 96k：单次调用发送前输入硬上限
├─ 24k：单次调用模型输出预留
└─  8k：单次调用协议与估算安全余量

72k：节点入口开始确定性压缩
64k：节点入口压缩目标
96k：任意模型调用发送前的输入硬上限
```

阈值采用统一配置，不根据模型名称建立分支。切换模型时由部署者同步调整配置；系统启动时只校验阈值之间的约束，不尝试猜测模型窗口：

| 配置项 | 环境变量 | 默认值 | 语义 |
|---|---|---:|---|
| `max-window-tokens` | `LOREDOCK_AGENT_CONTEXT_MAX_WINDOW_TOKENS` | 128000 | 单次模型调用的总窗口 |
| `max-input-tokens` | `LOREDOCK_AGENT_CONTEXT_MAX_INPUT_TOKENS` | 96000 | 单次调用输入硬上限 |
| `output-reserve-tokens` | `LOREDOCK_AGENT_CONTEXT_OUTPUT_RESERVE_TOKENS` | 24000 | 单次调用输出预留 |
| `safety-reserve-tokens` | `LOREDOCK_AGENT_CONTEXT_SAFETY_RESERVE_TOKENS` | 8000 | 协议与估算误差预留 |
| `compression-trigger-tokens` | `LOREDOCK_AGENT_CONTEXT_COMPRESSION_TRIGGER_TOKENS` | 72000 | 节点入口开始确定性压缩 |
| `compression-target-tokens` | `LOREDOCK_AGENT_CONTEXT_COMPRESSION_TARGET_TOKENS` | 64000 | 节点入口压缩后的目标 |
| `max-run-input-tokens` | `LOREDOCK_AGENT_CONTEXT_MAX_RUN_INPUT_TOKENS` | 512000 | 一个 run 内全部模型调用的累计输入上限 |
| `max-llm-compression-calls` | `LOREDOCK_AGENT_CONTEXT_MAX_LLM_COMPRESSION_CALLS` | 1 | 一个 run 内 LLM 压缩兜底调用上限 |
| `max-rolling-summary-generations` | `LOREDOCK_AGENT_CONTEXT_MAX_ROLLING_SUMMARY_GENERATIONS` | 3 | 连续滚动摘要达到该代数后，下次压缩从原始消息低频重建 |

配置必须满足：`compressionTarget < compressionTrigger < maxInput`，`maxInput + outputReserve + safetyReserve <= maxWindow`，且 `maxRunInputTokens`、`maxLlmCompressionCalls`、`maxRollingSummaryGenerations` 均大于 0。128k 只约束一次模型调用；ReAct 循环内多次调用的累计成本由 `max-run-input-tokens` 和既有 `curation-max-model-calls` 共同限制。

上下文有两种所有者：

| 内容 | 所有者 | 是否直接进入模型 |
|---|---|---|
| `currentInstruction`、`stage`、`nextNode`、重试次数、草稿 revision、来源引用 | Graph State / Checkpoint | 否，按当前节点选择性投影 |
| 完整 Tool 回执、公开事件、历史消息 | 数据库审计事实 | 否，按需读取或缩短投影 |
| 系统规则、当前指令、必要事实、人工决定、当前工作窗口 | Context Assembly | 是 |

Checkpoint 保存完整的可恢复事实；模型只接收一次调用所需的 `PreparedModelContext`。模型上下文不是跨轮事实的权威来源。父 Graph 的 `messages` 只作为“下一 Agent 节点的一次性输入缓冲区”，不再承担保存当前用户指令或跨节点历史的职责；`currentInstruction` 必须在进入任何 Agent 前以 REPLACE state 键单独保存。

输入模型禁止接收父 Graph 的原始 `messages`、完整 Tool 回执或旧 Agent JSON。文档、证据和草稿正文用 `documentId`、`draftId`、`revision`、`blockId` 等稳定引用表达；需要正文时由当前 Agent 通过受限业务 Tool 重读。

`pendingAdministratorGuidance` 对应现有“管理员追加指导”，不是新增一套消息：它来源于恢复接口写入当前 run 的 `USER` 消息，并同步投影到 `currentInstruction`。只有恢复断点的目标节点直接接收这段原始指导；该节点成功发起首个模型请求后记录已应用，后续节点只接收由结构化结果归纳出的任务要求，避免原始指导在全图重复注入。请求未发出、预算守卫拒绝或节点失败时仍保持 pending，下一次恢复可以再次注入。

## 5. 节点级最小上下文与注入边界

### 5.1 缓存友好的消息顺序

`PreparedModelContext.messages` 不是只要语义正确即可；同一 `agentNode × purpose` 的可复用内容必须以确定性顺序位于前缀。Context Assembly 对所有完整图节点遵守以下消息层次：

```text
框架固定层（由 ReactAgent 提供，组装器不得改变）
  1. Agent 固定 system instruction
  2. 固定 Tool 定义及其顺序

Context Assembly 稳定前缀（相同输入必须字节级等价）
  3. agentNode、purpose、Agent 定义版本、项目/分支/权限范围
  4. 已提交且未失效的 conversationSummary
  5. 已排序的稳定引用（sourceRef、draftId + revision、decisionId）

Context Assembly 动态后缀
  6. 当前节点任务和当前用户指令
  7. 本轮结构化结果、pending 管理员指导、validationError、retry 信息
  8. 节点内部 ReAct 新增的 Tool Call / Tool Result
```

“字节级等价”要求：引用按稳定 ID 排序；字段以固定 Schema 序列化；不把 `runId`、时间戳、日志 receipt、随机 ID、用量或异常堆栈写入模型消息；无值字段不输出占位文本。摘要仅在内容或版本实际变化时更新，不能每轮附加“本轮摘要”造成前缀变化。

该规则只优化输入成本与延迟，不放宽 Token 预算：缓存命中的输入仍计入单次模型上下文窗口。锁定版 Graph/ReactAgent 不管理模型 KV Cache；是否命中由模型供应商决定，LoreDock 只保证可控消息前缀尽量稳定。

| `agentNode × purpose` | 允许读取的权威字段 | 禁止继承 |
|---|---|---|
| Main / `CHAT` | `conversationSummary`、最近角色化轮次、当前用户消息、已确认决定、任务状态摘要 | `retrievalResult`/`draftResult`/`reviewResult` 原文、完整 Tool 链 |
| Main / `DIRECT_*` | CHAT 内容 + 当前专家任务需要的 `sourceRef`、`draftId + revision`、当前指令；请求中的 `agentNode` 仍为 `MAIN_AGENT` | 专家旧 Tool 历史、完整 Graph 工作消息 |
| Main / `FULL_CURATION_REPORT` | 当前 `reviewResult.summary`、本轮草稿引用、未解决问题、人工决定 | Retriever/Drafter Tool 原文和旧轮报告 |
| Retriever / `FULL_CURATION_RETRIEVE` | `goal`、固定输入引用、项目范围、与目标相关的人工决定；若它是恢复目标节点，再加入 pending 管理员指导 | 旧 `retrievalResult`、草稿/审查过程全文 |
| Coordinator / `FULL_CURATION_DECIDE` | `goal`、规范化 `retrievalResult`、人工决定、未解决问题；若它是恢复目标节点，再加入 pending 管理员指导 | Retriever Tool 原文、旧轮汇报 |
| Coordinator / `FULL_CURATION_FINISH` | `goal`、规范化 `reviewResult`、人工决定、未解决问题 + 显式 FINISH 标记；若它是恢复目标节点，再加入 pending 管理员指导 | 旧轮汇报、检索过程 |
| Drafter / `FULL_CURATION_DRAFT` | SUPPORTED 事实及引用、`coordinationResult.draftInstruction`、`draftId + baseRevision`；REVISE 返工入口额外接收本轮 `ReviewFinding`；若它是恢复目标节点，再加入 pending 管理员指导 | 完整检索链、旧 Reviewer 结论、无关会话 |
| Reviewer / `FULL_CURATION_REVIEW` | SUPPORTED 事实及引用、写入指令、`draftResult` 中待审 `draftId + revision`；若它是恢复目标节点，再加入 pending 管理员指导 | Drafter 完整 Tool 历史、旧会话闲聊 |
| 任一 Agent / `REPAIR` | 当前节点的最小输入、`lastValidatedNode`、有界 `validationError`、当前候选引用 | 全部旧候选和无关历史 |

完整子图的专家节点使用 `asNode(true, false)`，因此每个 Agent 前必须有一个确定性的上下文准备节点。准备节点调用 `ContextAssemblyService`，把完整的 `PreparedModelContext.messages` 写入父 Graph 的一次性 `messages` 缓冲区，再由 `asNode(true, false)` 复制为本次子图初始消息视图。父 Graph 的 `messages` 目标合并策略为 REPLACE；Agent 自身子图内部由框架维护的 `messages` 仍保持 APPEND，使同一节点内的 Tool Call、Tool Result 与后续 AssistantMessage 连续累积。不得把父 Graph 和 Agent 子图的两种 `messages` 策略混为一谈。

**子 Agent 不继承历史消息**：无论子图节点还是 AgentTool 直调，专家模型调用只见当前准备节点的最小消息视图；跨节点、跨轮历史一律由父 Graph 结构化 state 与 `conversationSummary` 承担，专家不得从父图 `messages` 缓冲区或历史轮次恢复旧上下文（直调路径由框架保证：`AgentTool` 以 `[instruction, UserMessage(actualInput)]` 在新建子线程 state 中执行，见本节直调边界）。

这项调整必须同时完成三个改动，不能只把现有父 Graph 的 APPEND 全局改成 REPLACE：

1. 在进入 Main、Retriever、Coordinator、Drafter、Reviewer 前统一经过对应准备节点；
2. 本轮用户输入先写入独立的 `currentInstruction` REPLACE state 键，`TURN_FINISH` 从该键生成本轮历史（用户侧取 `currentInstruction`，主回复取 `mainTurnResult.summary`、`recoveryInfo` 等结构化 REPLACE 键，不扫描可能被预算守卫裁剪的 `messages` 缓冲区），不再从 `messages` 追溯本轮消息；
3. 阶段推进节点不再增量追加一条提示，而是由下一准备节点根据结构化 state 重新生成完整消息视图；生成的视图必须保留与现有 Agent Spec 约定一致的显式阶段标记文本（如 `【当前阶段：DECIDE】`/`【当前阶段：FINISH】`、完整整理完成标记），维持 coordinator.md 既有的“以输入中最后出现的标记为准、无标记则视为 START”语义；标记格式变更时必须同步修订对应 spec 指令并说明依据，防止调度 Agent 重复开场白等已修复问题回归。

专家直调是另一条边界：锁定版 `AgentTool` 固定以 `[AgentInstructionMessage(instruction), UserMessage(actualInput)]` 创建子 Agent 新 state，没有专家侧的语义上下文注入点。因此 `DIRECT_RETRIEVE`、`DIRECT_DRAFT`、`DIRECT_REVIEW` 的语义组装发生在父侧 Main Agent；载体是 Main Agent 生成的 `AgentTool` `actualInput` 文本和专家自身 instruction。专家侧只安装每次调用前的预算守卫与日志，不尝试读取父会话 state。若未来要求服务端确定性丰富 `actualInput`，必须单独评估薄 ToolCallback 适配，不能假定框架 `AgentTool` 已提供该能力。

直调 Drafter 时，实际传递链路示例：

```text
ContextAssemblyService -> Main Agent 初始消息：
  当前指令=“只调整草稿 14 的错误处理章节”
  当前引用=draftId=14, revision=3
  相关决定=decision-8

Main Agent -> AgentTool 工具参数：
  {"input":"任务：调整错误处理章节；draftId=14；baseRevision=3；decisionIds=[decision-8]"}

Drafter 子 Agent 实际可见：
  [AgentInstructionMessage(Drafter 固定职责),
   UserMessage(上述 actualInput)]
```

它不会看到 Main Agent 的旧对话、父 Graph State 或其他专家历史；需要草稿正文时再通过 Drafter 已授权的业务 Tool 按 `draftId + revision` 读取。

例如 `FULL_CURATION_DRAFT` 的模型消息可被组装为：

```text
系统规则：Drafter 的固定职责与写入边界

【当前任务】
将草稿 7 和草稿 9 合并为一份文档

【人工已确认决定】
- SCENARIO_ID_CONFLICT 以已发布规则为准

【允许写入的事实】
- fact-1：…… sourceRef=[draft:7, knowledge:20]
- fact-2：…… sourceRef=[draft:9, knowledge:16]

【写入要求】
- 目录：项目资料/02-导入导出
- 当前草稿基线：draftId=14, revision=1
```

## 6. 内部核心流程

```text
节点入口：ContextAssemblyService.assemble(request)
  │
  ├─ 1. 根据 agentNode + purpose 选择允许的语义块
  ├─ 2. 按 §5.1 的稳定前缀→动态后缀顺序序列化规则、当前任务、人工决定、事实、引用和工作窗口
  ├─ 3. 使用 Token 估算器计算候选输入预算
  ├─ 4. <= compressionTrigger：返回 FULL
  ├─ 5. > compressionTrigger：先执行确定性压缩并重新组装
  ├─ 6. 确定性压缩后仍 > maxInput：调用 LLM 压缩可压缩块
  └─ 7. LLM 压缩后仍 > maxInput：返回 BLOCKED

节点内部每次模型调用前：ContextBudgetGuardHook.beforeModel(messages)
  │
  ├─ 1. 对当前完整消息链估算 Token 并记录调用前日志
  ├─ 2. <= maxInput 且 run 累计预算未耗尽：允许调用
  ├─ 3. > maxInput：只清理最旧且已经闭合的 Tool Call/Result 组
  ├─ 4. 保护最新未闭合 Tool Call、匹配 Tool Result 和当前任务消息
  ├─ 5. 清理后仍超单次上限：抛出 ContextLimitExceeded，不发送模型请求
  └─ 6. run 累计预算耗尽：抛出 ContextRunBudgetExceeded，不通过裁剪继续调用
```

`BLOCKED` 映射到 `WAITING_FOR_USER`，保留当前语义稳定 Checkpoint，并提示管理员缩小草稿范围、指定目录或拆分任务。它不是模型解析失败，不进入同输入重试回路。

锁定版框架提供 `MessagesModelHook` 的 `BEFORE_MODEL` 位置，每次 ReAct 模型调用前都会执行，因此预算守卫不需要改写 `StreamingModelInterceptor`。Hook 只做计数、日志和保持 Tool 消息组完整性的保守裁剪，不从数据库重新组装语义上下文，也不在节点内部调用 LLM 压缩，以免破坏当前 Tool 链连续性或形成递归模型调用。守卫 Hook 加入全部 5 个 Agent（主 Agent 与 Retriever/Coordinator/Drafter/Reviewer）的构建 hooks，与既有 `ModelCallLimitHook`/`ToolCallLimitHook` 同处注册；压缩调用由组装服务在发起前直接校验预算，不经守卫 Hook。

### 6.1 确定性压缩顺序

1. 移除旧 Tool 调用参数与 Tool 原文，保留 `toolCallId`、摘要、来源引用和截断标记；
2. 移除已完成节点的原始结构化 JSON，只保留已规范化的状态字段；
3. 用 `documentId`、`draftId`、`revision`、`blockId` 替换正文；
4. 按完整 User/Assistant 轮次从旧到新删除会话历史，不截断半轮；
5. 保留原始目标、当前指令、仅供恢复目标节点使用的 pending 管理员指导、人工决定、未解决问题和当前写入/审查引用。

确定性压缩只在输入估算位于压缩触发阈值与输入硬上限之间时执行；超过输入硬上限时进入受限 LLM 压缩兜底。压缩结果必须可复现并可由测试断言。

## 7. 旧轮读取源与压缩输入边界

跨轮对话的权威来源是 `knowledge_task_message`，按 `conversation_id`、`created_at`、`id` 读取真实的 `USER` 与最终 `COORDINATOR_AGENT` 消息。最终回复还必须满足 `subject_name = 当前会话使用的 agentName/targetSkill`，从而排除同为 `COORDINATOR_AGENT` 的“公开行动摘要”。Graph State 中的 `conversationHistory` 只是最近轮次缓存，不是完整历史。`knowledge_task_event` 与 `agent_run_event` 用于执行观测，`knowledge_tool_invocation` 用于 Tool 对账和审计，三者都不能自动当作旧轮对话喂给压缩模型。

旧轮压缩输入按以下边界取得：

1. `conversationHistory` 保留最近配置数量的完整轮次，供正常续聊；
2. 需要 LLM 压缩时，通过 `KnowledgeTaskMessageMapper` 读取最近窗口之前的 User/最终回复消息；
3. 过滤 `SUB_AGENT`、`TOOL`、阶段事件、原始候选和公开执行摘要，只压缩真实对话；
4. 人工决定、当前仍 pending 的管理员指导、未解决问题和草稿引用从结构化 Graph State/业务表合并，不能从摘要文本反推。

压缩结果保存到父 Graph State 的 REPLACE 字段：

```text
conversationSummary
summaryThroughMessageId
summarySourceDigest
summarySchemaVersion
summaryGeneration
```

### 7.1 滚动摘要与低频重建

摘要按“已提交摘要 + 摘要之后的增量会话”滚动，而不是每轮再次读取并压缩完整历史：

```text
M1..M40                        -> S40, summaryThroughMessageId=40, generation=1
S40 + M41..M55                 -> S55, summaryThroughMessageId=55, generation=2
S55 + M56..M70                 -> S70, summaryThroughMessageId=70, generation=3
```

每次滚动只处理完整 User/最终回复轮次。摘要只保存指代所需的目标、已确认决定、未决问题和稳定引用；知识正文、草稿正文、Tool 回执和实际执行事实不进入摘要，仍以业务表和受限 Tool 为准。

当 `summaryGeneration` 达到 `max-rolling-summary-generations` 后，下一次确有压缩需要时，从 `knowledge_task_message` 的原始已过滤消息低频重建摘要，并把 generation 重置为 1，避免无限以旧摘要再摘要而积累语义漂移。重建也受单次输入和 `max-llm-compression-calls` 预算限制；原始轮次无法组成有界批次时返回 `BLOCKED`，由管理员缩小会话范围或拆分任务，不隐式扩大模型调用次数。

### 7.2 Checkpoint 只保留最新稳定快照

业务数据库保存全量且长期可审计的事实：`knowledge_task_message`、`agent_run`、任务/运行事件、草稿与 Tool 对账记录。Graph Checkpoint 不承担审计或版本回放，只服务于“从当前断点继续”。

同一 `conversationId` 的全部 run 共享一个稳定 `threadId`，该 thread 只保留一份最新的、已经成功提交的 Graph State：`nextNode`、当前结构化工作状态、`conversationSummary` 和恢复信息。锁定版 `PostgresSaver` 在已有 `checkpointId` 时会在同一事务内删除旧记录、插入新记录，正常推进不形成 Checkpoint 历史链；`parent_checkpoint_id` 不作为 LoreDock 的版本恢复能力使用。

这些摘要字段不是 JVM 内存缓存。上下文准备节点成功返回后，由现有 `PostgresSaver` 随这一份父 Graph Checkpoint 持久化；同一 `threadId` 在进程重启、暂停恢复和下一轮对话中恢复 state 时可直接复用，不需要重新调用压缩模型。摘要属于可重建的派生缓存，不新增独立摘要表。

持久化提交边界是上下文准备节点完成：如果进程在 LLM 压缩期间、节点尚未返回前崩溃，本次摘要尚未进入 Checkpoint，恢复时最多重新压缩一次；节点已成功完成后崩溃则直接读取已提交摘要。实现必须先校验压缩结果和引用 ID，再把摘要字段作为同一次节点 state 更新提交，禁止先保存未校验摘要。

`summaryThroughMessageId` 表示摘要覆盖到哪条不可变业务消息；`summarySourceDigest` 只计算截至该 ID 的已过滤消息，因此新消息只作为未摘要增量，不使旧摘要失效。被摘要范围内的消息发生异常修改，或压缩规则、摘要 Schema、Agent 定义版本变化时，digest/version 不匹配，摘要失效并根据 `knowledge_task_message` 重建。无会话级 Checkpoint、Checkpoint 已按兼容策略废弃或摘要字段校验失败时，也从该表重建，不依赖已经被 TURN_FINISH 丢弃的 state 历史。

## 8. LLM 压缩兜底

只有完成第 6.1 节仍超过输入硬上限时，才由 `ContextAssemblyService` 内部发起一次受限的压缩模型调用：直接使用现有 ChatModel 的结构化输出能力（`json_schema`/JSON 输出 + Jackson 反序列化），不构建 ReactAgent、无 Agent Spec、不注册任何 Tool、不配置 Saver、不加入父图节点。它只可处理已完成轮次的对话解释和过程说明，不能处理来源事实、人工决定、草稿 revision 或当前节点输入。

```java
record CompressionRequest(
        String compressionGoal,
        List<CompressibleContextBlock> blocks,
        int targetTokens
) {
}

record CompressionResult(
        String summary,
        List<String> retainedReferenceIds,
        List<String> retainedDecisionIds,
        List<String> retainedQuestionIds
) {
}
```

压缩安全规则：

- 压缩只发生在节点入口；压缩请求本身也必须受预算限制，按 `knowledge_task_message` 中完整旧轮次选择一个有界批次，不截断半轮；超出 `max-llm-compression-calls` 后仍无法形成目标上下文则返回 `BLOCKED`，不递归压缩；
- `retainedReferenceIds`、`retainedDecisionIds` 和 `retainedQuestionIds` 必须是输入中已有 ID 的子集，校验失败即拒绝结果；
- 压缩摘要不成为事实来源；涉及草稿、证据或当前执行事实时必须根据引用重新读取；
- 同一 `summarySourceDigest + summarySchemaVersion + targetTokens` 最多压缩一次；滚动压缩的输入为已提交摘要与它之后的完整增量轮次，结果更新 `conversationSummary`、覆盖消息 ID 和 generation，不能每轮重复压缩；
- 压缩调用失败、结构化输出无效或压缩后仍超限时直接返回 `BLOCKED`，不得递归压缩或无限重试。

## 9. Token 估算、预算守卫与调用日志

部署应优先配置与模型一致的 Tokenizer；该结果为预算判定的权威计数。无法获得精确 Tokenizer 时，使用保守 UTF-8 字节上界和框架近似计数双重保护，日志必须标明估算模式，不能把估算误报为模型实际 usage。

节点入口组装完成后记录 `agent_context_assembled`；ReAct 循环每次模型请求前由 `ContextBudgetGuardHook` 记录 `agent_model_context_checked`：

```text
agent_model_context_checked
runId=45 agent=drafter purpose=FULL_CURATION_DRAFT callSeq=4
mode=DETERMINISTIC estimateMode=MODEL_TOKENIZER
estimatedInputTokens=81720 inputUtf8Bytes=70610
beforeTokens=88420 trimmedTokens=6700
droppedHistoryTurns=2 replacedBodiesWithReferences=6
```

每次模型响应后记录：

```text
agent_model_completed
runId=45 agent=drafter callSeq=4
estimatedInputTokens=81720
actualInputTokens=80642 actualOutputTokens=8526
mode=DETERMINISTIC
```

模型供应商未返回 usage 时，`actualInputTokens` 与 `actualOutputTokens` 记录为 `null`，不得写为 `0`。LLM 压缩调用也按普通模型调用记录，`agent=context_compressor`（仅作为调用点统计标识，压缩调用不是 Agent 运行）。日志禁止包含 Prompt、Tool 原文、压缩摘要正文、模型原始输出、完整知识正文或完整草稿正文。

## 10. 验收场景

| 场景 | 必须观察到的结果 |
|---|---|
| 连续完整整理后发送闲聊 | Main Agent 只接收会话摘要和角色化历史，不携带旧 Tool 链；输入小于 96k |
| Drafter 写入 | 只接收支持事实、写入指令和基线 revision；不接收 Retriever 原文 |
| 节点入口输入超过压缩阈值 | `estimateMode=MODEL_TOKENIZER` 时按 Token 阈值触发确定性压缩，日志有压缩前后 Token、策略和删除数量 |
| 节点内部 Tool 结果使后续调用超限 | `BEFORE_MODEL` 守卫清理最旧闭合 Tool 组；最新 Tool Call/Result 配对完整 |
| 专家直调 | 父侧 Main Agent 通过 `actualInput` 传递专家任务；子 Agent 不读取父 Graph State |
| 旧轮已从 state 裁剪 | 压缩输入从 `knowledge_task_message` 读取，摘要记录覆盖消息 ID 和版本 |
| 确定性压缩后仍超限 | 只压缩允许的旧对话块；引用和人工决定仍可验证 |
| LLM 压缩输出非法 ID | 压缩结果被拒绝，不进入业务 Agent |
| LLM 压缩后仍超限 | run 进入 `WAITING_FOR_USER`，模型业务调用数不增加 |
| 模型不返回 usage | 日志打印估算值和 `actual*=null`，不伪造零值 |

## 11. 实施顺序

1. 定义输入/输出 record、统一预算配置、启动约束校验和 `ContextReceipt`；
2. 增加 `currentInstruction` state 和各 Agent 的上下文准备节点；将父 Graph `messages` 改为 REPLACE 一次性缓冲区，并保持 Agent 子图内部 `messages` APPEND；直调路径只在父侧组装 `AgentTool actualInput`；
3. 实现确定性 Token 估算、节点入口压缩与 `ContextBudgetGuardHook` 每次调用前的硬上限守卫；
4. 实现确定性裁剪、跨轮角色化历史重建、旧轮数据库读取和状态引用替换；
5. 接入节点入口日志、每次模型调用的请求/完成日志与 run 累计 Token 门禁；
6. 最后接入仅在节点入口运行的受限 LLM 压缩、ID 校验、摘要版本缓存和 `WAITING_FOR_USER` 兜底。
