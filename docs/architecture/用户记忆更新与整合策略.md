## 1. 背景与问题

### 1.1 触发案例（2026-08-30）

知识整理会话中再次沉淀"汇报格式必须列具体细节"的偏好。服务端判断链判定其与既有记忆**语义重复**，返回 `SKIP_DUPLICATE`，回执为"与既有记忆语义重复，跳过且不改动既有记忆"。

问题不只是这次写入被丢弃，而是结构性的：当既有记忆表述不完整（本次新增了"每项附推荐方案"的表述更全），或者用户偏好确实变更（旧"汇总格式 X"→新"汇总格式 Y"），现有路径都无法把新信息落到存储里。

### 1.2 当前实现

写入链（`MemoryServiceImpl.acceptWrite` `backend/src/main/java/io/github/loredock/memory/service/MemoryServiceImpl.java:179-229`）：

| 步骤 | 机制 | 位置 |
|---|---|---|
| ① 候选校验 | 1~3 条、字段长度校验 | `MemoryServiceImpl.java:321-333` |
| ② run 预算 | 单 run 累计新写 ≥10 条拒写 | `MemoryServiceImpl.java:186-193` |
| ③ 相近召回 `recallNear` | **关键词 LIKE 粗筛**（同分类或 title/summary/content 含候选词元），上限 50 条，按 `updated_at DESC` | `MemoryServiceImpl.java:270-308` |
| ④ LLM 裁决 | 单次 ChatModel 调用 `judge`，输出 `CREATED` / `SKIP_DUPLICATE` / `CONFLICT_CREATED` / `SKIP_NOT_WORTH` | `MemoryWriteJudger.java:79-120` |
| ⑤ 分流 | `CREATED`/`CONFLICT_CREATED` 新插入；`SKIP_DUPLICATE`/`SKIP_NOT_WORTH` 不写 | `MemoryServiceImpl.java:213-227` |

判断链关键规则原文（`MemoryWriteJudger.java:112-114`）：

```
- 与既存记忆表达同一偏好（同分类、语义相同、异词表达）→ SKIP_DUPLICATE，不得改动既存记忆；
- 与既存某条记忆语义冲突（同类目但内容相反/不一致...）→ CONFLICT_CREATED，候选仍须写入，冲突双方同时保留 ACTIVE；
```

### 1.3 问题归纳

- **P1 重复即丢内容**：`SKIP_DUPLICATE` 不改动既有记忆，新表述中的增量信息（更完整的措辞、新约束）被整体丢弃；"重复必须在下次遇到时以最新为准"无法实现。
- **P2 冲突双写检索两难**：`CONFLICT_CREATED` 写入两条同槽位 ACTIVE 记忆，检索端只能靠 `main_agent.md:11-18` 的"按当前任务语义择优"，冲突是被推给模型解决的，而不是在存储层消解；既无新旧之分，也无失效标记，无法回答"旧值是什么"。
- **P3 无版本/审计**：`user_memory` 无 version、无 supersede 关系、无历史表（`V10__add_user_memory.sql`），一旦语义上出现"更正"，旧约定无法恢复或追溯。
- **P4 召回无语义层**：`recallNear` 是关键词 LIKE，语义判断全部压在单次 LLM 调用上；业界同类的语义去重普遍有嵌入层兜底（本仓库知识检索已有嵌入调研基础，见 `docs/research/T5知识检索Embedding依赖核验.md`）。

## 2. 业界调研：记忆管理怎么处理新增/重复/合并/冲突

### 2.1 通用框架（Hindsight / Vectorize《The Consolidation Problem in Agent Memory》）

记忆整合是四个杠杆：

| 杠杆 | 内容 | 代表性实践 |
|---|---|---|
| Importance | 什么值得成为记忆 | 生成式智能体（Park et al. 2023）逐观察 1-10 打分；Mem0/LangMem 用"事实抽取"本身作为过滤 |
| **Merge** | 同一实体/同一事实如何统一为一条 | 实体解析（写时而非读时）+ 事实去重 + **冲突处理**（见 2.2） |
| Decay | 置信度随时间衰减 | linear / exponential / step；Zep 的 Graphiti 每条边带 `valid_at`/`expired_at`/`invalid_at` |
| Eviction | 何时彻底退出 | 仅 GDPR/安全删除应硬删除；其余用归档分层（Letta 核心/归档记忆）或 TTL |

### 2.2 冲突处理的三种策略（Merge 的核心决策）

1. **Recency wins**：新事实取代旧事实。适合状态类（"用 Postgres"→"用 MySQL"）；对稳定属性（被错误重复断言覆盖）有误伤风险。
2. **Source wins**：可信来源优先。适合有显式 provenance 的系统。
3. **Confidence wins**：每条事实带置信分，最高胜。适合抽取概率性来源，需校准防"确定性跑飞"。

业界共识：**"recency-wins + 显式失效化（explicit invalidation）"是最稳妥的默认**——新值写入、旧值标记失效而非删除。旧状态可审计可恢复，当前状态对检索无歧义。

### 2.3 写入时机：增量式 vs 批次式

- **增量式（hot path）**：写入瞬间就判断合并——Mem0 的 `ADD/UPDATE/DELETE/NOOP` 操作符、Zep 写时边失效化、LangMem 的对话内 memory tool。
- **批次式（background / sleep time）**：后台异步整合存量——Letta 的 sleep-time compute、LangMem 的 background manager、Anthropic 的 **Dreams**。LangMem 与 Letta 都是两条路线并用。

### 2.4 各家对比

| 系统 | 写入模式 | 重复怎么处理 | 冲突怎么处理 | 审计 |
|---|---|---|---|---|
| Mem0（arXiv 2504.19413） | 增量 ops：检索 top-10 相似 → LLM 选 `ADD/UPDATE/DELETE/NOOP` | UPDATE 合并同类项 | 矛盾检测；graph 版将关系标记 `invalid/obsolete` 而非物理删除 | 弱——论文认可 `DELETE` 为硬删除、丢历史 |
| Zep / Graphiti（arXiv 2501.13956） | 增量 + 实体解析 | 同实体对间边去重；实体 resolve 合并 | **双时态失效化**：`tvalid/tinvalid`（事实有效期）+ `t'created/t'expired`（审计时间），新旧并存 | 最强（可答"搬家前地址是什么"） |
| LangMem（LangChain） | 双轨：hot-path 工具 + 后台 memory manager | 工具与后台自动 extract / consolidate / update | 后台 consolidate 统一消解 | BaseStore 支持可回溯 |
| Letta / MemGPT | LLM 自编辑 memory blocks + sleep-time compute | 模型重写块 | 睡眠时计算合并矛盾 | 核心/归档分层 |
| Claude Code auto memory | 热路径写入 `MEMORY.md` | **内置规则：若已有记忆覆盖同一事实，更新既有文件而非创建重复** | 冲突时当轮明确指令优先（本项目 `main_agent.md:11-18` 已采用此规则） | 200 行上限触发提示合并 |
| Anthropic Dreams（Managed Agents，2026-04 预览） | **批次异步**：现状描述与本案 P1 一字不差——"多会话后 store 累积重复、矛盾、过时条目" | **duplicates merged** | **stale/矛盾的 entry 替换为最新值**；输出全新 store，**输入 store 从不修改**，人工审核后决定是否采用 | 输出隔离，天然可审 |
| 学术基线（Generative Agents / A-Mem / MemoryBank） | 增量 | 重要性打分 + 时间权重 | 弱 | 弱 |

**对本案最直接的对照**：Claude Code 原生语义就是"重复→更新既有条目（以最新为准）"；本项目抄了它的 judger，却把重复行为改成了"跳过不改动"，与原生行为不一致。用户期望"重复时以最新为准"与业界主流一致，不是特例。

### 2.5 一个必须正视的风险

recency-wins 对**状态类**事实完全正确，对**稳定属性**（"这条规则长期有效"）如果被某轮错误断言覆盖，会越改越错。缓解手段不是放弃"以最新为准"：

- 只让 LLM 判定为**同一语义槽位的可用更新**才执行 supersede（现有 judger 已是同槽位语义判定的瓶颈）；
- 旧值失效化后仍保留、可人工恢复（方案 B 的审计即此防线）。

## 3. 方案设计

### 3.1 目标与非目标

目标：

- 语义重复写入时，以最新候选**合并更新**既有记忆（保留既有 id/source/use_count/created_at，title/summary/content 以最新为准）；
- 同一槽位偏好变更写入时，新值**取代**旧值，旧值失效保留（不双写同槽位 ACTIVE，不硬删除）；
- 更新可审计：管理界面能看到"被谁在什么时候替换成什么"；
- 改动贴合现有判断链，不引入新的 LLM 调用次数，不做架构重构。

非目标（本阶段明确不做，列作二期后置）：

- 不做批次整合/后台"记忆整理"任务（方案 C）；
- 不做嵌入向量化语义召回（P4，二期）；
- 不做 decay/TTL/自动 eviction（与 OpenSpec `user-memory` 基线 Non-Goal 一致）；
- 不做记忆多版本历史链（只留"当前版 + 被替代版"一层）。

### 3.2 方案 A：新增 `UPDATED` outcome（最小改动）

- `MemoryWriteOutcome` 新增 `UPDATED`；`MemoryWriteJudger` 语义重复时输出 `UPDATED` + `targetId`（`conflictsWith` 已是"既有记忆 id 数组"的现成通道，可复用为被更新条目 id）+ `summary`；
- `MemoryServiceImpl.acceptWrite` 分流（`:217-226`）新增 `UPDATED` 分支 → 调持久化更新（复用现有 `update` 的前半能力，或新增 `updateFromWrite`）：title/summary/content 以新候选为准，保留 id/source/use_count/created_at，刷新 `updated_at/updated_by`；
- 保留窄化的 `SKIP_DUPLICATE`：仅"完全同义转述、新候选为零信息增量"时跳过（降低重复 LLM 记忆噪音；也保留 SKIP_NOT_WORTH 语义）；
- `memory_write` verdict 与回执消息同步改文案（"已更新既有记忆 #…"）；
- 行为反转为"重复=更新"，需同步修改：`openspec/changes/user-memory/specs/user-memory/spec.md:63-66`（"重复偏好不覆盖只跳过"场景）、`design.md:31`（判断链结论）、`MemoryServiceIT.java:273-297`（断言"id=500 未被改动"需改为断言"id=500 已被更新为最新内容"）。

**代价**：误覆盖（2.5 风险）无回收路径——旧内容被覆盖即丢失（数据库无版本）——这是方案 A 唯一但实质的缺陷。

### 3.3 方案 B：方案 A + 失效化审计（推荐）

在 A 之上保留"更新前是什么"，两条路线存在一个不可兼得的权衡：**同 id 稳定**与**零新建存储**只能二选一。

| 选择 | 改动 | 优点 | 缺点 |
|---|---|---|---|
| B1 双行引用链 | `V11__add_user_memory_supersede.sql`：主表加 `superseded_by BIGINT NULL` + `superseded_at`；更新 = 旧行打标指向新行、新候选另起一行 | 仅 1 列迁移；"当前值 = `superseded_by IS NULL` 且 ACTIVE"；旧内容完整留原行 | **记忆 id 漂移**：同一条偏好两次更新产生三行 id，主 Agent 已引用的记忆 id、`use_count` 断链，预载快照与人工管理心智都要改 |
| B2 主表原地更新 + 历史表（推荐） | `V11__add_user_memory_revision.sql`：新增 `user_memory_revision（memory_id, revision, title/summary/content 快照, superseded_at, updated_by, reason）`；更新前先把旧版 INSERT 进历史表 | 主表同 id 原地更新，检索/工具/预载快照逻辑**零改动**；审计与回滚完整，可多代演进 | 每写 1 行多插 1 行；管理界面查看历史需一次 join |

推荐 **B2**：本项目记忆是"记忆卡"模型（主 Agent 以 id 引用、快照预载），id 稳定性是关键约束——B1 的 id 漂移会波及检索、预载、引用所有面，省的不只是一行迁移成本。B1 只在不接受历史表时才退而求其次。

B2 语义规则：

- 更新（`UPDATED`）时：主表同 id 原地覆盖（title/summary/content 以最新候选为准，保留 id/source/use_count/created_at，刷新 `updated_at/updated_by`），**更新前**旧值序列化入 `user_memory_revision`（revision +1）；
- 检索/工具/预载快照：语义不变，无需任何过滤改动；
- 管理界面（人工 REST 详情）展示历史区与每次更新的 `updated_at/updated_by/reason`，支持按历史快照人工回滚（回滚 = 把快照写回主表并再记一行 revision）。

**注意**：V10 迁移中 `ck_user_memory_status` CHECK 只允许 `ACTIVE/DISABLED`（`V10__add_user_memory.sql:36`）。**不新增 `SUPERSEDED` 枚举值**：被替代由 revision 历史表达即可（主表永远只有当前 ACTIVE 值），避免"DISABLED（人工停用）"与"SUPERSEDED（自动替代）"两枚状态语义交叉。

### 3.4 方案 C：批次整合（二期，Dreams 式）

后台任务定期对同 scope 记忆做整合：合并重复、消除同槽位矛盾（以最新为准替换）、归档过时；**输入不直接改**，产出候选结果给管理员审核后落库。与写时增量（A/B）互补，且为引入嵌入相似度（P4）提供自然入口——批次整合需要语义召回，递归近邻"词元 LIKE"的召回率不足以支撑无监督去重。

### 3.5 待拍板决策点

| # | 决策 | 推荐 | 理由 |
|---|---|---|---|
| 1 | 完全同义（无新增信息）的重复：合并还是跳过 | **合并（UPDATED）** | 业界主流是"以最新为准更新一次"；跳过只限零增量转述 |
| 2 | 同槽位偏好变化：覆盖 vs 双写 | **新值取代（supersede），旧值失效保留** | 双写同槽位 ACTIVE 让检索端两难（P2） |
| 3 | 更新是否保留审计 | **是（走 B2 历史表）** | 每写 1 行多插 1 行，换来 id 稳定 + 完整回滚 |
| 4 | 批次整合是否进本期 | **否，二期** | 一个 change 不同时改热路径与后台任务；批次整合依赖嵌入，占位 |
| 5 | 误覆盖防护是否需要人工确认弹窗 | **不需要强制** | 已有"当轮明确指令 > 记忆"规则（`main_agent.md:11-18`）+ 管理页可见已够 |

## 4. 演进路线

```text
一期（本 change，方案 B2 = A + 历史表审计）
  新增 UPDATED outcome + acceptWrite 更新分支
  V11 迁移：user_memory_revision 历史表（更新前旧版落表）
  管理 REST 详情支持查看/回滚历史（可选）
  spec/design/tasks/IT 同步（含反转"重复不覆盖只跳过"原规格）
二期（批次整合）
  Dreams 式后台整合任务 + 人工审核输出
  P4：嵌入语义召回（复用知识检索嵌入调研基础）升级 recallNear 与批次去重
三期（衰减与退出）
  Zep 式 validity interval / step-decay；合规硬删除路径（GDPR 类）；Letta 式归档分层
```

## 5. 验证要求（沿用项目 SDD+TDD 门禁）

- 每个新场景先写失败测试（中文注释说明业务目的与防回归），再实现；
- 关键 IT：①重复偏好→既有条目被更新为最新内容且 `use_count`/`created_at` 不变；②偏好变更→旧值标记 superseded、检索结果只含新值；③管理列表可见被替代项；④预算/校验/语义无关失败路径不受影响；
- 判断链提示词改动后需跑既有 `MemoryServiceIT` 全量，确认 SKIP_NOT_WORTH/CONFLICT_CREATED 语义未回归；
- 迁移需验证 Flyway 表数增量（当前 31 表基线）与 ARCHITECTURE-test 约束。
