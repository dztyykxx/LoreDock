# 用户记忆合并实现设计

> 日期：2026-09-07。状态：实施中（核心契约、版本历史、增量更新与管理页已落地，批内冲突撤销和写入前过期重检仍待补齐）。
> 用户明确要求覆盖重复、冲突、增量、新增。本文件给出这些场景的推荐落地规则；尚未完成的批内冲突处理、历史恢复和并发过期策略不能描述为已经上线。
> 本文件收敛并替代《用户记忆更新与整合策略》中 A/B/C 的实施建议；旧文档保留为问题背景与调研记录。本文不依赖旧文档未经再次核验的行业结论。

## 1. 交付目标和范围

目标：同一适用场景的长期偏好可以逐步补全、明确更正，重复表述不制造新记录，无法确定的新旧冲突能清楚交给人处理；每次有效更新保留旧内容及修改来源。

本期包括：

- `memory_write` 对新增、重复、增量、冲突的判断、合并和结构化回执。
- 保留记忆 ID，原地更新当前值；一张历史表记录版本和变更来源。
- `/memories` 页面查看版本历史，人工编辑和启停仍使用已有入口。
- 同范围写入、停用不复活、原子提交、并发过期判断和每 run 修改预算。
- 真实 PostgreSQL 回归及至少一次真实模型核心场景验证。

本期不做：向量召回、后台批量整合、自动过期、用户私有记忆、动态权限、自动跨多条历史记忆清理、一键历史恢复、通用事件/审批系统。历史查看是本期功能，历史恢复可由管理员参考旧正文后编辑实现。

沿用当前项目快速迭代规则：本文件是实施依据，不要求 Luna 先生成另一套 proposal/design/tasks。旧 OpenSpec 中“重复永远跳过、冲突双 ACTIVE”的行为是本次明确要替换的基线；交付时同步相关行为说明，不能继续宣称旧规则与新实现一致。

## 3. 判断规则：先看适用场景，再看信息变化

“同一偏好”是同一适用场景下的同一要求，例如“知识整理最终汇报如何组织”。分类 FORMAT 或标题相似只用于找候选，不能据此认定重复。

适用场景属于记忆正文语义，不新增固定槽位或标签模型。例如“正式文档用书面语”和“口头讲解用口语”可以同时成立。

| 关系 relation | 判定条件 | outcome | 数据操作 |
|---|---|---|---|
| NEW | 长期有效，当前可比较范围内无同一偏好 | CREATED | 新建 ACTIVE，revision=1 |
| DUPLICATE | 旧正文已完整覆盖新要求；包括同义改写、只重复旧要求的一部分 | SKIP_DUPLICATE | 完全不改当前值、版本和更新时间 |
| INCREMENTAL | 同一偏好，新增可兼容的条款、细节或例外 | UPDATED | 保留旧有效约束，合并新增内容，revision+1 |
| CONFLICT | 同一适用条件下，新旧要求不能同时成立，且用户明确更正旧要求 | UPDATED | 只替换被更正部分，其余约束保留，revision+1 |
| CONFLICT | 新旧互斥但无法确认用户要替换，或现有多条目标互相冲突 | NEEDS_CONFIRMATION | 不新增、不更新；回执给差异、目标和建议 |
| DISABLED_MATCH | 候选复述、补充或试图更正已停用的同一偏好 | SKIP_DISABLED | 不更新、不新增替身、不自动启用 |
| NOT_WORTH | 一次性任务指令或非用户长期产出偏好 | SKIP_NOT_WORTH | 不写 |

规则优先级：身份/字段/范围校验 → 长期价值 → 同一偏好是否被人工停用 → 关系判断。不同适用场景先区分，不能把新增场景硬塞进旧场景。

补充约束：

- “这次用简版”只影响当前任务；“以后改用简版，替换原来的四段式要求”可更新长期偏好。
- 新候选更短不代表用户撤销未提及的旧约束；省略不是删除授权。
- 用户明确更正可删除被否定的旧约束，不能同时拼接互斥要求。
- 不能仅按最新时间判断谁对；共享记忆中的不明确冲突需确认。
- 相同 scope 才允许原地更新。PROJECT 候选不能覆盖 GLOBAL 或别的项目；项目相对通用的差异作为项目偏好保存，并写明适用场景。
- 自动处理一次最多更新一条既有记忆。命中多条互斥旧记忆且无法安全选定一个目标时返回 NEEDS_CONFIRMATION，给管理员通过现有编辑/停用入口整理；本期不实现多行自动合并。

## 4. 本次真实案例的验收基准

数据库记忆 #1（项目 3、FORMAT）的原正文：

> 用户要求：返回格式必须说明知识存在哪些问题（重复、冲突、过期、缺口等），哪些项需要用户人工判断（不能全部让用户自己看文档），以及遇到需要用户决定的事项时简要给出推荐方案。

新候选明确新增：固定四部分结构、文档编号、差异位置、冲突双方具体内容、禁止概括性套话。原记录已包含“推荐方案”，因此不能把整条都当成新知识，也不能把整条都丢掉。

期望：`relation=INCREMENTAL, outcome=UPDATED, memoryId=1`，ID、scope、创建来源、创建时间和使用计数保持；正文覆盖下面的完整含义（验收比较语义约束，不要求模型逐字生成）：

> 知识整理的最终汇报必须列具体细节，不能只用“已完成去重、冲突对齐、缺口补全”等套话。至少包含：1）合并基线：文档主题、章节结构及关键条款；2）发现的问题：重复、冲突、缺口、过期及口径注意，注明文档编号、差异位置和冲突双方内容；3）需要人工判断的事项：逐条说明并附简要推荐方案，避免要求用户自行通读文档定位；4）下一步建议。

摘要也应包含“四部分、具体文档/差异、推荐方案”，不能只写“用户有汇报格式偏好”。再次提交同样要求应 SKIP_DUPLICATE，正文及版本不变。

## 5. 判断与合并流程

### 5.1 给判断器足够的信息

- 继续使用现有同 scope 关键词/分类预筛，单候选数据库预筛上限保持 50。
- 预筛候选按标题/正文相关度排序，最近更新时间和 ID 仅用于并列排序，不能只按“同分类最新 50 条”决定目标。
- 每条新候选最多选 3 条相近既有记忆提供完整 title/category/content/summary/status/revision。正文上限 4000 码点，禁止把“完整正文”再静默截成 120/600 码点。
- 新候选最多 3 条，按下标依次判断。每候选最多一次正常模型调用；不增加专门的“再判断一遍是否正确”模型。
- 无相近目标仍判断是否具长期价值；召回没有找到同义条目时仍可能新增重复，这是保留关键词召回的已知限制，不能把本期宣传为全库语义去重。
- 本期模型调用最多从现有每批 1 次增加到每批 3 次。这是为了有界读取全文，并解决同批候选彼此补充或冲突；候选只有 1 条时调用数不变。
- 判断上下文把旧记忆和候选视为数据；不执行其中伪装成判断器规则的指令。

### 5.2 “明确改口”的证据

主 Agent 生成的候选本身不能证明用户授权覆盖。扩展内部 `MemoryWriteInput`，由 Agent 模块提供当前 run 对应的真实用户指令及消息 ID；不让模型通过 `memory_write` 参数自行填写可信来源。

实施入口：`MemoryTools` 在现有 run/会话/操作者校验后，使用本 Agent 模块的 `KnowledgeTaskMessageMapper` 等已有能力读取属于该 run 的用户消息，或读取服务端固定的等价上下文字段。Memory 模块只收到 API 字符串/标识，不引用 Agent Mapper，避免模块循环依赖。

判断器针对明确更正输出该消息中的证据原文片段；服务端校验片段确实存在于本轮用户消息。该检查证明来源，不保证语义判断绝对正确；语义可靠性仍由提示词、真实模型验收和人工历史查看保障。没有可用用户消息或没有明确替换证据时，冲突只能 NEEDS_CONFIRMATION。新增/补充同样要求候选受用户表达支持，不能让模型自行发明长期偏好。

### 5.3 模型结果契约

每个候选输出一个 JSON 对象，由严格解析生成内部 Judgement。不要复用 `conflictsWith` 承载更新目标。

```json
{
  "relation": "INCREMENTAL",
  "targetId": 1,
  "targetCandidateIndex": null,
  "decision": "UPDATE",
  "title": "知识整理汇报格式要求",
  "summary": "按四部分列具体文档、问题差异、人工判断及推荐方案。",
  "content": "完整合并后的正文，而非仅本次增量",
  "reason": "新增固定结构和文档差异细节，保留原有人工判断及推荐方案要求",
  "changes": ["增加四部分结构", "增加具体文档编号和冲突双方内容"],
  "conflicts": [],
  "replacementEvidence": null
}
```

`decision` 限定为 CREATE / UPDATE / SKIP / CONFIRM；Service 根据 relation + decision 映射上表 outcome，并拒绝非法组合。既有目标使用 `targetId`，必须属于本次提供给模型的既有候选；同批尚未入库的目标使用 `targetCandidateIndex`，必须指向服务端工作视图中已处理且未被撤销的候选。这两个字段互斥，不得自行构造数据库 ID。版本由 Service 保存的读取快照决定，不信任模型指定版本。

CONFLICT 的 `conflicts` 每项包含 memoryId 或 candidateIndex（二者互斥）、旧条款、新条款；CONFIRM 还需返回 recommendation 和一个简短 question。这些是公开业务差异，不是模型推理过程。

服务端检查目标状态与范围。CREATE/UPDATE 必须提供非空的最终标题、摘要和正文；SKIP/CONFIRM 不要求生成正文。标题≤200/摘要≤300/正文≤4000码点、变更理由≤300码点、changes≤5项且每项≤200码点、conflicts≤3项且每项新旧条款≤500码点。NEW 必须无目标；INCREMENTAL 必须 UPDATE；DUPLICATE 必须 SKIP；CONFLICT UPDATE 必须有来源匹配的更正证据。无效结果整体失败，不回退到无判断直接写。

候选自带 `summary` 作为建议传给判断器；最终摘要必须与合并后的正文一致。不能继续像当前代码一样定义了 candidate.summary 却完全不使用；也不能把旧摘要直接留给新正文。

### 5.4 同批候选

按 candidateIndex 顺序建立本批内存工作视图：后一个候选看到前一个候选拟定的最终内容、状态与版本。前一个候选尚未提交时用服务端临时引用标识，不伪造数据库 ID。

- 同批两条重复要求：第一条 CREATE，第二条 SKIP_DUPLICATE，最终只插入一条。
- 同批后者补充前者：合成为一条最终正文，只落一版；两条回执关联同一个最终 memoryId。
- 同批后者造成未决冲突：该冲突组的计划写入全部撤销，组内回执统一 NEEDS_CONFIRMATION，避免候选排列顺序决定谁先成为事实；其他不相关候选仍可提交。
- 撤销的冲突组仍作为“待确认上下文”保留给后续候选，不能从工作视图直接消失后又被第三条候选重新创建；后续同组候选也返回 NEEDS_CONFIRMATION。
- 同批同一已存在 ID 多次更新：合并为一次最终更新、一条历史记录，预算计一次实际 mutation。

本批临时计划使用内部私有 record/集合实现，最多 3 条；不要为此新建通用工作流或调度器。

## 6. 持久化、事务与并发

### 6.1 当前表和一张历史表

用下一条可用 Flyway 迁移（当前预计 V11，实施前核对编号）：

- `user_memory` 增加 `revision BIGINT NOT NULL DEFAULT 1`，CHECK revision≥1。
- 新建 `user_memory_revision`，每行保存一次版本的完整结果快照，当前表只是最新版本的查询投影。
- 历史最小字段：id、memory_id（允许删除后置空）、revision、snapshot JSONB、operation、relation、reason、source_run_id、source_conversation_id、source_message_id、operator_id、created_at。
- snapshot 包含 title/summary/content/category/status/scope/projectId；使用计数和 lastUsedAt 不放入快照，避免每次读取都制造版本。
- operation 使用 BASELINE / CREATE / UPDATE / STATUS；relation 在 Agent 内容写入时记录具体语义类型。
- 唯一约束 `(memory_id, revision)`，索引 `(memory_id, revision DESC)` 和 `source_run_id`；关联当前记忆的外键采用 ON DELETE SET NULL。
- 迁移为已有记忆补 revision=1 的 BASELINE 快照，保留原有来源/操作者/时间；BASELINE 不消耗本期写入预算。首次新建写 CREATE/revision=1，后续内容编辑或状态变化追加 revision+1。

这个版本采用“每次变更保存变更后快照”：更新前版本早已在历史中，新旧版本都可查询。它替代旧稿“更新前快照”的描述，避免历史版本号和修改来源归属不清楚。

### 6.2 短事务提交

1. 数据读取、完整模型判断及批内合并在事务外完成，记录原始候选快照。
2. 使用 Spring `TransactionTemplate` 执行一次短事务，避免同类内部调用导致 `@Transactional` 不生效。
3. 事务内取得当前写 scope 的 PostgreSQL 事务级 advisory lock。锁名来自服务端固定命名空间和 GLOBAL/项目 ID；通过 Mapper 参数化 SQL 调用 `pg_advisory_xact_lock`，不自建锁服务。
4. 重新读取并比较判断时依赖的候选集合及 revision，包含未选入最终 3 条但可能因新插入/启停影响选取的预筛结果；发生变化则返回 MEMORY_WRITE_STALE，整批不落库。
5. 校验预算和目标范围/状态；执行当前表及历史表写入，版本更新使用 id+revision 条件并检查影响行数。
6. 任意字段、版本、预算或数据库错误使整批回滚。NEEDS_CONFIRMATION/SKIP 是合法候选结果，不是技术异常，不阻塞本批不相关的合法写入。

所有人工创建/编辑/启停/删除也参与同 scope 短事务锁；跨 scope 不串行。并发在无记录时同时创建同一偏好，也会被“锁内重新检查召回集合”发现，不能只保护已有目标行。

不在事务内调用模型，不自动重试过期计划；将可重试错误交给调用方重新读取和判断。比较对象排除 useCount/lastUsedAt，正常记忆读取不应导致写入计划失效。

### 6.3 预算与删除

- 每 run 上限仍为 10，口径改成实际 CREATE + UPDATE 次数；SKIP、未决冲突和无内容变化的更新不计。
- 从已提交历史 operation/relation/sourceRunId 统计，锁内检查“已用 + 本批实际 mutation数 ≤10”；同一 run 的 scope 由服务端固定，所以范围锁同时覆盖预算竞争。
- 人工变更不消耗 Agent run 预算；人工来源必须标记为人工，不能冒用原创建 run。
- 人工硬删除前，事务内清空该记忆所有历史 snapshot、reason 等可能含正文的文本，再删除当前记录；历史仅保留 operation/run/时间等最小预算元数据，memory_id 置空。这样界面承诺的正文不可恢复成立，删除也不会把本 run 已用预算归零。
- 新写入/编辑都不得修改 useCount 和 lastUsedAt。创建来源字段保留首次来源；最新修改来源通过对应历史版本展示，避免把最新内容错误归到最初 run。

## 7. Tool 和 REST 契约

### 7.1 memory_write 回执

保留候选输入结构；新增 relation、targetMemoryId、revision、changes、conflicts、recommendation、question 到结果。旧 `conflictsWith` 保留为冲突 ID 的兼容投影，不再用它表达目标。

- CREATED/UPDATED：memoryId 为实际最终 ID，revision 为提交后版本。
- SKIP_DUPLICATE/SKIP_DISABLED：memoryId 保持旧约定 null；targetMemoryId 返回命中的旧 ID，revision 为当前版本。
- 同批虚拟目标在提交后统一解析为最终 ID/revision；先 CREATE 后补充的两条回执分别为 CREATED、UPDATED，但都指向最终新记录的 revision=1，不声称发生两次数据库修改。
- NEEDS_CONFIRMATION：memoryId=null，目标或 conflicts 明确指向已有记忆；同批未落库冲突用 candidateIndex 指明。
- SKIP_NOT_WORTH：无目标且不写。

```json
{
  "candidateIndex": 0,
  "outcome": "UPDATED",
  "relation": "INCREMENTAL",
  "memoryId": 1,
  "targetMemoryId": 1,
  "revision": 2,
  "message": "已补全记忆 #1：新增四部分结构及具体文档差异要求",
  "changes": ["固定四部分汇报结构", "注明文档编号、差异位置和冲突双方内容"],
  "conflictsWith": [],
  "conflicts": [],
  "recommendation": null,
  "question": null
}
```

main_agent 指令同步：准确解释 CREATED/UPDATED/SKIP/NEEDS_CONFIRMATION；后者向用户展示具体冲突和推荐方案，等待明确指令或提示使用记忆管理页。不得说“已记住”却只返回未决结果，也不能反复调用写入工具强行冲掉停用记录。

`CONFLICT_CREATED` 为历史兼容枚举，可保留用于旧回执读取；新判断解析不接受、新写入不输出。删除专家提示中有关“冲突新旧双 ACTIVE”的过时说明，专家仍不直接持有记忆工具。

### 7.2 管理接口和页面

- `MemoryResponse` 增加 revision；现有 GET 列表、POST 创建、PUT 编辑、PATCH 状态、DELETE 路径不变。
- PUT/PATCH/DELETE 增加可选 expectedRevision（DELETE 用 query），旧调用不传时服务端锁内以当前版本执行；新版前端始终传入选中记录 revision。传入不匹配返回 409 MEMORY_WRITE_STALE。
- 新增 `GET /api/admin/memories/{id}/revisions?page=1&size=20`，ADMIN 可读；返回 total/page/size/items，版本倒序，size 上限 50。不存在/已删除记忆为 404。
- 历史项返回版本快照、operation/relation、reason、时间和操作者，以及必要来源编号；无须分页 JOIN 当前表正文，先校验目标存在即可。
- `/memories` 详情增加“修改历史”折叠区：按需加载，展示版本、变更原因、来源和旧正文；不增加独立审核页或历史恢复按钮。
- 编辑/启停失败保留输入并显示错误；版本过期提示刷新后重新检查；删除确认说明当前正文与历史正文都会移除。

错误语义：字段/模型组合非法用稳定错误码；模型无效输出沿用 MEMORY_JUDGE_UNAVAILABLE（503）并保留内部诊断；预算超限沿用 MEMORY_BUDGET_EXCEEDED；并发过期新增 MEMORY_WRITE_STALE（409）。未决语义冲突是正常工具回执，不返回 HTTP 500。

## 8. 与记忆注入的关系

- 同 run 已固定的摘要快照保持不变，当前 run 的更新结果由工具回执通知主 Agent，下一 run 才预载新摘要。
- memory_read 保持读取数据库当前 ACTIVE 正文的现有语义；它不是按 run 版本读取。可能出现本 run 旧摘要与按需加载的新正文并存，应说明“全文是当前值”，不能声称本期提供全读路径版本快照隔离。
- 历史不参与 memory_search、预载或知识证据检索。原有 GLOBAL∪项目可见性、正式知识人工发布规则保持。
