# LoreDock 核心业务链路与模块边界

> 当前唯一开发主线：**先保证用户基于指定项目和分支获得带引用的回答，证据不足时明确拒答**。链路一、链路二为当前主线；链路三、链路四标记为后续阶段，当前不建设对应代码、表和扩展点。

## 1. 一句话定义

LoreDock 的核心是把分散的业务材料和代码快照变成**有范围、有来源、可检索的证据**，再通过 Web 和 MCP 帮助开发人员理解项目，并把真实需求变更继续沉淀为新知识。

```text
材料进入 → 建立索引 → 检索证据 → 回答或拒答 → 人工反馈/变更沉淀 → 新知识发布 → 再次进入检索
```

认证、文件存储、后台任务、运行记录和页面管理都是支撑能力，不应反过来主导业务结构。

## 2. 核心链路

### 2.1 链路一：知识与代码进入系统

```text
创建项目/分支
├── 导入或编辑知识 → 设置范围 → 人工发布 → 分块与向量化 → 进入知识索引
└── 上传代码快照 → 绑定分支和 Commit → 过滤文件 → 建立全文索引 → 成为活动快照
```

完成标志：在指定项目和分支下，可以检索到正确的已发布知识和活动代码，并能返回来源。

核心约束：

- 知识只区分通用、项目、分支三个范围；
- 草稿不能被正式检索，发布后才进入索引；
- 同一分支只保留一个活动代码快照查询入口；
- Commit 是代码来源信息，不建设历史快照和版本管理系统；
- 索引失败不能把当前可用数据切换成不可用状态。

### 2.2 链路二：检索与项目问答

```text
用户选择项目/分支并提问
→ 解析查询范围
→ 检索通用知识、项目知识、分支知识和当前分支代码
→ Agent Runtime 基于证据生成回答
→ 返回回答、引用、分支和 Commit
→ 证据不足则拒答，来源冲突则同时提示
→ 用户可提交知识缺口反馈
```

这是首个可用闭环，也是当前开发的最高优先级。模型或 Agent 不可用时，普通知识检索和代码检索仍应可用。

### 2.3 链路三：需求变更沉淀为知识

> 后续阶段：当前不实现。以下描述保留为方向基线，不作为当前实现依据。

```text
导入需求、PR/Diff 和测试材料
→ 需求、代码、测试证据并行提取
→ 汇总证据台账
→ 文档 Agent 生成草稿
→ 独立审查
→ 管理员修改并确认发布
→ 更新知识索引
→ 后续 Web 与 MCP 可以检索
```

这是 LoreDock 持续产生价值的核心闭环。多 Agent 只负责证据提取、编写和审查，主流程由应用固定，不建设动态编排平台。Agent 只能生成草稿，不能直接发布正式知识。

### 2.4 链路四：MCP 向本地 Agent 提供上下文

> 后续阶段：当前不实现身份校验、摘要和模型生成；如提供 MCP 工具，只复用现有检索服务。

```text
Claude Code 调用 MCP
→ 搜索知识、读取文档或搜索代码
→ 复用 Web 同一套范围与检索服务
→ 返回原始证据和引用
→ Claude Code 结合本地最新代码完成分析
```
MCP 是检索能力的另一个入口，不单独实现业务逻辑。当前阶段不做身份校验、不生成 MCP 摘要，也不调用模型生成最终答案。

## 3. 模块边界

当前已实现模块：`project`、`knowledge`、`code`、`agent`、`qa`、`feedback`、`job`、`auth`、`storage`。`change`（需求沉淀）与 `mcp` 属于后续阶段模块，当前没有代码、表或扩展点。

| 模块 | 对外能力 | 主要输入 | 主要输出 |
|---|---|---|---|
| `project` | 项目、分支与查询范围 | 项目标识、分支 | 项目/分支信息、有效范围 |
| `knowledge` | 文档维护、发布、索引和混合检索 | 文档、范围、查询条件 | 文档、检索结果、引用 |
| `code` | 快照上传、索引、搜索和片段读取 | 项目、分支、Commit、ZIP、查询 | 活动快照、代码结果、片段 |
| `agent` | 运行 Spring AI Alibaba Agent | 问题、工具、范围、限制 | 回答/拒答、引用、运行结果 |
| `qa` | 编排一次项目问答 | 项目、分支、问题 | 流式状态、最终回答、引用 |
| `feedback` | 记录和处理知识缺口 | 问题、类型、关联问答 | 缺口记录、处理状态 |
| `change`（后续阶段） | 需求到实现的知识沉淀 | 需求、PR/Diff、测试材料 | 证据台账、待审核草稿 |
| `mcp`（后续阶段） | 将查询能力暴露给本地 Agent | MCP 工具参数 | 原始上下文与引用 |

模块协作遵循：

```text
Web Controller ─┬→ QA Service → Agent / Project / Knowledge / Code 的 api
                └→ 各业务模块 Service

MCP 入口（后续阶段） ──→ Knowledge / Code 的 api

Change Service ──→ Project / Knowledge / Code / Agent Service
```

- 每个业务模块内部使用 `Controller → Service → Mapper → PostgreSQL`；
- 跨模块只引用对方模块的 `api` 契约包（Service 接口与最小稳定契约类型），不访问对方 Service 实现、Mapper、Entity 或内部过程模型；
- MCP 和 Web 只做入口适配，不复制范围、检索和引用规则；
- `AgentRuntime` 只隔离 Spring AI Alibaba，具体知识规则仍由业务 Service 决定；
- 模型和嵌入模型分别直接依赖 Spring AI 的 `ChatModel`、`EmbeddingModel`，替换实现不影响上层链路。

## 4. 开发优先级

1. **当前主线：先保证可回答**（链路一 + 链路二）：项目/分支管理、知识导入发布与索引、代码快照索引、范围检索、带引用问答和明确拒答真实可运行；证据不足的拒答和运行故障的失败说明必须可区分；
2. **后续阶段：第二入口 MCP**：复用现有查询服务返回原始证据，当前不实现身份校验和摘要；
3. **后续阶段：知识增长闭环**：需求变更材料经多 Agent 整理、人工审核后发布；
4. **后续阶段：治理能力**：知识体检、定期任务、历史版本、复杂恢复和统计均不得阻塞主链路。

每推进一项功能，都应先说明它接入哪条核心链路、调用哪些模块接口、产生什么可观察结果。无法回答这三个问题的功能，当前阶段不应进入开发。
