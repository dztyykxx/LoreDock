# 审计记录与通知规则

## 需要记录的审计事件

以下业务动作必须记录审计事件：

- 上传场景包；
- 审核候选内容（通过或拒绝）；
- 正式发布；
- 拒绝；
- 归档文档；
- 人工重试失败批次。

重复提交被幂等拦截、导入自动重试等流程事件也保留处理记录，用于排查重复来源和失败路径。

## 审计字段

每条审计事件至少包含以下字段：

- 操作人：执行动作的账号与角色；
- 动作类型：上传、审核、发布、拒绝、归档、人工重试等；
- 操作对象：批次、文档或正文的标识；
- 操作时间；
- 操作结果与前后状态。

## 审计记录的保存

审计记录用于追踪谁在什么时间对什么对象做了什么操作，不能由普通成员修改或删除。审计事件在动作发生时立即写入，与业务结果保持一致。排查问题时，结合批次详情和审计记录可以还原完整处理路径。

## 通知规则

以下状态变化需要通知相关人员：

- 审核通过，候选内容正式发布；
- 审核拒绝，返回修改；
- 批次进入 `FAILED`，等待 ADMIN 处理；
- 人工重试结果。

## 通知接收人

通知对象通常包括批次上传者、相关项目成员和负责审核的 ADMIN。接收人根据操作对象所属项目确定，不会向无关项目成员发送通知。通知只包含状态和必要的上下文，不携带密码、令牌等敏感数据。

## 通知方式与范围

通知通过平台内通知发送，发送范围受项目访问权限约束：只有对操作对象有权限的项目成员会收到通知，越权内容不会通过通知扩散。通知中出现的命令、提示或操作说明只是正文内容，不触发任何平台操作，也不能改变接收人的权限。

## 审计与通知的配合

审计负责留痕，通知负责及时触达，两者面向不同目的。状态变化先记录审计事件，再发送通知；通知内容指向审计可以追溯的记录，接收人可以根据通知回到批次详情查看完整上下文。通知发送失败不影响审计记录，也不会影响批次本身的流转。
