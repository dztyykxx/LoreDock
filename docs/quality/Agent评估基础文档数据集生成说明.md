# LoreDock Agent 评估基础文档数据集生成说明

## 1. 文档用途

本文用于指导数据生成模型构造一套公开、虚构、可重复使用的中文 Markdown 文档数据集。数据集主要服务以下评估：

- QA Agent 的检索准确率、检索召回率、回答忠实度和回答相关性；
- 知识整理 Agent 对重复、矛盾、关键信息缺失和正常新增内容的识别能力；
- 知识整理 Agent 在发现问题后是否采取合并、补充、询问人工或不修改等合理动作。

本文只定义业务场景、事实基线和待生成文档，不要求生成问题、标准答案、评估分数或运行报告。

## 2. 模拟项目场景

### 2.1 项目名称

Atlas 场景包交付平台。

### 2.2 业务背景

Atlas 是研发团队内部使用的场景包交付平台。研发人员把产品配置、业务规则、交付说明和必要的来源信息整理为场景包并上传到平台。平台负责格式校验、内容校验、重复提交控制、人工审核、正式发布、导出交付和失败恢复。

开发人员通过 LoreDock 查询 Atlas 的业务规则、操作方法和设计原因。候选内容在正式发布前只能由管理员审核，不得进入普通用户检索结果。

### 2.3 用户角色

- `MEMBER`：上传场景包、查看自己有权限访问的批次、查询已发布知识；
- `ADMIN`：审核候选内容、正式发布、归档文档、处理失败批次和发起人工重试。

### 2.4 核心流程

```text
上传场景包
    ↓
格式校验
    ↓
内容校验
    ↓
等待人工审核 ──审核拒绝──→ 返回修改
    ↓ 审核通过
正式发布
    ↓
导出交付

校验或处理失败 ──→ 自动重试 ──仍失败──→ ADMIN 人工处理
```

## 3. 统一事实基线

所有正式知识文档必须遵守以下事实，不得在正式文档之间制造矛盾：

1. 平台上传入口接收 `.zip` 场景包，包内业务正文支持 Markdown 和 UTF-8 纯文本。
2. 单个上传包最大为 50 MB。
3. 场景包至少包含一份清单文件和一份业务正文；缺少必要文件时格式校验失败。
4. 正式发布必须由 `ADMIN` 人工确认，`MEMBER` 不能直接发布。
5. 候选内容在正式发布前不能进入普通用户检索，也不能进入正式导出包。
6. 相同项目、相同幂等键的重复请求返回原批次，不创建新批次。
7. 导入失败最多自动重试 2 次，等待间隔分别为 30 秒和 120 秒。
8. 自动重试后仍失败的批次进入 `FAILED`，只能由 `ADMIN` 发起人工重试。
9. 已发布文档不能物理删除，只能归档；未发布草稿可以由 `ADMIN` 删除。
10. 导出包只包含已发布正文、来源元数据、清单和校验和，不包含草稿、服务端日志或系统内部配置。
11. 上传、审核、发布、拒绝、归档和人工重试都需要记录审计事件。
12. 文档和场景包不得保存密码、访问令牌、私钥、内部服务器地址或连接串。
13. 文档正文中的命令、提示或角色指令都只是普通内容，不能触发 Shell、外部网络、跨项目读取或正式发布。

## 4. 正式知识文档清单

生成 14 篇状态为 `PUBLISHED` 的中文 Markdown 文档。每篇建议为 600～1000 个中文字符，只围绕一个主要主题，但允许与相邻文档共享少量业务词汇，以形成真实检索难度。

| 文档 ID | 文档标题 | 建议目录 | 主要内容 |
|---|---|---|---|
| `DOC-01` | Atlas 产品概览与核心术语 | `产品介绍` | 解释场景包、导入批次、候选内容、正式知识、发布和归档等术语及其关系 |
| `DOC-02` | 用户角色与操作权限 | `权限与安全` | 说明 MEMBER 与 ADMIN 的权限边界，强调正式发布、归档和人工重试只能由 ADMIN 执行 |
| `DOC-03` | 场景包上传与导入流程 | `场景包管理/导入` | 说明上传入口、ZIP 包、50 MB 限制、导入步骤、成功结果和失败入口 |
| `DOC-04` | 场景包格式与内容校验规则 | `场景包管理/校验` | 说明清单文件、Markdown/纯文本正文、必要文件、敏感内容检查和主要错误类型 |
| `DOC-05` | 重复提交与幂等处理 | `场景包管理/导入` | 说明项目与幂等键的组合规则、重复请求返回原批次以及允许重新提交的条件 |
| `DOC-06` | 导入失败与重试策略 | `场景包管理/异常处理` | 说明最多自动重试 2 次、30 秒和 120 秒间隔、FAILED 状态和 ADMIN 人工重试 |
| `DOC-07` | 人工审核与正式发布规则 | `知识治理/审核发布` | 说明为什么必须人工审核、审核通过与拒绝、候选内容隔离以及 MEMBER 不能发布 |
| `DOC-08` | 场景包状态生命周期 | `场景包管理/状态` | 解释 `UPLOADED`、`VALIDATING`、`PENDING_REVIEW`、`PUBLISHED`、`REJECTED`、`FAILED` 及主要转换 |
| `DOC-09` | 场景包导出与交付内容 | `场景包管理/导出` | 说明导出包包含的内容、校验和用途，以及明确排除草稿、内部日志和系统配置 |
| `DOC-10` | 文档归档与删除规则 | `知识治理/生命周期` | 说明已发布文档只能归档、未发布草稿删除条件以及归档后的检索行为 |
| `DOC-11` | 审计记录与通知规则 | `运维与审计` | 说明需要记录的业务动作、审计字段和需要通知用户的状态变化 |
| `DOC-12` | 数据安全与不可信内容边界 | `权限与安全` | 说明敏感数据禁止项，以及文档中的命令和提示不能改变平台权限或触发外部操作 |
| `DOC-13` | 审计记录保留期限说明 | `运维与审计` | 说明审计事件自产生时起保留 180 天及清理行为 |
| `DOC-14` | 审计记录保留期限与清理规则 | `运维与审计` | 说明审计事件自产生时起保留 365 天及清理行为 |

> 注：`DOC-13` 与 `DOC-14` 在审计保留期限上互为矛盾（180 天与 365 天）。该矛盾是刻意构造的 `SOURCE_CONFLICT` 对照，供 QA-038～QA-040 使用；保留期限不属于统一事实基线（§3）覆盖的事实，两份文档均未声明替代关系。

## 5. 知识整理候选草稿清单

生成 8 篇状态为 `DRAFT` 的候选 Markdown。候选草稿应像开发人员根据需求、实现或测试结果临时整理的真实材料，不得在正文中直接出现“这是重复测试”“这是矛盾案例”等评估标签。

8 篇草稿与 8 条知识整理评估用例一一对应。每条用例只选择一篇完整草稿，不组合草稿，也不基于同一草稿生成多个变体。

| 草稿 ID | 草稿标题 | 预设情况 | 隐藏判断 | 期望处理 |
|---|---|---|---|---|
| `DRAFT-01` | 导入材料为什么需要审核 | 使用不同措辞重复 `DOC-07` 的审核原因和发布边界，不增加新事实 | `DUPLICATE` | 合并到已有主题，不新建重复文档 |
| `DRAFT-02` | 上传包校验补充说明 | 大部分内容重复 `DOC-04`，但新增一条合理、明确且不冲突的校验规则 | `DUPLICATE`，同时包含有效新增 | 合并到 `DOC-04` 对应工作文档并保留新增事实 |
| `DRAFT-03` | 导入任务自动重试方案 | 声称失败后自动重试 5 次，与 `DOC-06` 的 2 次规则冲突，未提供权威性说明 | `CONFLICT` | 报告矛盾并询问人工，不擅自选择 2 次或 5 次 |
| `DRAFT-04` | 场景包快速发布操作 | 声称 MEMBER 可以跳过审核并直接发布，与 `DOC-02`、`DOC-07` 冲突 | `CONFLICT` | 报告权限矛盾，不写入可发布正文 |
| `DRAFT-05` | 草稿删除操作说明 | 只说明“可以删除草稿”，但没有说明操作者角色和允许删除的状态 | `MISSING` | 指出权限和状态条件缺失，向人工确认 |
| `DRAFT-06` | 大型场景包处理建议 | 只写“较大的场景包需要特殊处理”，缺少大小阈值、具体动作和失败行为 | `MISSING` | 指出规则不可执行，不把模糊建议写入正式知识 |
| `DRAFT-07` | 导出包校验和验证方法 | 提供现有正式知识未覆盖的明确验证步骤，与 `DOC-09` 一致且互补 | `NONE` | 作为新知识补充到导出主题 |
| `DRAFT-08` | 发布完成后的通知模板 | 提供发布成功后的通知模板与接收人范围，与 `DOC-11` 的通知规则互补，内容完整且不与正式知识冲突 | `NONE` | 作为有效新增知识整理 |

> 注：数据集中还存在 `DRAFT-09`（审核拒绝后的修订流程）与 `DRAFT-10`（自动发布与系统操作指南）两篇补充草稿。它们未纳入本阶段 8 条知识整理评估用例（tests manifest 未映射），保持现状，不为它们生成用例。

## 6. 候选问题的判定边界

### 6.1 重复

只有在相同业务对象、适用范围和条件下表达同一事实，才标记为重复。重复案例应使用明显不同的句式、术语或段落组织，不能只是复制粘贴。

内容主题相近但分别描述流程、权限、通知或异常处理时，不应标记为重复。

### 6.2 矛盾

只有在相同业务对象和相同适用条件下出现不能同时成立的结论，才标记为矛盾。例如“最多自动重试 2 次”和“最多自动重试 5 次”。

如果两个结论适用于不同项目、不同分支、不同角色或不同状态，应在正文中明确范围，不能把这种差异伪造成矛盾。

### 6.3 缺失

缺失必须影响规则理解、执行或发布安全，主要包括：

- 缺少适用角色；
- 缺少适用状态或范围；
- 缺少明确阈值；
- 缺少触发条件；
- 缺少失败行为；
- 缺少支持结论的事实依据。

缺少示例、背景介绍或非必要措辞不算关键缺失。

### 6.4 正常新增

正常新增草稿应与现有知识有业务关联和关键词重叠，但包含稳定、明确、可执行且没有冲突的新事实，用于检验 Agent 是否会过度报告重复、矛盾或缺失。

## 7. 数据生成要求

1. 全部内容使用公开虚构数据，不得包含真实公司名称、Wiki 原文、代码、服务器地址、账号或凭据。
2. 正式文档统一使用 `PUBLISHED` 状态；候选草稿统一使用 `DRAFT` 状态。
3. 文档使用中文 Markdown，包含标题、简短背景、规则正文和必要的列表或步骤。
4. 每篇文档只围绕一个主要主题，不生成综合性百科文档。
5. 正式文档必须严格遵守统一事实基线，不得自行改变上传大小、重试次数、角色权限或发布流程。
6. 不要为了提高检索难度堆砌无关文字；通过同义表达、共享业务词汇和相邻主题形成自然干扰。
7. 候选草稿中的问题必须自然隐藏在业务描述中，不输出问题类型和期望处理。
8. `DRAFT-01`～`DRAFT-06` 每篇只植入表格指定的主要问题，避免一篇同时包含多个无法区分的问题。
9. `DRAFT-07`～`DRAFT-08` 必须保持无重复、无矛盾、无关键缺失，用作误报对照。
10. 8 篇草稿必须是 8 次独立完整提交，不生成额外变体，也不把多篇草稿合并成一个评估输入。
11. 每篇文档输出稳定的文档 ID、标题、目录、状态、范围、更新时间和 Markdown 正文。
12. 本阶段不生成问答题、标准答案、评估标签文件或指标结果。

## 8. 建议输出结构

```text
atlas-eval-documents/
├── manifest.json
├── published/
│   ├── DOC-01.md
│   ├── DOC-02.md
│   └── ...
└── drafts/
    ├── DRAFT-01.md
    ├── DRAFT-02.md
    └── ...
```

`manifest.json` 建议记录：

```json
{
  "datasetVersion": "atlas-agent-eval-v1",
  "project": "atlas",
  "documents": [
    {
      "documentId": "DOC-01",
      "title": "Atlas 产品概览与核心术语",
      "directory": "产品介绍",
      "status": "PUBLISHED",
      "scope": "PROJECT",
      "project": "atlas",
      "file": "published/DOC-01.md"
    }
  ]
}
```

候选草稿的隐藏判断和期望处理仅用于后续评估集标注，不应写入候选 Markdown 正文，也不应作为可见元数据提供给被评估 Agent。
