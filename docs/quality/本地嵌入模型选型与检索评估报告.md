# 本地嵌入模型选型与检索评估报告

## 1. 结论

在当前 LoreDock 的本地 CPU、ONNX Runtime 和 512 token 配置下，`BAAI/bge-small-zh-v1.5` 更适合作为默认在线检索模型：单条用户问题的向量化 P95 约 2.7 ms，模型文件约 90.5 MiB，QA 检索 Top-5 命中率为 35/36（97.22%）。

`BAAI/bge-base-zh-v1.5` 的离线 QA 检索结果略好，Top-5 命中率为 36/36（100%），但单条查询向量化 P95 约 10.7 ms，模型文件约 388 MiB，运行时堆增量约为 small 的 4.1 倍。当前建议保留 base 作为对召回质量要求更高的离线评估或专用实例选项，默认仍使用 small。

## 2. 评估范围

本次只评估检索相关能力，不包含在线 Agent、LLM 生成答案、在线 Judge 或 Web 端到端请求。

- 数据集：40 条 Atlas QA 问题，14 份已发布知识文档。
- 可度量问题：36 条带人工标注正确文档的问题；其余问题用于无答案或边界场景，不计入命中率分母。
- 检索方式：问题向量化后，在内存中对文档向量计算相似度并排序。
- 模型运行：本地 ONNX Runtime，CPU 推理，最大输入长度 512 token。
- small 输出：`sentence_embedding`，512 维。
- base 输出：`last_hidden_state`，取 CLS 向量后做 L2 归一化，768 维。
- 评估限制：排序阶段使用 14 份文档的内存数据，不能直接等同于 PostgreSQL/pgvector SQL 查询耗时。

## 3. 检索质量结果

| 指标 | `bge-small-zh-v1.5` | `bge-base-zh-v1.5` |
|---|---:|---:|
| 向量维度 | 512 | 768 |
| 可度量问题数 | 36 | 36 |
| Hit@5 | 35/36（97.22%） | 36/36（100%） |
| MRR | 0.8975 | 0.9259 |
| 唯一未命中 | QA-025，正确文档排第 9 | 无 |

在这份数据集上，base 的召回质量略高：Hit@5 提升 2.78 个百分点，MRR 提升约 0.0284。但样本规模有限，不能据此宣称 base 在所有业务语料上都稳定优于 small，正式选型仍应结合真实知识库抽样集复测。

## 4. 单条用户问题的嵌入耗时

下表只统计“问题文本 → 查询向量”，不包含数据库检索、RRF 混合、网络和 LLM 生成。

| 指标 | `bge-small-zh-v1.5` | `bge-base-zh-v1.5` | base / small |
|---|---:|---:|---:|
| P50 | 1.981 ms | 9.359 ms | 4.72 倍 |
| P95 | 2.700 ms | 10.668 ms | 3.95 倍 |
| 平均 | 2.122 ms | 9.549 ms | 4.50 倍 |

面试口径可以直接说：在相同本地 CPU 和 ONNX Runtime 配置下，单条查询的向量化耗时，small 约 2～3 ms，base 约 9～11 ms，base 大约是 small 的 4～5 倍。

## 5. 离线 QA 检索延迟与资源

| 指标 | `bge-small-zh-v1.5` | `bge-base-zh-v1.5` | base / small |
|---|---:|---:|---:|
| 查询嵌入 P95 | 2.700 ms | 10.668 ms | 3.95 倍 |
| 内存排序 P95 | 0.121 ms | 0.174 ms | 1.44 倍 |
| 单次检索总耗时 P95 | 2.883 ms | 11.215 ms | 3.89 倍 |
| 14 份文档嵌入总耗时 | 254 ms | 1,225 ms | 4.82 倍 |
| JVM 堆增量 | 约 102 MiB | 约 422 MiB | 4.14 倍 |
| 模型文件大小 | 约 90.5 MiB | 约 388 MiB | 4.29 倍 |
| 14 个向量的理论存储 | 28,672 bytes | 43,008 bytes | 1.50 倍 |

冷启动时间受 JVM、ONNX Runtime 和操作系统缓存影响较大，本次记录的数值波动明显，不作为主要选型指标。生产部署应单独监控模型初始化耗时、常驻内存、查询 P50/P95 和索引重建耗时。

## 6. 500 份文档耗时的换算口径

内网使用 small 处理 500 份文档耗时“两百多秒”，这个数字更接近批量导入或索引重建的端到端成本，可能包含文档读取、切分、批量嵌入、数据库写入和索引处理，不能直接作为单条用户问题的嵌入耗时。

如果只为了估算同一配置下的批量嵌入规模，可以使用：

```text
small 平均每个文档处理单元耗时 ≈ T500 / 500
base 平均每个文档处理单元耗时 ≈ (T500 / 500) × 4.8
```

其中 `T500` 是 500 份文档的实际总耗时，且“文档处理单元”必须统一为文档或切分后的 chunk。若 500 份文档最终切成了更多 chunk，应使用 `T500 / chunk 数量`，不能使用 `T500 / 500`。

这个换算用于容量规划，不用于回答“单条用户问题多久”。单条查询应以第 4 节的 warmed P50/P95 为基线，再叠加实际 pgvector 查询和网络耗时。

## 7. 模型选型原因

选择 `bge-small-zh-v1.5` 作为默认模型，主要是因为 LoreDock 的检索场景更看重本地部署下的综合成本：

1. **质量已经满足当前检索目标。** 在本次 36 条可度量 QA 上，small 的 Hit@5 为 97.22%，只出现 1 条进入 Top-5 之外的结果；当前项目还使用关键词检索与向量检索的混合策略，可以进一步降低单一语义模型偶发漏召回的影响。
2. **查询延迟更低。** small 的单条问题嵌入 P95 约 2.7 ms，base 约 10.7 ms。在线问答会为每次请求生成查询向量，small 能把更多延迟留给真正的数据库检索和答案生成。
3. **本地资源占用更小。** small 模型约 90.5 MiB，base 约 388 MiB；实测 JVM 堆增量约为 102 MiB 对 422 MiB。对于内网部署、普通 CPU 机器和多实例扩展，small 更容易控制内存和冷启动风险。
4. **向量存储和迁移成本更低。** 512 维向量比 768 维向量少 33.3% 的浮点存储，索引重建、备份和跨环境迁移的成本也更低。
5. **base 保留为质量优先选项。** 当真实业务评估集持续出现 small 的 Top-k 漏召回，或者部署环境具备更充足的内存并且可以接受约 4～5 倍的嵌入耗时时，再切换 base；切换前必须重新生成全量文档向量，不能混用两个模型的向量。

因此当前决策是：**small 默认上线，base 作为质量优先的对照模型和后续可切换方案；是否切换由真实业务 QA 集的 Hit@k、MRR、P95 延迟和内存预算共同决定。**
