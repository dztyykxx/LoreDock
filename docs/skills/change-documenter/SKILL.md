# 需求实现文档提炼

将一次已经完成的开发整理成可复用的业务实现说明，让后续开发者知道“这类需求怎么落地、要改哪里、容易踩什么坑”。不要写抽象规范，也不要逐文件复述 Diff。

## 工作流程

### 1. 确认分析范围

收集本次需求描述、开发会话、Git 变更范围、测试结果和必要的现有文档。只执行只读 Git 检查；范围不明确时，先确认基线分支、起止提交或目标 PR。

### 2. 明确交付结果

先说明业务背景、用户目标、本次实际完成的能力和明确未完成的内容。以最终代码行为为准，不把需求中尚未实现的设想写成现状。

### 3. 还原完整业务流程

沿真实执行路径描述流程：

```text
用户操作或任务触发
→ 接口、命令或定时任务入口
→ 参数与业务校验
→ 核心业务处理
→ 数据库读写
→ 异步任务或外部系统
→ 状态变化
→ 最终结果或失败处理
```

每一步说明“做了什么、为什么需要、下一步流向哪里”。复杂流程可分正常路径和关键失败路径。

### 4. 定位关键实现

按业务职责整理真正影响流程的修改：

- 前端入口、交互与状态展示；
- Controller、API、命令或任务入口；
- Service 中的业务编排、校验和状态变化；
- Mapper、SQL、Flyway 迁移与数据初始化；
- 模型、枚举、配置和外部依赖；
- 保护核心流程的测试与验证证据。

只列关键文件、类、方法或配置，并解释它们在业务流程中的作用。

### 5. 单独检查 SQL 与配置

主动检查以下内容，不能因为代码 Diff 不显眼而遗漏：

- 表、字段、索引、约束和 Flyway 迁移；
- 初始化数据、字典数据或产品包相关 SQL；
- Mapper 查询或更新语句；
- YAML、properties、JSON、环境变量和功能开关；
- 权限、存储、定时任务和外部服务配置。

说明每项变更的用途、执行顺序、适用环境，以及漏改后的影响。没有变更时明确写“无”。

### 6. 提炼踩坑与决策

从开发会话、失败测试、错误日志、返工记录和最终实现中提取：

- 最初理解或方案哪里不准确；
- 漏掉了哪些代码、SQL、配置或状态；
- 框架、事务、异步、数据兼容有哪些限制；
- 最终如何修复；
- 下次怎样更早发现或避免。

只记录有证据的真实问题，不为了充实文档编造踩坑。

### 7. 形成复用清单

把本次实现抽象成下一次同类需求可直接执行的步骤，至少覆盖入口、核心逻辑、数据、SQL、配置、状态、异常和测试。只提炼已经验证过的做法。

## 输出要求

- 用户指定文件路径时写入该路径，否则直接输出 Markdown；
- 保留业务流程和关键技术触点，不生成完整 Diff 清单；
- 不泄露密钥、连接串、内部地址、完整业务数据或无关代码；
- 只生成待审核文档，不自动发布知识或处理平台侧冲突；
- 不切换、修改或提交用户分支，除非用户明确要求。
