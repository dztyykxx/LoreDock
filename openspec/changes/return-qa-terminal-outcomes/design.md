## Context

参见 `proposal.md` 的问题说明。现有 `project_qa` 规格已经要求无证据时返回 `COMPLETED/REFUSAL`，但运行适配器把模型调用数与工具调用数共同计入 8 步预算；模型在空检索后继续请求工具时，下一次调用会被拒绝并形成 `TERMINATED/AGENT_STEP_LIMIT_EXCEEDED`。当前执行台账只保存证据和计数，没有区分“至少一次检索成功但无合格证据”与“检索本身失败”。

运行时只在最终结构化结果通过校验后发布 `ANSWER_DELTA` 或 `REFUSAL`，失败/终止运行不会生成公开助手消息。这一安全边界必须保留。Web 详情当前只返回 `errorCode`，前端失败面板再用不完整的本地映射生成文案，因此步骤上限直接落入通用“运行未形成可信结果（错误码）”。

Pencil `04 · 项目问答 / 引用展开` 与 UI Kit 已把“当前知识库没有足够依据”定义为正常可信状态。现有 HTTP/SSE 均以持久化运行快照为事实来源，终态事件后客户端会重新读取详情，适合由详情统一提供失败说明。

### 与后端精简重构的边界

本 change 已确认的问答终态、SSE 续读、引用/拒答和失败文案属于后续实现必须保持的行为基线。后续包结构、接口收敛、Agent Runtime 框架接入、持久化表精简和自增主键改造统一由 `simplify-backend-mvc-runtime` change 接管；本 change 不再为这些结构调整新增旧式 `application/domain/infrastructure` 分层、单实现 Port/Gateway 或 Skill 数据库版本能力。

尚未完成的本地真实模型烟雾验证仍保留在本 change 的 4.4，不能用结构重构替代，也不能在缺少实际模型结果时标记完成。

## Goals / Non-Goals

**Goals:**

- 在不依赖模型自觉停止的前提下，让“成功检索但没有合格证据”的工具循环安全收敛为模板化拒答。
- 保留运行故障与业务拒答的语义区别，不能把模型、工具、权限或版本故障伪装成知识库没有内容。
- 由服务端提供稳定、脱敏的失败说明，使刷新、重连和不同 Web 客户端得到相同文案。
- 保持现有运行、事件、消息投影、引用校验与项目/分支隔离边界。

**Non-Goals:**

- 不提高默认步骤或模型调用上限，也不取消任何资源保护。
- 不公开模型中间消息、思维链、异常原文或未经引用校验的文本。
- 不新增数据库表或修改历史问答记录，不把失败运行保存为助手消息。
- 不处理多轮会话、ID 生成策略或 SSE 异步 Sa-Token 上下文异常。

## Decisions

### 1. 用执行台账的“成功空检索”事实提供确定性拒答兜底

扩展运行内执行台账，除现有证据、检索数量和裁剪量外，再记录成功完成的检索调用数以及保留的合格证据数。只有同时满足以下条件时，步骤/模型调用预算阻止下一次调用将被收敛为服务端模板化结果：

1. 当前异常语义是 `AGENT_STEP_LIMIT_EXCEEDED` 或 `AGENT_MODEL_CALL_LIMIT_EXCEEDED`；
2. 至少一个允许的检索工具已经成功完成；
3. 当前运行没有任何可保留、可引用的合格证据；
4. 本轮没有工具故障、权限变化或证据版本变化。

兜底结果固定为 `REFUSAL/INSUFFICIENT_EVIDENCE`，正文使用领域层已有“当前知识库没有足够依据”模板，引用为空，再进入现有 `ProjectQaResultValidator`、完成事务和 `REFUSAL → RUN_COMPLETED` 事件路径。它不绕过最终校验，也不会发布被丢弃的模型内容。运行使用量仍记录实际已执行步骤和模型调用；结构化日志增加 `terminalOutcome=INSUFFICIENT_EVIDENCE` 和成功空检索数量，证明为何没有按资源故障终止。

模型不可用、响应无效、工具异常、范围违规、版本变化、超时，以及已经取得合格证据却仍不能完成回答的预算耗尽，继续保留原失败/终止错误。这样“查询成功但没有内容”与“系统没有成功查询”不会混淆。

备选方案是单纯把 `max-steps` 从 8 提高到更大值；它只会延迟同一循环。另一方案是在第一次空检索后立即拒答；它会阻止模型改写查询或查询另一种允许来源，因此仅以运行预算边界上的严格条件做最终兜底。

### 2. Skill 升级为 1.0.1，并把范围可用性和停止规则显式交给模型

内置 `project_qa` Skill 升级到 `1.0.1`，说明以下规则：

- 固定范围包含当前分支是否有活动代码快照；没有快照时不得调用代码搜索或片段读取。
- 一个证据类别完成必要检索但无合格结果时，不重复相同或等价查询；没有其他可用证据类别时立即输出 `INSUFFICIENT_EVIDENCE`。
- 询问具体实现且明确无活动快照时输出 `CODE_SNAPSHOT_NOT_INDEXED`。

模型指令中的固定范围摘要增加 `codeSnapshotAvailable`，但不加入服务器路径、对象键或内部 generation。版本必须递增，不能在 `1.0.0` 下修改内容哈希；启动引导在同一短事务中退役旧启用版本并发布新版本，已经启动的运行继续使用其固定的旧内容。

Skill 规则用于减少无效调用，决策 1 的服务端兜底用于保证最终行为，两者缺一不可。只修改提示词无法对模型行为提供确定性保证；只做兜底则每次空结果仍会浪费完整预算并降低响应速度。

### 3. HTTP 详情增加服务端生成的可空 `failureMessage`

先扩展问答响应契约，在 `WebQaQuestionResponse` 与前端 `QaQuestion` 增加可空 `failureMessage`：

- `COMPLETED`（回答或拒答）返回 `null`，用户可见正文继续使用 `resultText`。
- `FAILED` 或 `TERMINATED` 根据 `AgentErrorCode` 的完整白名单返回稳定中文说明。
- `ACCEPTED` 或 `RUNNING` 返回 `null`。

映射采用穷尽的服务端错误码映射，不读取异常对象或数据库自由文本。步骤上限文案明确“本次检索已达到运行上限，尚未形成可信回答”，并建议缩小问题范围或使用新运行重试；模型不可用、队列繁忙、超时、版本变化和内部错误分别提供安全且可操作的说明。未知或未来错误使用统一安全兜底，并记录结构化告警以提示维护者补齐映射。

该字段是 JSON 响应的可空新增字段，不修改路由、请求或状态码；现有客户端忽略未知字段即可兼容。终态 SSE 继续只发送稳定 `errorCode`，客户端按现有流程读取详情后获得最终 `failureMessage`，避免在 SSE 与 HTTP 中维护两份文案。

备选方案是由 Vue 直接映射错误码。服务端映射能保证刷新恢复、未来其他 Web 客户端和测试使用同一公开语义，也避免将内部异常原文意外送到页面。

### 4. 前端按可信状态选择正文来源，不混用部分文本

回答面板保持三条互斥路径：

- `IN_PROGRESS`：只显示阶段和允许的流式状态。
- 已完成回答/拒答：显示 `resultText`、拒答原因、快照状态、来源和知识缺口入口。
- `FAILED`：显示 `failureMessage` 为主要正文、适用的重试/浏览入口，并把 `errorCode` 放在次要诊断位置。

终态刷新时继续用服务端详情覆盖 `partialText`；失败或终止时必须清空或忽略本地部分文本。现有“失败运行不生成 ASSISTANT 消息”的投影策略不变，因此页面上出现的失败说明是运行终态展示，不是被保存为可信回答的助手消息。

Pencil 已有回答主区、状态徽标和操作入口，本次只调整状态内容层级，不新增页面结构；不修改 `.pen` 源稿。

### 5. 按业务事实分层测试，不用提高限制掩盖问题

测试先于实现并使用中文注释和实际证据日志：

- 运行适配器测试：脚本模型在成功空检索后持续调用工具，断言最终为 `COMPLETED/REFUSAL`、原因 `INSUFFICIENT_EVIDENCE`、无引用且实际调用不超过固定预算。
- 反例测试：已有合格证据后仍耗尽预算、工具异常和模型异常继续为原失败/终止错误，不被转换为拒答。
- Skill 引导集成测试：`1.0.1` 成为新运行启用版本，旧 `1.0.0` 保持可读，同版本内容冲突仍失败。
- Web 契约/持久化集成测试：失败详情返回脱敏 `failureMessage`，完成拒答返回 `resultText` 且 `failureMessage=null`，失败运行不产生助手消息。
- 前端组件和 composable 测试：拒答正文、步骤上限说明、错误码次要显示、终态刷新清除部分文本以及重试使用新幂等键。

## Risks / Trade-offs

- [模型可能使用多个不同查询仍然没有命中，直到预算边界才触发兜底] → Skill 1.0.1 禁止无新证据价值的重复检索；服务端兜底保证最终仍是拒答，日志保留实际调用数量供后续调优。
- [把预算耗尽误判为无证据] → 只在至少一次检索成功、零合格证据且没有其他执行错误时转换；一旦有合格证据或基础设施失败便保留资源/故障终态。
- [新增错误码后遗漏公开文案] → 使用穷尽映射测试和安全兜底，未知码不暴露原始异常并记录告警。
- [Skill 版本升级影响在途运行] → 运行已固定内容哈希和对象键；只让新运行选择 1.0.1，不改写历史记录。
- [用户把失败说明误认为可信回答] → 保持 `trustState=FAILED`、失败徽标和无助手消息，仅在同一回答区域提供解释，不展示来源或回答依据标签。

## Migration Plan

1. 先发布兼容读取 `failureMessage` 的前端；字段缺失时继续使用本地安全兜底文案。
2. 发布后端契约与错误文案映射，再发布运行台账兜底和 `project_qa` Skill 1.0.1；无需 Flyway 迁移。
3. 启动后确认 Skill 引导日志显示 1.0.1 可用，并用一个无已发布知识、无活动快照的测试项目验证终态为 `COMPLETED/REFUSAL`。
4. 验证模型不可用和已有证据后预算耗尽仍分别保持失败/终止，且详情提供脱敏说明。

回滚时可回退应用包；新增 JSON 字段对旧客户端无破坏。数据库中的 Skill 1.0.1 和历史运行保留，旧包仍可读取兼容的 Skill 内容与运行记录，不删除版本或问答数据。
