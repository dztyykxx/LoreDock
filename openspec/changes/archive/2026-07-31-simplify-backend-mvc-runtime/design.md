## Context

参见 `proposal.md` 的问题与范围。当前后端生产代码约 630 个 Java 文件，其中 `agent` 模块约 92 个文件、4665 行；Agent 核心已经调用 Spring AI Alibaba `ReactAgent`，但只有极少数类直接使用 Spring AI/Spring AI Alibaba，大量调度、运行事件、工具台账、Skill 发布和恢复逻辑由项目自行实现。

当前数据库约 24 张业务表并广泛使用 UUID 主外键。项目尚处于可重建开发数据库的快速迭代阶段，因此不承担生产数据在线迁移兼容成本。现有 HTTP 核心能力、范围隔离、知识发布边界、引用和拒答语义必须保持。

## Goals / Non-Goals

**Goals:**

- 将功能模块内部统一为可自动检查的 MVC 结构，缩短 Controller 到业务和持久化的调用路径。
- 保留模型、Embedding、Agent Runtime、Agent 定义和外部存储等真实替换边界。
- 让 Spring AI/Spring AI Alibaba 承担通用模型与 Agent 运行机制，LoreDock 只维护产品特有规则。
- 将业务表主外键统一为自增 `Long`，并减少无独立生命周期的数据表。
- 保持核心链路可运行，并为后续多 Agent 知识挖掘留下可组合、可检查点恢复的运行时。

**Non-Goals:**

- 不在本 change 内实现知识挖掘 Agent、动态 Agent Marketplace、模型管理后台或在线 Skill 编辑发布。
- 不保留旧开发数据库中的 UUID 数据，也不提供新旧包结构的长期兼容层。
- 不用删除文件数、接口数或表数作为单独验收目标；只有职责和行为允许时才合并或删除。
- 不改变现有项目、分支、知识、代码、问答和反馈 API 的业务语义，除 ID 从 UUID 改为数值标识外。

## Decisions

### 1. 采用“功能模块 + 模块内严格 MVC”

目标模块为 `auth`、`project`、`knowledge`、`code`、`agent`、`qa`、`feedback`；`storage` 和 `job` 可作为独立技术能力模块，但其代码仍按 MVC 职责归类，不创建空层。真正跨模块的配置、Web 错误、时间与 MyBatis 类型支持放入最小 `common`。

模块根下按实际职责使用以下结构，不要求创建空包：

```text
<feature>/controller
<feature>/service
<feature>/service/impl
<feature>/mapper
<feature>/model/{entity,request,response,command,result,tool,snapshot,enums}
<feature>/{config,exception,scheduler,converter,skill}
```

其中 `service` 只保存业务服务及流程，`mapper` 只保存 MyBatis-Plus Mapper 接口，所有跨层数据载体按语义进入 `model` 子包；简单转换留在 Service，只有复杂或复用转换才建立 Converter。依赖方向固定为：

```text
Controller -> Service -> Mapper
                    -> OtherFeatureService
```

Controller 不访问 Mapper，Service 不访问其他模块 Mapper，HTTP DTO 不进入 Mapper。删除 `application/domain/infrastructure` 不是简单移动目录，而是同时消除只做委托的 UseCase、Port、Repository Adapter 和 Converter。

替代方案是保留现有能力内分层，仅合并小类；该方案无法解决新增功能跨多层修改的问题，因此不采用。

### 2. 接口按真实替换边界保留，不按实现数量机械判断

保留以下接口：

- `AgentRuntime`：隔离业务任务与具体 Agent 框架。
- `AgentDefinitionProvider`：当前 classpath 实现，未来可增加数据库或远程定义实现。
- Spring AI `ChatModel`：聊天模型标准替换边界。
- Spring AI `EmbeddingModel`：Embedding 推理标准替换边界。
- 对象存储等已经存在真实本地/外部替换需求的能力。
- MyBatis Mapper。

删除以下接口：

- Controller 前的单实现 UseCase。
- Mapper 前的 Repository 与 MyBatis Adapter。
- 只转发一次调用的 Gateway、Registry、Coordinator。
- 仅为 Mock 创建且没有业务或外部边界的接口。

测试替身优先围绕保留的模型、Agent Runtime 和外部系统边界构建，不为每个 Service 机械创建接口。

### 3. 统一使用 Spring AI 模型接口

Agent Service 注入 Spring AI `ChatModel`，由配置类按部署配置装配具体模型。只有实际出现“同一进程按 Agent 动态选择多个模型”的需求时，才增加返回 `ChatModel` 的 `ChatModelProvider`。

现有 ONNX Embedding 适配器改为实现 `EmbeddingModel`，只负责批量推理。标题、标签、正文组合、查询指令、索引模型摘要和维度一致性由 `KnowledgeEmbeddingService` 负责，避免通用模型接口携带知识业务语义。

替代方案是保留项目自定义 `KnowledgeEmbeddingPort` 和完整 `DeepSeekChatModelFactory`；这会继续复制 Spring AI 已有抽象并增加供应商耦合，因此不采用。供应商特有的必要参数仍可留在 Bean 装配配置中。

### 4. Agent Runtime 采用“框架运行时 + LoreDock 业务外壳”

`SpringAiAlibabaAgentRuntime` 负责创建和调用 `ReactAgent` 或 Flow Agent。框架与项目职责如下：

| 能力 | 负责方 |
|---|---|
| ReAct 循环、单/多 Agent 编排、Graph 状态 | Spring AI Alibaba |
| 模型/工具调用限制、重试、Fallback、上下文 Hook | Spring AI Alibaba Hook/Interceptor |
| ToolCallback、流式执行、Checkpoint | Spring AI/Spring AI Alibaba |
| 用户权限、项目/分支、活动快照、知识 generation | LoreDock Service |
| 工具返回裁剪、证据来源、引用与拒答校验 | LoreDock Agent Service |
| 运行业务状态、公开进度、最终结果 | LoreDock Agent Service/Mapper |

运行流程为：

```text
AgentController / QaController
  -> AgentRunService（短事务接受运行）
  -> AgentRuntime（事务外执行框架 Agent）
  -> KnowledgeService / CodeService 工具
  -> AgentRunService（短事务保存进度、证据和终态）
```

现有 `ProjectQaToolRegistry` 可由明确注册的 `ToolCallback` 集合替代；只注册允许工具本身即形成白名单，LoreDock Service 继续在每次调用时校验固定范围。现有手工模型/工具计数优先由框架 Hook 提供；只有框架未暴露但产品必须展示的用量才做薄采集。

### 5. Agent 定义使用 classpath，不建设当前无用的版本管理

内置 `project_qa` 及后续 Agent 定义存放在 classpath，由 `ClasspathAgentDefinitionProvider` 加载和启动时校验。运行记录保存 Agent 名称、模型名称、必要配置摘要和固定业务范围，不保存 Skill 数据库版本 ID、内容对象键、发布状态、工具策略版本或限制策略版本。

删除 `agent_skill_version`、对象存储 Skill bundle、发布器、启用目录和配套 Repository/Mapper。未来出现在线编辑、灰度启用或历史复现的明确需求时，再增加 `AgentDefinitionProvider` 的数据库实现并建立独立规格。

代码 Commit、活动代码快照、知识索引 generation 和 Flyway 版本继续保留，因为它们直接决定证据范围或数据库兼容性；它们只是运行事实，不演化为通用版本平台。

### 6. Agent 持久化只保存产品需要的事实

保留并精简：

- `agent_run`：任务类型、操作者、固定范围、状态、模型/配置摘要、用量、最终结果、错误和时间。
- `agent_run_event`：单调序号和粗粒度对外事件，仅用于进度观察和断线续读。
- `agent_evidence`：知识或代码来源、相关度、范围、引用状态和引用顺序；合并原 `agent_citation`。

删除：

- `agent_skill_version`：当前没有动态版本管理需求。
- `agent_tool_call`：工具内部调用优先通过框架 Observation、stdout 和结构化日志观察，不为每次调用维护业务表。
- 独立 `agent_citation`：引用标志和顺序合并到证据记录。

Web 问题和用户可见答案继续属于 `qa` 模块；`qa` 记录引用 `agent_run.id`，避免把完整用户问题复制到运行追踪表。

### 7. 框架 Checkpoint 由 Flyway 建兼容表

短 Web 问答默认可配置为不可恢复，进程重启后单调终结。后续长任务可声明为可恢复，并使用 Spring AI Alibaba `PostgresSaver` 从最后 Checkpoint 继续。

为遵守 Flyway 唯一建表和自增主键规则：

- Flyway 创建与锁定版本 `PostgresSaver` 兼容的 `graphthread`、`graphcheckpoint` 表。
- 表以 `BIGINT GENERATED BY DEFAULT AS IDENTITY` 为主键。
- 框架需要的 thread/checkpoint UUID 作为唯一普通列。
- Saver 使用项目 `DataSource` 和 `CreateOption.CREATE_NONE`。
- 通过集成测试锁定当前依赖版本实际使用的列与 SQL；升级框架时先跑兼容测试。

不自行重新实现 Checkpoint Saver。替代方案是沿用 `MemorySaver` 加自定义恢复表，但它无法真正恢复 Graph 且会继续维护两套运行状态，因此不采用。

### 8. 数据库以新基线重建并同步压缩表

本阶段采用破坏性开发库重建，不编写 UUID 到 Long 的在线数据转换。新的 Flyway 基线统一使用自增主键和显式外键，所有 Entity 使用 `Long` 与 `IdType.AUTO`。

除 Agent 表调整外，按以下原则压缩现有表：

- 文档标签没有独立生命周期时合并为文档字段。
- 导入条目只用于展示批次结果时合并为批次结果 JSON。
- 索引构建可直接读取正式文档时删除重复文档投影表。
- 知识索引和搜索 generation 表表达同一原子切换时合并。
- 已有独立状态、重试或查询需求的项目、分支、文档、代码快照、后台任务、对象存储和知识缺口记录继续保留。

最终表数不是验收目标；每张保留表必须有独立生命周期、完整性约束或必要查询价值。

### 9. 保持 HTTP 业务语义，仅同步 ID 类型

既有 API 路径、权限、幂等性、范围和错误码保持。UUID 主键字段改为数值 ID 后，后端 DTO、前端 TypeScript 类型、路由参数和 API 客户端同步更新。代码 Commit、项目 identifier 和分支名等自然业务标识保持字符串。

正在进行的 `return-qa-terminal-outcomes` 先作为问答终态行为基线：实施本 change 时保留其已经确认的终态和 SSE 语义，但不继续复制其旧分层和持久化结构。

### 10. 采用核心链路优先的迁移顺序

先建立可重复核心冒烟，再删除确定无用的版本管理和死代码；随后按 `auth -> project -> storage/job -> knowledge -> code -> agent -> qa -> feedback` 转换 MVC。包结构稳定后一次性切换数据库基线和 `Long` ID，最后替换 Agent Runtime 内部并清理残余旧包。

每个阶段必须保持可编译；若数据库基线切换造成不可避免的短暂破坏，必须在同一任务批次内完成后端、前端和测试的 ID 更新后再交付。

## Risks / Trade-offs

- [大范围移动容易产生长时间不可编译状态] → 按模块迁移并设置每阶段编译门禁，数据库 ID 切换单独作为原子批次。
- [删除接口可能误伤模型或运行时替换能力] → 先维护接口分类清单，只删除无法指出第二实现、外部边界或稳定业务契约的接口。
- [框架能力与当前版本行为不完全一致] → 基于锁定依赖编写最小兼容性测试，验证流式输出、结构化结果、Hook、ToolCallback 和 PostgresSaver 后再删除现有实现。
- [框架 Checkpoint 表结构升级可能变化] → 以 `CREATE_NONE` 和 Flyway 管理结构，升级依赖前执行 Saver SQL 兼容测试。
- [粗粒度事件可能降低内部调试细节] → 内部步骤使用框架 Observation、stdout 和日志，业务事件只承担对外进度与续读。
- [开发库重建会丢失本地数据] → 明确备份/重建说明和演示数据脚本；当前不承诺自动迁移可丢弃数据。
- [表合并可能降低临时分析便利性] → 只有无独立生命周期和查询价值的数据才合并，核心范围与引用字段保持关系约束。

## Migration Plan

1. 记录当前核心 API、数据库和 Agent/QA 冒烟结果，处理与活动 change 的行为重叠。
2. 增加架构约束测试和目标包骨架，按模块完成 MVC 收敛与接口清理。
3. 删除 Agent Skill/策略版本管理和确认无入口的半成品，保持现有问答行为。
4. 建立新 Flyway 基线，重建开发数据库，同步后端、前端和测试的 `Long` ID。
5. 将模型和 Embedding 接入 Spring AI 标准接口，并以框架能力替换重复 Agent 运行机制。
6. 精简 Agent 及其他无独立价值的数据表，接入 Flyway 管理的框架 Checkpoint。
7. 运行空库启动、真实 PostgreSQL 集成测试、前后端构建和核心端到端冒烟。
8. 更新开发计划、架构说明和本地数据库重建文档。

回滚以 Git 回退代码并重建旧开发数据库为单位，不提供新旧数据库结构的原地双向转换；执行数据库重建前应提示开发者备份需要保留的本地数据。
