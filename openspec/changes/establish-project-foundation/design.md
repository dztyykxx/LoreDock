## Context

仓库当前只有文档与 OpenSpec 配置，没有可运行代码或既有数据库，因此本变更可以建立干净的工程基线，不承担旧接口或旧数据兼容。设计依据 `proposal.md`、四份增量规格、MVP 需求基线第 10 节，以及 Java 技术栈建议第 3、10～12 节。

T1 是后续所有任务的依赖：这里形成的错误结构、时间与审计约定、对象存储端口和后台任务状态机将被 Web、内部服务和 MCP 复用。公开仓库不得包含真实内部地址、凭据、Wiki 原文或公司代码，所有默认配置和测试夹具只能使用虚构数据。

## Goals / Non-Goals

**Goals:**

- 形成后端、前端、数据库和持久化卷边界清楚的单体 MVP 工程。
- 先定义稳定契约，再通过最小实现和真实 PostgreSQL 集成测试建立可信基础。
- 让失败可以被调用方识别、被运维定位，并且不泄露敏感信息。
- 让后续导入和索引任务能够复用持久状态与受控并发，而不引入消息队列。

**Non-Goals:**

- 不在 T1 建立认证授权、项目/分支、知识、代码快照或检索领域模型。
- 不实际接入 MiniMax、Embedding、Lucene 索引或 MCP，只在构建中冻结其兼容版本线。
- 不实现 S3 适配器、分布式任务调度、任务自动重试或多实例协调。
- 不引入 Spring Batch、消息队列、MinIO、Spring Cloud 或 Kubernetes。

## Decisions

### 1. 采用后端与前端分目录的单体仓库

根目录包含 `backend/`、`frontend/`、`compose.yaml` 和统一说明；后端使用 Maven Wrapper 的单个 Spring Boot 应用，前端使用锁文件和仓库声明的包管理器。后端首先按 `platform`、`storage`、`job` 等能力分包，每个业务能力内部固定使用 `domain`、`application`、`infrastructure` 分层。HTTP Controller 等输入适配器放在 `platform.web` 或对应能力的 `infrastructure.web`，MyBatis-Plus 与文件系统实现只放在 `infrastructure`。依赖方向为基础设施 → 应用 → 领域，领域和应用不得反向依赖具体 Mapper、数据库或文件路径实现。T1 不拆多 Maven 模块。

这样既保留清楚边界，又避免在尚无业务代码时承担多模块构建复杂度。项目不采用把全部能力横向堆入全局 `controller/service/mapper` 的传统 MVC 目录；Web 只是多个输入通道之一，后续 MCP 与后台任务应复用同一应用和领域能力。备选的前后端独立仓库会增加版本和本地联调成本；后端多模块方案目前也没有足够的替换边界支撑。

### 2. 在实现开始时建立并记录精确版本矩阵

Java 固定为 21；Spring Boot、Spring AI、pgvector 和 Lucene 使用技术调研建议的正式版本线，并在开始写行为实现前解析公司构建环境可获得的最新兼容 GA 补丁版本。实际选中的精确版本分别锁定在 Maven 属性/BOM、容器镜像摘要或完整标签、Node 版本文件和前端锁文件中，同时记录到 README 的版本矩阵。MyBatis-Plus 与 Lombok 也必须使用与 Spring Boot 4.1、Java 21 兼容的精确 GA 版本。构建启用版本约束检查，禁止动态版本、SNAPSHOT 和 Milestone。

Spring AI 和 Lucene 在 T1 只进入依赖管理，不引入未使用的运行时 Starter；这样既冻结后续兼容基线，也避免提前初始化模型或索引基础设施。若公司内网不能获得首选 Spring Boot 4.1.x + Spring AI 2.0.x，必须先更新本 change 的设计与任务，再采用调研文档定义的兼容线，而不是在代码中静默降级。

### 3. Docker Compose 只提供依赖服务，前后端在宿主机开发

Docker Compose 只承载带 pgvector 的 PostgreSQL 以及后续确有需要的中间件，不构建或运行本地开发用的后端、前端镜像。统一开发脚本负责启动/检查 Compose 依赖，并以宿主机 Java 21 运行 Spring Boot、以仓库声明的 Node/npm 运行 Vite；这样保留热更新和调试体验，同时避免为开发进程增加容器构建等待。

后端只有在 Flyway 校验和数据库连接成功后才就绪，前端通过本地代理访问后端并展示最小运行状态页。配置通过环境变量注入，仓库只提交 `.env.example`，任何密钥都不得带真实默认值。生产部署是否容器化不在 T1 范围内，后续部署规格另行决定。

### 4. Flyway 管理结构，MyBatis-Plus 管理显式数据映射

数据库迁移使用只追加的版本化 SQL；初始迁移负责 pgvector 扩展、`stored_object`、`background_job` 及必要索引和约束。应用启用迁移校验，禁止通过 ORM 自动建表或启动脚本绕开 Flyway 改结构。

数据库访问使用 MyBatis-Plus，但不启用任何自动建表能力。持久化实体与领域对象分离：每个实体使用 `@TableName` 声明表、`@TableId` 声明主键、每个字段使用 `@TableField` 显式声明列名，避免依赖全局驼峰配置产生隐式契约。实体优先使用 Lombok 生成构造器和访问器；API DTO、值对象和需要保持不变量的领域模型继续使用 Java `record` 或显式方法，不为了 Lombok 牺牲不可变语义。

SQL 实现顺序固定为：优先使用 `BaseMapper`、Lambda Wrapper 等可编译检查的 Java API；这些 API 无法清楚表达条件更新或批量恢复时，才在 Mapper 方法上使用 `@Select`、`@Update` 等注解 SQL。项目不使用 XML Mapper，避免同一查询在 Java 接口和外部 XML 之间分散维护。无论采用 Java API 还是注解 SQL，领域和应用服务只依赖仓储端口，不直接拼接 SQL。

时间列使用带时区语义的数据库类型，并通过 MyBatis 类型处理确保以 `Instant` 的 UTC 语义往返；状态和进度约束由数据库与领域状态机共同保护。映射约束测试通过反射检查每个持久化字段均有显式列注解，真实 PostgreSQL 集成测试验证映射读写。集成测试启动与生产兼容的 PostgreSQL/pgvector 容器并执行相同迁移，不用 H2 模拟 PostgreSQL 行为。

### 5. 平台契约先于异常处理实现

先定义 `ApiError`、`FieldError`、错误码枚举、时钟端口、操作者端口与审计值对象，再实现 HTTP 异常映射、请求 trace 过滤器和持久化审计辅助代码。`ApiError` 固定包含 `code`、`message`、`timestamp`、`traceId`，字段校验失败时附加 `fieldErrors`；未知异常对外统一为安全消息。

trace ID 优先接受符合长度和字符约束的上游值，否则由服务生成，并写入响应头、错误体和日志上下文。默认 profile 使用 Spring Boot 的可读文本控制台格式，方便宿主机开发和调试；`prod` profile 才启用 Spring Boot 的 Logstash JSON 结构化输出，供日志采集系统解析。两种格式复用相同 logger、MDC 和集中脱敏规则，禁止记录 Authorization、密码、Token、模型密钥、对象正文和完整代码内容。

在 T2 接入认证前，审计操作者固定为显式 `SYSTEM` 身份；T2 只需替换操作者端口实现，不修改已有表的审计语义。公共契约、实现策略和关键脱敏分支必须添加中文 Javadoc 或中文原因注释。

### 6. 对象存储采用端口与本地适配器

应用层先定义 `ObjectStorage` 端口及 `put/get/delete/exists` 语义、`StoredObject` 元数据和分类异常，再实现本地适配器。对象键由服务生成 UUID，不接受原始文件名作为路径；磁盘布局可按对象键前缀分层，但该布局不进入端口契约。对象元数据仓储端口由 MyBatis-Plus Mapper 适配，业务代码不直接依赖 Mapper 或持久化实体。

写入流程为：校验元数据与根目录 → 在根目录内创建临时文件并流式计算大小/SHA-256 → 原子移动为最终对象 → 在事务中写入 `stored_object` 元数据。数据库写入失败时立即删除最终文件；进程崩溃可能留下的孤儿文件由后续受控清理处理，但读取只承认数据库中可用的对象记录。删除先将记录转为删除中状态、移除文件，再完成元数据删除；重复删除返回成功。

所有解析后的路径必须规范化并验证仍位于配置根目录，且不跟随会逃逸根目录的符号链接。存储根目录不可写、空间不足和校验失败映射为稳定存储错误。备选 S3/MinIO 不在 T1 实现，因为需求只要求稳定替换边界且调研已排除默认 MinIO。

### 7. 后台任务使用数据库记录和有界线程池

先定义任务提交、状态查询、进度/心跳更新、成功、失败和取消的应用端口，以及状态转换领域规则；再实现基于 MyBatis-Plus Mapper 的仓储适配器与线程池调度。`background_job` 保存 UUID、类型、状态、进度、输入对象键、可选范围引用、创建/开始/完成/心跳时间、执行实例、错误码、脱敏错误摘要和审计字段。

提交事务先持久化 `PENDING`，提交执行器后返回任务 ID；若有界队列拒绝，独立事务将记录终结为 `FAILED/CAPACITY_EXCEEDED`。工作线程通过条件更新把 `PENDING` 认领为 `RUNNING`，业务工作不持有创建事务；进度、心跳和终态均以短事务更新，终态条件更新防止重复完成。任务异常在边界统一捕获、分类和脱敏，绝不吞掉，也不传播到线程池导致其他任务停止。

线程数、队列容量、心跳阈值和优雅停机时间全部有安全默认值并可配置，但必须设置上限。启动恢复仅把超过心跳阈值的 `RUNNING` 任务标为 `FAILED/PROCESS_INTERRUPTED`，不自动重放；自动重试要等具体任务具备幂等规格后再设计。

### 8. 测试以风险最高的基础行为为主

后端使用 JUnit 5，并用真实 PostgreSQL/pgvector Testcontainers 验证迁移、约束、MyBatis-Plus 显式映射、存储元数据和任务事务；领域单元测试保护状态转换、进度约束、错误映射和路径安全；前端使用 Vitest 与 Vue Test Utils 验证最小运行状态和错误呈现。每个测试方法必须有中文注释说明业务目的及所防止的回归。

最小关键测试集包括：迁移首次/重复执行；错误体与敏感信息保护；对象原子写入、重启读取、路径逃逸和重复删除；任务成功、失败、容量拒绝、非法转换和陈旧任务恢复。Docker Compose 冒烟测试验证完整栈启动，而不重复领域测试。

## Risks / Trade-offs

- [文件系统与数据库无法组成原子事务，崩溃可能留下孤儿文件] → 读取以数据库记录为准，补偿删除已知失败文件，并为后续清理任务保留可枚举机制。
- [后台任务仅适合单实例和 MVP 负载] → 使用数据库条件更新和执行实例字段降低重复认领风险，明确不宣称分布式调度；扩容前另建规格。
- [精确依赖版本受公司镜像可用性影响] → 在实现第一步完成版本解析和记录；若需要切换兼容线，先更新 OpenSpec，不静默替换。
- [完整 Compose 构建比本地快速路径慢] → 两种入口复用同一配置和迁移，CI/验收使用完整栈，日常开发可只启动依赖服务。
- [过早定义通用平台抽象可能偏离后续需求] → 只建立 T1 明确要求且已有替换边界的端口，不引入通用仓储、事件总线或插件框架。

## Migration Plan

1. 先提交版本矩阵、目录骨架、Wrapper/锁文件与空构建，确认工具链约束生效。
2. 引入 PostgreSQL/pgvector Compose 服务和初始 Flyway 迁移，使用集成测试验证空库与重复迁移。
3. 按契约、失败测试、最小实现顺序接入平台 API、对象存储和后台任务。
4. 加入前端最小运行状态页及数据库依赖 Compose，使用宿主机前后端进程执行数据库与端到端冒烟验证。
5. 由于不存在旧应用和旧数据，无在线迁移；回滚代码时必须同时使用兼容数据库迁移的版本，已执行迁移不得编辑或自动删除。
